## 一、导读

### 1.1 数据形态变换（自顶向下）

```text
形态 A  .dts（源码，给人看）
           │ dtc 编译
           ▼
形态 B  .dtb / dtb 二进制块（DDR 里连续字节，未展开）
           │ U-Boot fixup（改二进制块里的属性，可能换地址）
           ▼
        dtb'（fixup 后的二进制块，经 r2 交给内核）
           │ early_init_dt_*（仍按偏移读二进制块）
           │ unflatten_device_tree()
           ▼
形态 C  device_node 树（of_root，内核 C 结构体 + 指针）
           │ of_platform_populate + compatible
           ▼
        mxsfb_probe ──► /dev/fb0
```

### 1.2 两种独立配置链

| 链路 | 设备树 | 内核入口 | 作用 |
|------|--------|----------|------|
| **启动/NFS** | `/chosen/bootargs` | `early_init_dt_scan_chosen()` | 命令行、NFS 根文件系统 |
| **显示** | `lcdif` → `display` → `timing0` | `mxsfb_probe()` → `mxsfb_init_fbinfo_dt()` | 分辨率、LCDIF、fb0 |

改屏参只动**显示链**；NFS 只动 **bootargs**。同一 dtb 内并存，读取路径完全不同。

### 1.3 硬件 ↔ 节点 ↔ 驱动（速查）

| 硬件 | 设备树 | 驱动/子系统 |
|------|--------|-------------|
| LCDIF @ 0x021c8000 | `lcdif@021c8000` + `compatible` | **mxsfb** |
| RGB 时序 | `display` / `display-timings` / `timing0` | mxsfb + OF timing API |
| DATA0~23 / 同步脚 | `&lcdif { pinctrl-0 = ... }` | **pinctrl** |
| PWM 背光 | `backlight` + `pwms` | **pwm-backlight** |

Linux 下一般**不写新 LCD 驱动**；800×480 / 1024×600 同接口，差别在 `display-timings`。

### 1.4 三种形态对照（核心术语）

同一份板级信息，在启动过程中有 **三种「长相」**：

| 形态 | 是什么 | 典型位置 | 谁在用 | 怎么读 |
|------|--------|----------|--------|--------|
| **A · dts 源码** | 文本，有层级缩进 | `*.dts` 文件 | 人、dtc | 编辑器 |
| **B · dtb 二进制块** | 压平后的连续字节（头 + 结构区 + 字符串区） | TFTP 到 `0x83000000`；fixup 后或 `0x8eaf0000` | U-Boot、内核早期 | libfdt：`fdt_getprop()` |
| **C · device_node 树** | 内核分配的节点结构体，有 parent/child 指针 | 内核堆，`of_root` 为根 | 驱动、sysfs | `of_get_property()`、`of_parse_phandle()` |

**为何叫「压平（Flattened）」**：`.dts` 里是嵌套树；编译成 `.dtb` 后不用指针，而是用 **偏移量 + 字符串表** 串在同一整块字节里——像一张表，不是对象树。

**二进制块内部布局（概念）**：

```text
┌ header（magic = d0 0d fe ed）──┐
├ memory reserve map            │
├ structure block（节点/属性）   │  ← 按 offset 遍历，无 parent 指针
├ strings block（"compatible"…）│
└───────────────────────────────┘
```

**名称对照**（同形态 B，阶段不同叫法不同）：

| 说法 | 含义 |
|------|------|
| `.dtb` 文件 | 磁盘上的设备树二进制 |
| **dtb 二进制块** | 本文主用语；强调「在 DDR 里、尚未 unflatten」 |
| FDT blob / flat device tree | U-Boot、内核文档习惯叫法 |
| `initial_boot_params` | 内核源码里指向该块的指针 |

**关键边界**：

- **NFS bootargs、memory**：U-Boot fixup 改的是 **形态 B** 里 `/chosen` 等属性的字节；内核 early scan 读 **形态 B**。
- **lcdif / 1024×600 timing**：来自 **编译 dts** 写进 **形态 B** 的内容；fixup **一般不改**；mxsfb 在 **形态 C** 上匹配与读属性。
- **unflatten** = 把 **形态 B** 展开成 **形态 C**；此后 `/proc/device-tree/` 镜像 **形态 C**。

**板上确认二进制块合法**：

```text
=> md.b 83000000 4
83000000: d0 0d fe ed    ← 说明此处是 dtb 二进制块头部
```

## 三、启动阶段：dtb 二进制块如何进内核（boot/NFS 链）

> 显示链最终也在 **形态 C** 上匹配；本章讲 **形态 A→B→C** 的前半段，以及 **U-Boot fixup**（主要服务 NFS/启动链）。

### 3.1 U-Boot 加载与 bootz

```text
tftp 80800000 zImage
tftp 83000000 imx6ull-14x14-evk-emmc-gengtao0901-1024-600.dtb
bootz 80800000 - 83000000
```

| 步骤 | 内存地址 | 说明 |
|------|----------|------|
| zImage 加载 | `0x80800000` | 压缩内核；U-Boot 跳入此处 |
| dtb 加载 | `0x83000000` | **形态 B** 落入 DDR；与 zImage 分离 |
| 内核运行 | `0x80008000` | 解压后代码（PHYS_OFFSET + TEXT_OFFSET） |
| fixup 后 | 如 `0x8eaf0000` | **形态 B** 可能拷贝/扩容到新地址；**r2 指向最终块** |

**bootz 寄存器约定**：r0=0，r1=machine type（常忽略），**r2 = dtb 二进制块物理地址**。

内核 `head-common.S`：`str r2, [r6]` → `__atags_pointer` → `setup_machine_fdt()`。

日志中 `Flattened Device Tree blob at 83000000` 即 **「在 0x83000000 有一份 dtb 二进制块」**。

---

### 3.2 dtb 二进制块：从文件到内存

**不是**特殊硬件区域，就是 **普通 DDR 里连续字节**，格式符合 FDT（Flattened Device Tree）。

```text
PC: tftpboot/xxx.dtb（形态 B 文件）
         │ TFTP
         ▼
DDR: 0x83000000 起 36KB 左右（形态 B 运行时副本）
         │ bootz 内 fixup（仍属形态 B，内容可能被改）
         ▼
DDR: 0x8eaf0000 等（fixup 后副本，r2 常指这里）
         │ 内核 unflatten
         ▼
内核堆: device_node 树（形态 C，不再叫 dtb 块）
```

| 你想确认的事 | 看哪种形态 | 方法 |
|--------------|------------|------|
| bootargs 最终值 | B → 内核读出 | `Kernel command line:` |
| hactive=1024 是否进 dtb | **B** | PC：`dtc -I dtb -O dts` |
| lcdif 节点是否存在 | **C** | `ls /proc/device-tree/.../lcdif@021c8000/` |
| mxsfb 是否读到屏参 | **C** + 驱动 | `virtual_size`、`dmesg \| grep mxsfb` |

---

### 3.3 U-Boot fixup 详解

**fixup** = `bootz`/`bootm` 跳内核**之前**，U-Boot 用 **libfdt** 对 **形态 B** 做「读—改—可能搬家」，生成适合**当前这块板、这一次启动**的二进制块，再经 **r2** 交给内核。

```text
tftp 83000000 xxx.dtb          ← 编译产物（形态 B 模板）
        │
        ▼
bootz 内部 fixup               ← 改块内字节 + 可能 fdt_open_into 扩容/拷贝
        │
        ▼
r2 → fixup 后的形态 B          ← 内核只认这份，不直接读 U-Boot 环境变量
```

#### 3.3.1 为何要 fixup

编译 dtb 时，部分信息在 PC 上**写死或为空**；真正启动时只有 U-Boot 知道：

| 运行时信息 | 谁知道 | fixup 写入位置 |
|------------|--------|----------------|
| 本次命令行 | `setenv bootargs` | `/chosen/bootargs` |
| 实际 RAM | U-Boot 初始化 DDR 后 | `/memory` |
| 网口 MAC | `ethaddr` 等 | FEC 节点 `local-mac-address` |
| initrd 位置 | bootz 参数 | `/chosen/linux,initrd-*`（本项目 `-` 则无） |

**dtb 是模板，fixup 把「当前启动参数」填进二进制块。**

#### 3.3.2 bootz 内大致顺序

```text
1. 校验 zImage @ 80800000
2. 校验 dtb @ 83000000（magic d00dfeed）
3. fdt_shrink_to_minimum / fdt_open_into
      → 为增改属性扩容；可能拷贝到新缓冲区
      → 日志: Loading Device Tree to 8eaf0000 ... OK
4. fdt_fixup_memory / fdt_fixup_ethernet / 写 bootargs 等
5. r0=0, r1≈0, r2=fixup 后 dtb 物理地址
6. 跳 zImage（r2 由解压 stub 原样传给内核）
```

#### 3.3.3 常见 fixup 项 ↔ 内核消费

| U-Boot fixup | 二进制块内节点/属性 | 内核函数 | 结果 | 与屏显关系 |
|--------------|---------------------|----------|------|------------|
| 写 `$bootargs` | `/chosen/bootargs` | `early_init_dt_scan_chosen()` | `boot_command_line` | **无关** |
| RAM 探测 | `/memory` `reg` | `early_init_dt_scan_memory()` | memblock | 无关 |
| `$ethaddr` | FEC `local-mac-address` | 驱动读属性 | eth0 MAC | 无关 |
| 无 initrd（`-`） | 清 initrd 属性 | — | 无 ramdisk | 无关 |
| （通常**不**做） | `lcdif` / `timing0` | mxsfb 读 **形态 C** | 1024×600 | **屏参靠编译 dts** |

**NFS 链闭环**：

```text
setenv bootargs 'root=/dev/nfs nfsroot=...'
  → fixup 写入二进制块 /chosen/bootargs
  → 内核 early_init_dt_scan_chosen
  → 打印 Kernel command line: ...
```

内核**不会**再去读 U-Boot 环境变量；只读 r2 指向的二进制块。

**调试要点**：

- `Kernel command line:` 是 bootargs 的**最终真相**；
- 若 `boot` 走 EMMC 出厂脚本、未 `tftp+bootz`，fixup 可能未执行，command line 仍是旧值（见 `03`、`08`）。

#### 3.3.4 fixup 与显示链的边界

| 内容 | 谁决定 | fixup 会不会改 |
|------|--------|----------------|
| `root=/dev/nfs`、`nfsroot=...` | `$bootargs` | **会** |
| `/memory` | U-Boot 探测 | **会** |
| FEC MAC | `$ethaddr` | **常会** |
| `lcdif` / `display` / `timing0` | 你编译的 dts | **一般不会** |
| `virtual_size`、LCDIF 寄存器 | 内核 mxsfb | 与 fixup 无关 |

→ **分辨率不对**：查 tftpboot dtb 内容、是否加载正确文件，**不是**查 `setenv bootargs`。  
→ **NFS 挂不上**：查 bootargs、是否执行 bootz、command line 第一行。

#### 3.3.5 libfdt 在 fixup 里做什么

典型 API（U-Boot 与内核早期共用同一套思路）：

```text
fdt_check_header()     校验 magic
fdt_open_into()        拷到更大 buffer，便于增改
fdt_setprop()          写 bootargs 等字符串属性
fdt_setprop_u32()      写 initrd 地址等
fdt_path_offset()      找 /chosen、/memory
fdt_fixup_memory()     内存 banks
fdt_fixup_ethernet()   MAC
```

改的是 **structure block 里的属性字节**；块可能比编译时更大，故常需 `open_into` 扩容。

### 3.4 内核：读二进制块 → 展开为 device_node 树

| 阶段 | 形态 | 典型 API | 显示链 |
|------|------|----------|--------|
| early scan | **B**（r2 / `initial_boot_params`） | `of_get_flat_dt_prop()` | 否（仅 bootargs/memory） |
| unflatten | **B → C** | `unflatten_dt_node()` | 建立 lcdif 等节点 |
| 驱动 probe | **C** | `of_get_property()`、`of_parse_phandle()` | **mxsfb 在此读屏参** |

```text
setup_machine_fdt(r2)
  early_init_dt_verify()          校验形态 B
  early_init_dt_scan_nodes()      扫 /chosen、/memory（仍读形态 B）
unflatten_device_tree()           形态 B → 形态 C（of_root）
of_platform_populate()            形态 C 上创建 platform_device
mxsfb_probe()                     形态 C + 驱动代码
```

`/proc/device-tree/` = **形态 C** 的只读镜像，**不是**再去读 0x83000000 的原始 TFTP 落点。

两遍 unflatten：第一遍算大小，第二遍分配内存并建树；内核并 **reserve** dtb 块所在 DDR，防被当普通内存覆盖。

## 三-B、内核驱动匹配全过程（mxsfb + fb0 + 背光）

> 源码：`drivers/video/fbdev/mxsfb.c`  
> 时序 API：`drivers/video/of_display_timing.c`、`videomode.c`、`fbmon.c`  
> 背光：`drivers/video/backlight/pwm_bl.c`（独立 platform 驱动）  
> 下文 **A～H** 为显示链 **八段匹配**；**§4 分步** 展开各 dts 字段与寄存器细节。

### B.1 总览：八段匹配链

```text
A. 设备树展开 + 创建设备
   unflatten → of_platform_populate → platform_device（lcdif@021c8000，status=okay）

B. Platform 驱动匹配（LCDIF 控制器）
   compatible "fsl,imx28-lcdif" ↔ mxsfb_dt_ids[] → mxsfb_probe

C. 控制器硬件绑定（mxsfb_probe 前半）
   ioremap(021c8000) / IRQ / pix·axi·disp_axi 时钟 / 可选 enable-gpio

D. display phandle + timing 解析（mxsfb_init_fbinfo_dt）
   display → of_get_display_timings → videomode → fb_videomode → fb_var

E. 帧缓冲与 pinctrl
   fb 内存 mmap；pinctrl default；mxsfb_set_par → VDCTRL/TRANSFER_COUNT

F. 开控制器 + 注册 fb
   mxsfb_enable_controller（clk_pix）；register_framebuffer → /dev/fb0

G. 背光（独立驱动，与 mxsfb 并行匹配）
   pwm-backlight → PWM1 → GPIO1_IO08（BLT_PWM）

H. 用户态可见
   virtual_size=1024,600；dd/console 刷屏；背光 brightness 0~7
```

**与网卡（文档 10）的关键差别：**

| | 网卡 FEC | 显示 mxsfb |
|--|----------|------------|
| 匹配后还要「第二次绑定」 | open 时才 `of_phy_connect` PHY | **probe 内一次完成** timing→寄存器→fb0 |
| 子设备驱动 | PHY 有独立 phylib | RGB 屏**无**屏控驱动；timing 在 mxsfb 内解析 |
| 易忽略日志 | `Device eth0 not found` | `failed to find mxc display driver`（可忽略） |

### B.2 A 段：从 dtb 到 platform_device

```text
dtb → unflatten → device_node「lcdif@021c8000」
        ↓
of_platform_populate（遍历 aips2 子节点，顺序 ≈ dtsi）
        ↓
板级 status = "okay" → 创建 platform_device
        dev.of_node → 合并后的 lcdif 节点（含 pinctrl、display 等）
```

dtsi 默认 `status = "disabled"` → **不会**创建设备；板级 `&lcdif { status = "okay"; }` 是显示链起点。

### B.3 B 段：mxsfb 如何匹配 compatible

dts（`imx6ull.dtsi`）：

```dts
compatible = "fsl,imx6ul-lcdif", "fsl,imx28-lcdif";
```

驱动表（`mxsfb.c`）：

```c
static const struct of_device_id mxsfb_dt_ids[] = {
    { .compatible = "fsl,imx23-lcdif", .data = &mxsfb_devtype[0], },
    { .compatible = "fsl,imx28-lcdif", .data = &mxsfb_devtype[1], },
    { /* sentinel */ }
};
static struct platform_driver mxsfb_driver = {
    .driver.of_match_table = mxsfb_dt_ids,
    .probe = mxsfb_probe,
};
module_platform_driver(mxsfb_driver);
```

| 要点 | 说明 |
|------|------|
| 表内 **无** `imx6ul-lcdif` | 靠 dts **第二字符串** `fsl,imx28-lcdif` 命中 |
| 匹配成功 | `of_match_device()` → `pdev->id_entry` → `host->devdata` |
| 不是模块 insmod | 内核配置 `CONFIG_FB_MXS` 时 **built-in**，启动即注册 |

### B.4 C 段：`mxsfb_probe` 硬件绑定（按代码顺序）

| 顺序 | 代码 | dts / 硬件 |
|------|------|------------|
| 1 | 可选 `enable-gpio` | 部分板 LCD 电源脚（本板多靠背光） |
| 2 | `devm_ioremap_resource` → `host->base` | `reg = <0x021c8000 0x4000>` |
| 3 | `devm_request_irq` | `interrupts` |
| 4 | `devm_clk_get("pix"/"axi"/"disp_axi")` | `clocks` + `clock-names` |
| 5 | 可选 `regulator_get("lcd")` | 部分板 LCD 供电 |
| 6 | **`mxsfb_init_fbinfo(host)`** | 见 D、E 段 |
| 7 | **`mxsfb_dispdrv_init`** | 仅当存在 `disp-dev` 属性；RGB 直出**无**此属性 → 日志可忽略 |
| 8 | **`devm_pinctrl_get_select_default`** | `pinctrl-0 = pinctrl_lcdif_*` |
| 9 | **`mxsfb_set_par` + `mxsfb_enable_controller`** | 写 VDCTRL、开 clk_pix |
| 10 | **`register_framebuffer`** | 注册 **fb0** |
| 11 | `fb_blank(UNBLANK)` | 取消 blank |
| 12 | 日志 **`mxsfb initialized`** | probe 成功 |

### B.5 D 段：display / timing 匹配链（probe 内，非独立驱动）

```text
mxsfb_init_fbinfo_dt(host)
  │
  ├─ of_parse_phandle(np, "display", 0)     ← display = <&display0>
  │     → display_np（display0 节点）
  │
  ├─ of_property_read_u32(display_np, "bus-width", ...)   → ld_intf_width（24bit）
  ├─ of_property_read_u32(display_np, "bits-per-pixel") → var.bits_per_pixel（16）
  │
  ├─ of_get_display_timings(display_np)     ← display-timings 下所有 timing*
  │     └─ of_parse_display_timing(timing0)  per child
  │           hactive/vactive/clock-frequency/porch/*-active ...
  │
  ├─ videomode_from_timings(timings, &vm, i)
  ├─ fb_videomode_from_videomode(&vm, &fb_vm)
  ├─ 补丁 DE/像素沿：DISPLAY_FLAGS → fb_vm.sync
  └─ fb_add_videomode(&fb_vm, &fb_info->modelist)

mxsfb_init_fbinfo（续）
  modelist 第一条 → fb_videomode_to_var(var, ...)   → xres/yres/margin/pixclock
  host->sync = var.sync
```

| 阶段 | 匹配键 | 谁处理 |
|------|--------|--------|
| LCDIF 控制器 | `compatible` → **mxsfb** | platform 总线 |
| `display` 子节点 | **phandle**，非 compatible | `of_parse_phandle` |
| `timing0` | 节点名 + 属性名 | **OF display timing API**，不注册独立 platform 驱动 |
| RGB 屏模组 | 无 Linux 驱动 | 时序写死在 dts |

### B.6 E 段：`mxsfb_set_par` → LCDIF 寄存器

probe 末尾调用（`fb_info->var` 已由 D 段填好）：

```text
mxsfb_set_par(fb_info)
  TRANSFER_COUNT  ← xres / yres（1024×600）
  VDCTRL0         ← host->sync（HSYNC/VSYNC/DE/PCLK 极性）
  VDCTRL1~4       ← margin / hsync_len / vsync_len（635 / 1344 / …）
  NEXT_BUF        ← fb 物理地址

  clk_set_rate(clk_pix, pixclock)   ← timing0 clock-frequency 51.2MHz
  开 DOTCLK_MODE / RUN / SYNC
```

详见 **§4 Step 4～6** VDCTRL 与 RGB 时序说明。

### B.6.1 E 段展开：pinctrl 匹配全过程

> pinctrl **不走** lcdif 的 `compatible`，也**没有**名为 `pinctrl_lcdif` 的独立 platform 驱动。  
> 它是 **「控制器先注册 → 外设 probe 时按 phandle 引用 pin group → 写 IOMUXC 寄存器」** 的第二条链。

#### 两层结构：控制器 vs 消费者

```text
【控制器链 — 启动早期，arch_initcall】
iomuxc@020e0000          compatible = "fsl,imx6ul-iomuxc"
  └─ imx6ul-evk/         ← function 名 = 此子节点名
       lcdifdatgrp       ← group 名 = 此子节点名；fsl,pins = <...>
iomuxc-snvs@02290000     compatible = "fsl,imx6ull-iomuxc-snvs"
  └─ imx6ul-evk/
       lcdifresetgrp     ← 复位脚在 SNVS 域，**另一颗** pinctrl 控制器

【消费链 — mxsfb_probe 内，与 timing 同一设备节点】
&lcdif {
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_lcdif_dat      /* → lcdifdatgrp，属 iomuxc */
                 &pinctrl_lcdif_ctrl     /* → lcdifctrlgrp，属 iomuxc */
                 &pinctrl_lcdif_reset>;  /* → lcdifresetgrp，属 iomuxc_snvs */
};
```

| 层级 | 匹配键 | 驱动 / 入口 | 说明 |
|------|--------|-------------|------|
| IOMUXC 控制器 | `fsl,imx6ul-iomuxc` | `pinctrl-imx6ul.c` → `imx_pinctrl_probe` | 解析 `&iomuxc` 下全部 group，注册 pinctrl 子系统 |
| SNVS IOMUXC | `fsl,imx6ull-iomuxc-snvs` | 同上驱动、不同 `soc_info` | 管 SNVS_TAMPER* 等脚 |
| pin group | **phandle + 节点名**（如 `lcdifdatgrp`） | 无独立驱动 | label `pinctrl_lcdif_dat` 仅 dts 编译期符号 |
| 外设消费 | `pinctrl-names` + `pinctrl-0` | `devm_pinctrl_get_select_default` | 在 **lcdif 设备** 上解析，不是 iomuxc 上 |

#### 控制器 probe：group 如何被「登记」

`imx6ul_pinctrl_init()` 以 `arch_initcall` 注册 platform 驱动；`of_platform_populate` 创建 `iomuxc@020e0000` 设备后：

```text
imx6ul_pinctrl_probe
  → of_match_device("fsl,imx6ul-iomuxc")
  → imx_pinctrl_probe
       → imx_pinctrl_probe_dt
            遍历 iomuxc 子节点（imx6ul-evk）
            遍历每个 function 下的 group 子节点（lcdifdatgrp …）
            imx_pinctrl_parse_groups：读 fsl,pins，解析每脚的 mux/conf 寄存器偏移
       → pinctrl_register（向内核 pinctrl 子系统注册 group/function 表）
```

此时 **仅完成「字典登记」**，尚未写硬件；真正写 MUX/PAD 寄存器要等消费者 select state。

#### 消费者：`devm_pinctrl_get_select_default` 内部链

`mxsfb_probe` 在 `mxsfb_init_fbinfo` 之后、**仅当无 `disp-dev`（本板 RGB 直出）** 时调用：

```c
pinctrl = devm_pinctrl_get_select_default(&pdev->dev);
```

等价于：

```text
pinctrl_get(lcdif.dev)
  → create_pinctrl
       → pinctrl_dt_to_map
            读 pinctrl-names[0] = "default"
            读 pinctrl-0 的 3 个 phandle
            对每个 phandle 指向的 group 节点：
              dt_to_map_one_config
                向上 walk 父节点，找到挂有 pinctrl 驱动的 iomuxc / iomuxc_snvs
                imx_dt_node_to_map（pinctrl-imx.c）
                  grp = imx_pinctrl_find_group_by_name(np->name)  ← 按节点名 "lcdifdatgrp"
                  生成 PIN_MAP_TYPE_MUX_GROUP + PIN_MAP_TYPE_CONFIGS_PIN
pinctrl_lookup_state(p, "default")
pinctrl_select_state(p, state)
  → pinmux_enable_setting
       → imx_pmx_set：对每个 pin 写 IOMUXC MUX 寄存器 + PAD 配置
```

**要点**：一条 `pinctrl-0` 可混合引用 **两颗** 控制器下的 group（本板 `lcdif_reset` 在 `iomuxc_snvs`）；core 会对每个 group 分别找所属 `pctldev`。

#### dts 里一行 `fsl,pins` 展开后写什么

> **逐字段展开、ENABLE/DE 示例、内核两阶段解析** 见 **Step 1.1.2**；此处保留速查。

```dts
MX6UL_PAD_LCD_DATA00__LCDIF_DATA00  0x79
```

宏由 `imx6ull-pinfunc.h`（含 `imx6ul-pinfunc.h`）展开为 **6 个 u32**：`mux_reg`、`conf_reg`、`input_reg`、`mux_mode`（ALT 功能号）、`input_val`、`pad_config`（即行末 `0x79`）。

| 字段 | 硬件效果 |
|------|----------|
| `__LCDIF_DATA00` | 把 LCD_DATA00 pad 复用到 LCDIF DATA0 |
| `0x79` | **PAD_CTL**：驱动能力、上下拉、压摆率等（写 conf 寄存器） |
| （对比网卡） | ENET `TX_CLK` 常用 `0x4001B009`，含 `IMX_PAD_SION` 等特殊位；LCDIF 用 `0x79` 即可 |

写寄存器基址：`iomuxc` → `0x020E0000`；`iomuxc_snvs` → `0x02290000`（与 `reg` 一致）。

#### 本板屏幕相关三组 pin

| label | group 节点 | 控制器 | 脚 |
|-------|------------|--------|-----|
| `pinctrl_lcdif_dat` | `lcdifdatgrp` | iomuxc | LCD_DATA00～23 → LCDIF DATA |
| `pinctrl_lcdif_ctrl` | `lcdifctrlgrp` | iomuxc | CLK / ENABLE(DE) / HSYNC / VSYNC |
| `pinctrl_lcdif_reset` | `lcdifresetgrp` | **iomuxc_snvs** | SNVS_TAMPER9 → GPIO5_IO09（屏复位） |

背光 PWM 脚 **独立一条消费链**（不经 mxsfb）：

```dts
&pwm1 { pinctrl-0 = <&pinctrl_pwm1>; };   /* GPIO1_IO08 → PWM1_OUT */
backlight { pwms = <&pwm1 ...>; };        /* pwm-backlight 只引用 pwm 设备 */
```

#### 与 mxsfb / FEC 的 API 对比

| 外设 | 调用点 | API |
|------|--------|-----|
| lcdif / mxsfb | probe 内，`!host->dispdrv` 分支 | `devm_pinctrl_get_select_default` |
| fec1 / fec2 | probe 开头 | `pinctrl_pm_select_default_state` |
| 效果 | 相同 | 都是 `pinctrl_get` + 选 `"default"` state + 写 IOMUXC |

pinctrl 失败时 mxsfb **probe 直接返回错误**，不会出现 `mxsfb initialized`；故 dmesg 有 initialized 通常表示 pinctrl 已成功（无单独 success 日志）。

#### 常见误区

| 误区 | 正解 |
|------|------|
| 「pinctrl 靠 compatible 匹配 lcdif」 | compatible 只匹配 **iomuxc 控制器**；lcdif 侧是 **phandle 引用** |
| 「三个 label 要写在 &lcdif 下面」 | group 定义在 `&iomuxc` / `&iomuxc_snvs`；lcdif 只 **引用** |
| 「timing 对了就一定有图像」 | MUX 未切到 LCDIF 时，VDCTRL 正确也看不到 RGB 波形 |
| 「reset group 必须跟 dat 同一 iomuxc」 | SNVS 脚必须走 `iomuxc_snvs` 控制器，不能放进主 iomuxc 树 |

验证与 **§4 Step 1.1.1**、**Step 1.1.2**、**Step 8.1**、**§6.2** 对照；网卡 pinctrl 对称说明见文档 **10** **§3.4.1**、**Step 1.1/1.2**。

### B.8 G 段：背光——独立驱动的匹配

```dts
backlight {

    default-brightness-level = <...>;
```

```text
of_platform_populate
  → platform_device「backlight」
  → pwm-backlight 驱动 probe（compatible 匹配）
```

| 子系统 | 驱动 | 匹配键 |
|--------|------|--------|

### Step 1 — `lcdif: lcdif@021c8000` 如何匹配到 mxsfb

> 本步回答：你写的 `lcdif: lcdif@021c8000` **本身不会去找驱动**；匹配是「板级启用 → 创建设备 → compatible 绑驱动」完成的。  
> 与 Step 2 的区别：**本步 = 匹配控制器节点**；**Step 2 = probe 内用 phandle 找 display 子节点**。

#### 1.1 这一行在 dts 里分别表示什么

SoC 级定义在 `imx6ull.dtsi`（本项目 overlay 路径同）：

```dts
lcdif: lcdif@021c8000 {
    compatible = "fsl,imx6ul-lcdif", "fsl,imx28-lcdif";
    reg = <0x021c8000 0x4000>;
    interrupts = <GIC_SPI 5 IRQ_TYPE_LEVEL_HIGH>;
    clocks = <&clks IMX6UL_CLK_LCDIF_PIX>,
             <&clks IMX6UL_CLK_LCDIF_APB>,
             <&clks IMX6UL_CLK_DUMMY>;
    clock-names = "pix", "axi", "disp_axi";
    status = "disabled";   /* SoC 默认关，板级必须改 okay */
};
```

| 片段 | 含义 |
|------|------|
| `lcdif:` | **label**，给板级写 `&lcdif { ... }` 用，编译进 dtb 后消失 |
| `lcdif@021c8000` | **节点名@单元地址**；`021c8000` 与 `reg` 首地址一致 |
| `compatible` | **匹配键**，驱动靠它认设备（见 1.4） |
| `reg` / `interrupts` / `clocks` | probe 里 `ioremap`、申请 IRQ、拿时钟 |
| `status = "disabled"` | 默认关；不改成 `okay` 就不会创建设备 |

板级在 `imx6ull-14x14-evk-gengtao0901.dts` 里**合并**（不是新建第二个 lcdif）：

```dts
&lcdif {
    /* 分辨率/时序由 *-1024-600.dts 配置；此处只开节点 + pinctrl */
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_lcdif_dat
                 &pinctrl_lcdif_ctrl
                 &pinctrl_lcdif_reset>;
    status = "okay";
};
```

#### 1.1.1 `pinctrl-0 = <&...>` 里的 `<>` 如何理解

> 本小节专门解释上式中 **`pinctrl-names` / `pinctrl-0` / `<>` 内三个 `&label`** 的含义；**group 内每行 `MX6UL_PAD_... 0x79`** 见 **Step 1.1.2**；机制总线见 **§3-B B.6.1**，验证见 **§4 Step 8.1**。

**一句话**：`<&pinctrl_lcdif_dat &pinctrl_lcdif_ctrl &pinctrl_lcdif_reset>` 表示 lcdif 在 **default** 状态下要启用 **三组** 预先定义好的引脚配置；dtc 把 label 编译成 phandle；mxsfb probe 时内核逐个解析，把 pad 切到 LCDIF/GPIO 并写 PAD 电气参数。

##### （1）`<>` 与 `pinctrl-names` / `pinctrl-0` 的分工

设备树里 `<>` 表示 **cell 数组**（一串 32 位整数）。对 `pinctrl-0` 而言，每个 cell 是一个 **phandle**——指向别处定义好的 **pin group 节点**。

```dts
pinctrl-names = "default";          /* 给 state 起名字 */
pinctrl-0 = <&pinctrl_lcdif_dat     /* state 0 = "default" 要用的 group 列表 */
             &pinctrl_lcdif_ctrl
             &pinctrl_lcdif_reset>;
```

| 属性 | 含义 |
|------|------|
| `pinctrl-names = "default"` | 第 0 个 state 名叫 `"default"` |
| `pinctrl-0 = <...>` | 第 0 个 state 引用哪些 pin group（与 `pinctrl-names` 下标一一对应） |
| `&pinctrl_lcdif_dat` 等 | **label 引用**（dts 源码写法）；dtc 编译时换成 phandle 数字 |

`&` 是设备树 **label 引用**，不是 C 语言取地址。`pinctrl_lcdif_dat` 是在别处给节点起的别名，编译进 dtb 后 **label 消失**，只留下 phandle 数字。

##### （2）三个 label 分别指向哪里？

pin group **定义在 IOMUXC 控制器下**，不在 `&lcdif` 下。本板 `gengtao0901.dts` 中：

**① 数据脚（24 根 RGB）— 主 iomuxc**

```dts
/* &iomuxc { imx6ul-evk { ... } } */
pinctrl_lcdif_dat: lcdifdatgrp {
    fsl,pins = <
        MX6UL_PAD_LCD_DATA00__LCDIF_DATA00  0x79
        /* ... DATA01～DATA23 ... */
    >;
};
```

**② 同步/时钟脚 — 主 iomuxc**

```dts
pinctrl_lcdif_ctrl: lcdifctrlgrp {
    fsl,pins = <
        MX6UL_PAD_LCD_CLK__LCDIF_CLK        0x79
        MX6UL_PAD_LCD_ENABLE__LCDIF_ENABLE  0x79   /* DE */
        MX6UL_PAD_LCD_HSYNC__LCDIF_HSYNC    0x79
        MX6UL_PAD_LCD_VSYNC__LCDIF_VSYNC    0x79
    >;
};
```

**③ 复位脚 — SNVS 域 iomuxc（另一颗 pinctrl 控制器）**

```dts
/* &iomuxc_snvs { imx6ul-evk { ... } } */
pinctrl_lcdif_reset: lcdifresetgrp {
    fsl,pins = <
        MX6ULL_PAD_SNVS_TAMPER9__GPIO5_IO09  0x79
    >;
};
```

编译后 dtb 中的逻辑关系：

```text
lcdif@021c8000
  pinctrl-names = "default"
  pinctrl-0 = <0xNN 0xMM 0xKK>     ← 三个 phandle 数字

phandle 0xNN → .../iomuxc@020e0000/imx6ul-evk/lcdifdatgrp
phandle 0xMM → .../iomuxc@020e0000/imx6ul-evk/lcdifctrlgrp
phandle 0xKK → .../iomuxc-snvs@02290000/imx6ul-evk/lcdifresetgrp
```

| phandle 引用（源码 label） | group 节点名 | 管什么脚 | pinctrl 控制器 |
|---------------------------|--------------|----------|----------------|
| `&pinctrl_lcdif_dat` | `lcdifdatgrp` | DATA00～23 | `iomuxc@020e0000` |
| `&pinctrl_lcdif_ctrl` | `lcdifctrlgrp` | CLK / DE / HS / VS | 同上 |
| `&pinctrl_lcdif_reset` | `lcdifresetgrp` | 屏复位 GPIO | `iomuxc-snvs@02290000` |

三个写在一个 `pinctrl-0` 里 = **「default」state 同时启用这三组**；内核依次解析、依次写 IOMUXC 寄存器。也可合成一个 group，但按功能分组更清晰，且 reset 必须在 SNVS 控制器下。

##### （3）与 `display = <&display0>` 的类比

| 属性 | `<>` 里引用的是 | 消费方（mxsfb_probe 内） |
|------|----------------|--------------------------|
| `display = <&display0>` | 显示时序子节点 | `of_parse_phandle("display", 0)` |
| `pinctrl-0 = <&pinctrl_lcdif_dat ...>` | 引脚 group 节点 | `devm_pinctrl_get_select_default` |

二者都是 **phandle 引用**，不是 `compatible` 字符串匹配；区别是一个找 timing，一个找 pin mux。

##### （4）内核如何用这三个 phandle？

`mxsfb_probe` 在 RGB 直出（无 `disp-dev`）时调用：

```c
pinctrl = devm_pinctrl_get_select_default(&pdev->dev);
```

内部链（源码路径：`drivers/pinctrl/devicetree.c`、`drivers/pinctrl/freescale/pinctrl-imx.c`）：

```text
① pinctrl_dt_to_map
   读 lcdif 的 pinctrl-0 → [phandle₁, phandle₂, phandle₃]
   对每个 phandle：
     np_config = of_find_node_by_phandle(phandle)   ← 找到 lcdifdatgrp 等
     dt_to_map_one_config
       向上 walk 父节点 → 定位 iomuxc 或 iomuxc_snvs
       imx_dt_node_to_map

② imx_dt_node_to_map
   grp = imx_pinctrl_find_group_by_name(np->name)   ← 按节点名 "lcdifdatgrp"
   生成 PIN_MAP_TYPE_MUX_GROUP + PIN_MAP_TYPE_CONFIGS_PIN

③ pinctrl_lookup_state(p, "default")     ← 对应 pinctrl-names[0]
   pinctrl_select_state → imx_pmx_set
     写 IOMUXC MUX 寄存器 + PAD 配置（0x79 等）
```

**匹配键是 group 节点名**（`lcdifdatgrp`），不是 label（`pinctrl_lcdif_dat`），也不是 group 上的 `compatible`。

##### （5）与 lcdif 驱动匹配的关系（勿混）

```text
lcdif compatible "fsl,imx28-lcdif"     →  platform 总线匹配 mxsfb
pinctrl-0 三个 phandle               →  pinctrl 子系统（phandle 链）
iomuxc compatible "fsl,imx6ul-iomuxc" →  更早注册的 pinctrl 控制器驱动
```

timing 与 pinctrl **挂在同一 lcdif 节点**，但走 **不同代码路径**：timing → VDCTRL；pinctrl → IOMUXC。pinctrl 失败则 mxsfb probe 直接 abort，不会出现 `mxsfb initialized`。

##### （6）板上验证 pinctrl 属性是否进 dtb

```bash
ls /proc/device-tree/soc/aips-bus@02100000/lcdif@021c8000/
# 应有 pinctrl-0、pinctrl-names

xxd /proc/device-tree/soc/aips-bus@02100000/lcdif@021c8000/pinctrl-0
# 三个 big-endian u32，即三个 phandle

dmesg | grep mxsfb
# 有 "initialized" 通常表示 pinctrl 已成功（失败则 probe 不会走到这里）
```

#### 1.1.2 `fsl,pins` 单行：`MX6UL_PAD_...  0x79` 如何理解

> 本小节解释 pin group 内 **每一行** 的语义；与 Step 1.1.1（group 级 phandle 引用）配合阅读。机制总线见 **§3-B B.6.1**。

**示例**（`lcdifctrlgrp` 内一行）：

```dts
MX6UL_PAD_LCD_ENABLE__LCDIF_ENABLE  0x79
```

**一句话**：宏名选定 **哪颗 pad、复用到哪个 ALT 功能**；行末 `0x79` 写 **PAD 电气参数**；mxsfb probe 选 default state 时，内核向 IOMUXC 写 MUX + PAD_CTL 寄存器。

##### （1）这一行在 dts 里拆成两半

| 部分 | 含义 |
|------|------|
| `MX6UL_PAD_LCD_ENABLE__LCDIF_ENABLE` | **选 pad + 选复用功能**（由 NXP `imx6ul-pinfunc.h` 宏给出 5 个 cell） |
| `0x79` | **该 pad 的 PAD 电气配置**（驱动强度、上下拉、边沿速度等，第 6 个 cell） |

出现在 group 的 `fsl,pins` 属性中，例如：

```dts
pinctrl_lcdif_ctrl: lcdifctrlgrp {
    fsl,pins = <
        MX6UL_PAD_LCD_CLK__LCDIF_CLK        0x79
        MX6UL_PAD_LCD_ENABLE__LCDIF_ENABLE  0x79
        MX6UL_PAD_LCD_HSYNC__LCDIF_HSYNC    0x79
        MX6UL_PAD_LCD_VSYNC__LCDIF_VSYNC    0x79
    >;
};
```

##### （2）宏名怎么读？

命名规则：

```text
MX6UL_PAD_<物理 pad 名>__<复用后的外设信号名>
         └─ 芯片引脚      └─ 该 pad 的某一组 ALT 功能
```

对本行：

| 片段 | 含义 |
|------|------|
| `MX6UL_PAD` | i.MX6UL 引脚宏前缀 |
| `LCD_ENABLE` | 封装上的 **物理 pad 名**（本板 RGB 屏 **DE/Data Enable** 常接此脚） |
| `LCDIF_ENABLE` | 复用为 **LCDIF 的 ENABLE（DE）输出** |

同一 pad 还可复用到其它功能，宏里用不同 `mux_mode` 区分。`imx6ul-pinfunc.h` 中同 pad 的其它选项：

```dts
#define MX6UL_PAD_LCD_ENABLE__LCDIF_ENABLE    0x0108 0x0394 0x0000 0x0 0x0
#define MX6UL_PAD_LCD_ENABLE__LCDIF_RD_E      0x0108 0x0394 0x0000 0x1 0x0
#define MX6UL_PAD_LCD_ENABLE__GPIO3_IO01      0x0108 0x0394 0x0000 0x5 0x0
```

选 `__LCDIF_ENABLE` = 选 **ALT0（mux_mode = 0）**，硬件信号连到 LCDIF，而非 GPIO/UART 等。

##### （3）宏展开：实际 6 个 u32（24 字节）

头文件说明（`imx6ul-pinfunc.h`）：

```text
pin function ID = <mux_reg conf_reg input_reg mux_mode input_val>
加上行末 pad_config → fsl,pins 每行共 6 个 cell（FSL_PIN_SIZE = 24 字节）
```

本行 dtc 预处理后等价于：

```text
MX6UL_PAD_LCD_ENABLE__LCDIF_ENABLE  0x79

→  0x0108   mux_reg      IOMUXC MUX 寄存器偏移
   0x0394   conf_reg     IOMUXC PAD 配置寄存器偏移
   0x0000   input_reg    输入选择寄存器偏移（本脚不用，为 0）
   0x0      mux_mode     ALT0 = LCDIF_ENABLE
   0x0      input_val    输入选择值（本脚为 0）
   0x79     pad_config   电气参数（dts 里手写部分）
```

IOMUXC 基址 `0x020E0000`（`imx6ull.dtsi` 中 `iomuxc@020e0000`），物理地址：

| 寄存器 | 偏移 | 物理地址 | select state 时写入 |
|--------|------|----------|---------------------|
| MUX | `0x0108` | `0x020E0108` | `0x0`（LCDIF ENABLE / DE） |
| PAD_CTL | `0x0394` | `0x020E0394` | `0x79` |

##### （4）`0x79` 是什么？与宏前半段的分工

| 写什么 | 寄存器 | 谁决定 | 作用 |
|--------|--------|--------|------|
| **复用功能** | MUX | 宏名（`mux_mode = 0x0`） | pad 连到 LCDIF DE，还是 GPIO 等 |
| **电气特性** | PAD_CTL | 行末 `0x79` | 驱动强度、边沿、上下拉等 |

`0x79` **不是** ALT 编号，而是 **SW_PAD_CTL** 整寄存器值。NXP EVK 上 LCD 并行口常用此值（较快边沿、适合 ~51.2MHz RGB 总线）。细位域查 **i.MX6ULL RM → IOMUXC → SW_PAD_CTL**。

对比网卡（文档 10）：

```dts
MX6UL_PAD_ENET1_TX_CLK__ENET1_REF_CLK1  0x4001B009
```

高位 `0x40000000` = **`IMX_PAD_SION`**（强制输入路径），REF_CLK 需要；LCD DE/数据线用简单 **`0x79`** 即可，无需 SION。

##### （5）内核两阶段：解析 vs 写硬件

**阶段 A — iomuxc probe（登记，尚未写 pad）**

`imx_pinctrl_parse_groups` 读 `fsl,pins`，每行 6 cell 解析进 `struct imx_pin`（`pinctrl-imx.c`）：

```text
mux_reg, conf_reg, input_reg, mux_mode, input_val, config(0x79)
  → pin->mux_mode = 0x0
  → pin->config   = 0x79
```

**阶段 B — mxsfb probe 选 default state（写 IOMUXC）**

```text
devm_pinctrl_get_select_default
  → pinctrl_select_state("default")
  → imx_pmx_set：writel(0x0, base + 0x0108)     /* MUX → LCDIF_ENABLE */
  → imx_pinconf_set：writel(0x79, base + 0x0394) /* PAD_CTL */
```

源码对应（`drivers/pinctrl/freescale/pinctrl-imx.c`）：

- `imx_pmx_set` → `writel(pin->mux_mode, ipctl->base + pin_reg->mux_reg)`
- `imx_pinconf_set` → `writel(configs[i], ipctl->base + pin_reg->conf_reg)`

##### （6）与显示链、Step 1.1.1 的关系

```text
Step 1.1.1  pinctrl-0 phandle → 引用 lcdifctrlgrp（group 级）
Step 1.1.2  fsl,pins 每一行   → group 内单 pin 的 MUX + PAD（脚级）

LCDIF 控制器（0x021C8000）产生 DE 时序（Step 2~5 / VDCTRL）
       ↓ pad 已 mux 为 LCDIF_ENABLE
芯片 LCD_ENABLE 引脚 → PCB → ATK 7 寸屏 DE 输入
```

- **timing 对、MUX 错**：DE 信号到不了屏脚，仍可能无图像  
- **MUX 对、timing 错**：脚上有信号但时序不对，花屏/不同步  

##### （7）同 group 四行对照（ctrl 组）

| fsl,pins 行 | pad | LCDIF 信号 | mux_mode |
|-------------|-----|------------|----------|
| `...LCD_CLK__LCDIF_CLK` | LCD_CLK | 像素时钟 PCLK | 0 |
| `...LCD_ENABLE__LCDIF_ENABLE` | LCD_ENABLE | **DE** | 0 |
| `...LCD_HSYNC__LCDIF_HSYNC` | LCD_HSYNC | 行同步 | 0 |
| `...LCD_VSYNC__LCDIF_VSYNC` | LCD_VSYNC | 场同步 | 0 |

四行 PAD 配置均为 `0x79`；**区别在宏名（不同 pad、不同 mux 偏移）**，不是 `0x79` 不同。

##### （8）一句话速记

```text
MX6UL_PAD_LCD_ENABLE__LCDIF_ENABLE  0x79
│                                    │
│                                    └─ 电气：0x020E0394 ← 0x79
└─ 复用：0x020E0108 ← 0x0（ALT0 = LCDIF DE 输出）
```

`*-1024-600.dts` 再在同一节点上追加 `display = <&display0>` 与 timing（见 Step 2~5）。

#### 1.2 数值 `021c8000`：从哪里来、有什么作用

> **不是随便写的数**，而是 **i.MX6ULL 芯片手册 Memory Map 里规定的 LCDIF 寄存器物理基址**。

**来源**

| 外设 | 物理基址 | 说明 |
|------|----------|------|
| AIPS-2 总线窗口 | `0x02100000` 一带 | 很多外设挂在这条总线上（dtsi 中 `aips-bus@02100000`） |
| **LCDIF** | **`0x021C8000`** | LCD 接口控制器寄存器起始地址 |
| 寄存器区长度 | **`0x4000`（16KB）** | 对应 `reg` 的第二个 cell |

手册：*i.MX 6ULL Applications Processor Reference Manual* → Memory Map → LCDIF。

设备树写法：

```dts
aips2: aips-bus@02100000 {
    ...
    lcdif: lcdif@021c8000 {
        reg = <0x021c8000 0x4000>;   /* 基址 + 长度 */
        ...
    };
};
```

- `@021c8000`：节点单元地址，惯例与 `reg` 基址一致  
- `reg = <基址 长度>`：真正告诉内核「从哪开始、占多大」  
- 板级 `&lcdif { ... }` **不要改这个数**——同一颗 SoC 上 LCDIF 基址固定；换屏只改 timing

**作用**

CPU 只能通过**物理地址**访问外设寄存器。`0x021c8000` 是 LCDIF 寄存器在总线上的「门口」：

```text
物理地址               含义（相对偏移，见 mxsfb.c 宏）
0x021c8000 + 0x00     LCDC_CTRL
0x021c8000 + 0x70     LCDC_VDCTRL0
0x021c8000 + 0x80     LCDC_VDCTRL1
...
```

mxsfb probe 中：

```c
res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
/* 从 dts 的 reg 解析出 start=0x021c8000, size=0x4000 */

host->base = devm_ioremap_resource(&pdev->dev, res);
/* 映射成内核虚拟地址，后续 writel(host->base + LCDC_VDCTRLx, ...) */
```

没有正确 `reg` → 驱动不知道往哪写 → 时序配不上、屏不亮。

**与「匹配驱动」的分工（勿混）**

| 字段 | 作用 |
|------|------|
| **`compatible`** | 决定绑哪个驱动（mxsfb） |
| **`reg` / `021c8000`** | 决定驱动往哪读写硬件（ioremap） |
| **`status = "okay"`** | 决定要不要创建设备 |

**如何自行确认**

```bash
# 手册 Memory Map + imx6ull.dtsi 中的 reg
# 板上（路径因内核略有差异）：
cat /proc/iomem | grep -i lcd
ls /sys/bus/platform/devices/ | grep 21c8000
```

**一句话**：`021c8000` 来自 SoC 内存映射表，是 LCDIF 外设寄存器物理基址；写进 `reg` 后 mxsfb 用它 `ioremap`，才能配置 1024×600 时序并刷屏。

#### 1.3 从多文件 dts 到内核里「一个节点」

```text
imx6ull.dtsi                 定义 lcdif（disabled）+ compatible + reg
        +
gengtao0901.dts              &lcdif { status=okay; pinctrl }
        +
*-1024-600.dts               &lcdif { display; timing... }
        │ dtc
        ▼
形态 B（dtb）                 只有一个 lcdif@021c8000（属性已合并）
        │ unflatten
        ▼
形态 C（device_node）         full_name 类似：
                             /soc/aips-bus@02100000/lcdif@021c8000
```

板上验证：

```bash
ls /proc/device-tree/soc/aips-bus@02100000/lcdif@021c8000/
cat /proc/device-tree/soc/aips-bus@02100000/lcdif@021c8000/compatible
# fsl,imx6ul-lcdif\0fsl,imx28-lcdif
cat .../status
# okay
```

#### 1.4 匹配分两步：先创建设备，再绑驱动

**第一步：platform 总线创建设备**

内核 init 阶段 `of_platform_populate()` 遍历形态 C：

```text
遍历 device_node
  ├─ of_device_is_available(np)?
  │     → status 为 "okay"/"ok"（或无 status）才算可用
  │     → 仍是 dtsi 默认 disabled → 直接跳过，不创建设备
  ├─ 节点有 compatible 属性?
  └─ of_platform_device_create()
        → platform_device
        → pdev->dev.of_node = 该 lcdif 的 device_node *
        → 挂到 platform 总线
```

**第二步：compatible 字符串匹配驱动**

mxsfb 注册时带 OF 匹配表（`drivers/video/fbdev/mxsfb.c`）：

```c
static const struct of_device_id mxsfb_dt_ids[] = {
    { .compatible = "fsl,imx23-lcdif", ... },
    { .compatible = "fsl,imx28-lcdif", ... },  /* i.MX6ULL 实际命中这条 */
};

static struct platform_driver mxsfb_driver = {
    .probe = mxsfb_probe,
    .driver = {
        .name = "mxsfb",
        .of_match_table = mxsfb_dt_ids,
    },
};
module_platform_driver(mxsfb_driver);
```

platform 总线 bind 时（`drivers/base/platform.c` → `of_driver_match_device`）：

```text
platform_match(dev, drv)
  → of_match_device(mxsfb_dt_ids, dev)
  → 取 dev->of_node 的 compatible 字符串列表，与驱动表逐项比较
```

| 侧 | compatible |
|----|------------|
| **节点（dtsi）** | `"fsl,imx6ul-lcdif"`, `"fsl,imx28-lcdif"` |
| **驱动表（mxsfb）** | `"fsl,imx23-lcdif"`, `"fsl,imx28-lcdif"` |

规则：节点列表里**任意一条**与驱动表某条相同即可。  
驱动表**没有** `fsl,imx6ul-lcdif`，但有 **`fsl,imx28-lcdif`** → 用节点第二项匹配成功。

这是 NXP 常见写法：SoC 专用名放前，**旧驱动兼容串**放后做 fall-back。

匹配成功后调用 `mxsfb_probe(pdev)`：

```c
np = pdev->dev.of_node;              /* 就是 lcdif@021c8000 那个节点 */
host->base = ioremap(0x021c8000, ...); /* 来自 reg */
/* 之后才是 Step 2~7：读 display phandle、timings、配寄存器、分配 fb */
```

#### 1.5 整条链（实现时你要保证什么）

```text
① dtsi 定义节点 + compatible + reg          （SoC 固定，一般不改）
② 板级 &lcdif { status = "okay"; pinctrl }  （必须做，否则不 probe）
③ 板级 &lcdif { display; timing... }         （屏参，*-1024-600.dts）
④ dtc → dtb → 启动 → unflatten（形态 B→C）
⑤ of_platform_populate → platform_device(of_node=lcdif)
⑥ compatible "fsl,imx28-lcdif" ↔ mxsfb_dt_ids
⑦ mxsfb_probe → ioremap / 读 display / fb0
```

| 机制 | 作用对象 | 匹配方式 |
|------|----------|----------|
| **platform + compatible** | `lcdif@021c8000` | 字符串 ↔ `mxsfb_dt_ids` |
| **phandle**（Step 2） | `display` / `timing0` | 数字 ID，probe 内 `of_parse_phandle` |

`display0` **没有**单独 compatible 去匹配 mxsfb；它是 lcdif 的子节点，由 probe 通过 `display = <&display0>` 找到。

#### 1.6 失败条件与排查

| 检查项 | 不通过现象 |
|--------|------------|
| `&lcdif { status = "okay"; }` | 无 platform_device，无 fb0 |
| compatible 不含驱动表中任一项 | mxsfb 绑不上 |
| 内核未编入 mxsfb（如 `CONFIG_FB_MXS`） | 驱动未注册 |
| `display` / timing 缺失 | 本步已成功，但 Step 2~5 失败 |
| pinctrl / 背光 | 有 fb 尺寸可能仍黑屏（Step 8） |

```bash
# 节点在不在、开没开（路径写全，勿照抄文档里的 "..."）
ls /proc/device-tree/soc/aips-bus@02100000/lcdif@021c8000/
cat /proc/device-tree/soc/aips-bus@02100000/lcdif@021c8000/status
# 期望：okay

# 驱动绑没绑上 / 寄存器资源
ls /sys/bus/platform/devices/ | grep 21c8000
# 期望：21c8000.lcdif
cat /proc/iomem | grep -i lcd
# 期望：021c8000-021cbfff : .../lcdif@021c8000
dmesg | grep -i mxsfb
```

**一句话**：`lcdif: lcdif@021c8000` 在 dtsi **声明**硬件；板级 `&lcdif { status = "okay" }` **启用**；unflatten 后进形态 C；`of_platform_populate` 创建 platform 设备；**`compatible` 里的 `fsl,imx28-lcdif` 与 mxsfb 表对上** 即进入 `mxsfb_probe`——这就是「匹配到 lcdif」的完整过程。

### Step 2 — `display` phandle 找到 display 节点

> 本步回答两件事：  
> 1. `display0: display` 这种写法是什么意思？  
> 2. `display = <&display0>` / 编译成 `0x2a` 有什么用、为什么要这样写？

#### 2.1 设备树写法（本项目）

```dts
&lcdif {
    display = <&display0>;     /* lcdif：去找标签为 display0 的节点 */

    display0: display {        /* 节点名叫 display，标签是 display0 */
        bits-per-pixel = <16>;
        bus-width = <24>;
        display-timings { ... };
    };
};
```

#### 2.2 `display0: display` 是什么意思？

这是设备树的 **「标签: 节点名」** 语法：

```dts
display0: display {
    bits-per-pixel = <16>;
    ...
};
```

| 部分 | 是什么 | 作用 |
|------|--------|------|
| **`display0`** | **label（标签）** | 给节点起的“别名”，供 `&display0` / `<&display0>` 引用 |
| **`:`** | 分隔符 | 固定语法 |
| **`display`** | **节点名（node name）** | 节点在树里的名字，会出现在路径中 |
| `{ ... }` | 节点内容 | 属性、子节点 |

**节点名 `display`**

- 路径示例：`.../lcdif@021c8000/display`
- 表示“这是一块显示面板描述”，**不能**直接写进 `<&display>`（引用靠的是 label）
- 若合并出多个同名节点，procfs 里可能出现 `display#1`（见 `08`）

**标签 `display0`**

- **主要在 `.dts` 编译期有用**
- 用来写 `display = <&display0>` 或 `&display0 { ... }`
- 编进 `.dtb` 后，label 字符串一般不保留，变成 **phandle 数字**

**有无 label 的差别**

```dts
/* 只有节点名 —— 外面没法用 &xxx 引用 */
display {
    bits-per-pixel = <16>;
};

/* 有 label —— 别处可以 &display0 */
display0: display {
    bits-per-pixel = <16>;
};
```

命名习惯：`display` = 角色；`display0` = 第 0 块屏实例编号（不是寄存器地址）。

**一句话**：`display0: display` = **声明名为 display 的节点，并贴上标签 display0，方便被 `<&display0>` 引用。**

#### 2.3 为什么要写 `display = <&display0>`？phandle `0x2a` 有什么用？

**这样写的目的**

让 **lcdif（控制器）** 通过一个属性 **指向** 真正的屏参节点，而不是把分辨率直接堆在 lcdif 上：

| 写法 | 作用 |
|------|------|
| `display0: display { ... }` | 被引用目标：bpp、bus-width、timings 放这里 |
| `display = <&display0>` | lcdif 上的“指路牌”：去找 display0 |

mxsfb 驱动约定（绑定文档 / 代码）：

```text
先匹配 lcdif（Step 1，compatible）
  → of_parse_phandle(np, "display", 0)   // 属性名必须叫 "display"
  → 跟着引用读 bus-width、timings …
```

因此属性名 **`display`**、引用形式 **`<&label>`** 是为了 **符合驱动 API**，不是随意起名。

**职责分离**

- lcdif = SoC 上的 LCDIF 控制器（`reg`、时钟、中断）  
- display = 这块屏的参数（色深、总线宽、时序）  
- label 可维护：始终用 `&display0`，**不要手写** phandle 数字

**编译后变成 u32 phandle（如 `0x2a`）有什么用？**

`.dts` 里 `&display0` 给人看；**blob 里存不下字符串引用**，dtc 编成 **32 位数字 ID**：

```text
lcdif 节点:
  display = <0x0000002a>     ← 只是一个编号（指路牌）

display 节点:
  phandle = <0x0000002a>     ← 同一编号贴在自己身上
```

作用：在二进制设备树 / 形态 C 节点树里，用 **同一个数字** 把两个节点拴在一起。

运行时：

```text
mxsfb_probe
  → of_parse_phandle(lcdif, "display", 0)
  → 读出 0x2a
  → 整树查找 phandle == 0x2a 的节点
  → 得到 display 节点
  → 再读 bus-width、bits-per-pixel、display-timings
```

没有这个引用 → 驱动只认到控制器，**读不到 1024×600**。

#### 2.4 内核代码

```c
/* mxsfb_init_fbinfo_dt() — mxsfb.c */
display_np = of_parse_phandle(np, "display", 0);

/* drivers/of/base.c */
phandle = be32_to_cpup(display_property);
node = of_find_node_by_phandle(phandle);   /* 匹配 np->phandle */
```

```text
label "display0" 仅 dtc 编译期存在
形态 B 里只有 phandle 数字；unflatten（B→C）后写入 device_node->phandle
of_parse_phandle 在形态 C 上读 u32 → 整树查找 → 返回 display_np
```

#### 2.5 与 Step 1 的对比、调试要点

| 机制 | 作用对象 | 匹配方式 |
|------|----------|----------|
| Step 1：`compatible` | `lcdif@021c8000` | 字符串 ↔ mxsfb 驱动表 |
| Step 2：`display` phandle | `display` 节点 | u32 数字 ↔ `np->phandle` |

| 调试要点 | 说明 |
|----------|------|
| 始终用 `<&display0>` | 不要手写 `display = <0x2a>` |
| `/proc/.../lcdif@021c8000/display` | 文件内容是 phandle 的原始字节，不是路径字符串 |

| 成功旁证 | `virtual_size=1024,600`（说明 Step 2~5 已通） |

**一句话**：`display0: display` 定义“屏参节点 + 可引用标签”；`display = <&display0>` 是给 mxsfb 的指路牌，编译成 phandle 数字后在节点树里把 lcdif 和屏参拴在一起。

### Step 4~6 — `timing0` 属性如何一步步解析到 LCDIF 寄存器

> 对应 dts 中这一段（本项目 1024×600）：
>
> ```dts
> timing0: timing0 {
>     clock-frequency = <51200000>;
>     hactive = <1024>;
>     vactive = <600>;
>     hfront-porch = <160>;
>     hback-porch = <140>;
>     hsync-len = <20>;
>     vfront-porch = <12>;
>     vback-porch = <20>;
>     vsync-len = <3>;
>     hsync-active = <0>;
>     vsync-active = <0>;
>     de-active = <1>;
>     pixelclk-active = <0>;
> };
> ```
>
> 前提：Step 1 已匹配 lcdif；Step 2 已 `of_parse_phandle("display")`；Step 3 已读 bus-width/bpp。

#### 总览：五段变换

```text
timing0 节点属性（dts）
  │ ① of_get_display_timings / of_parse_display_timing
  ▼
struct display_timing（min/typ/max + flags）
  │ ② videomode_from_timings
  ▼
struct videomode（单值 + flags）
  │ ③ fb_videomode_from_videomode + mxsfb 补 DE/像素时钟极性
  ▼
struct fb_videomode → modelist → fb_var_screeninfo
  │ ④ mxsfb_set_par / mxsfb_enable_controller
  ▼
LCDIF 寄存器 + clk_pix
```

入口：`mxsfb_init_fbinfo_dt()` 里对 `display_np` 调用 `of_get_display_timings()`。

---

#### ① 找到 timing0 并读属性（`of_display_timing.c`）

```c
/* mxsfb.c */
timings = of_get_display_timings(display_np);
```

`of_get_display_timings()` 内部：

```text
1. of_get_child_by_name(display_np, "display-timings")  → 容器节点
2. of_parse_phandle(..., "native-mode", 0)               → <&timing0> 变节点指针
   （无 native-mode 则取第一个子节点）
3. for_each_child_of_node → of_parse_display_timing(entry, dt)
4. 若 entry == native_mode 节点 → disp->native_mode = 数组下标
```

**native-mode 本质**：phandle 指针相等，**不是**按名字 `"timing0"` 字符串查找。

**①-a 数值类属性：`parse_timing_property`**

你写的都是 **单 cell**（如 `<1024>`）：

```c
prop = of_find_property(np, name, &length);
cells = length / sizeof(u32);          // 单值为 1
of_property_read_u32(np, name, &result->typ);
result->min = result->typ;
result->max = result->typ;
```

| dts 属性 | `display_timing` 字段 | `.typ`（本项目） |
|----------|----------------------|------------------|
| `hback-porch` | `hback_porch` | 140 |
| `hfront-porch` | `hfront_porch` | 160 |
| `hactive` | `hactive` | **1024** |
| `hsync-len` | `hsync_len` | 20 |
| `vback-porch` | `vback_porch` | 20 |
| `vfront-porch` | `vfront_porch` | 12 |
| `vactive` | `vactive` | **600** |
| `vsync-len` | `vsync_len` | 3 |
| `clock-frequency` | `pixelclock` | **51200000** |

**①-b 极性类属性：变成 `flags` 位**

```c

void videomode_from_timing(const struct display_timing *dt, struct videomode *vm)
{
```

#### ③ `videomode` → `fb_videomode` → `fb_var`

**③-a 通用转换（`fbdev/core/fbmon.c`）**


| videomode | fb_videomode / fb_var | 本项目值 |
|-----------|------------------------|----------|
| `hactive` | `xres` | 1024 |
| `hback_porch` | `left_margin` | 140 |
| `hfront_porch` | `right_margin` | 160 |
| `hsync_len` | `hsync_len` | 20 |
| `vactive` | `yres` | 600 |
| `vback_porch` | `upper_margin` | 20 |
| `vfront_porch` | `lower_margin` | 12 |
| `vsync_len` | `vsync_len` | 3 |
| `pixelclock` (Hz) | `pixclock`（皮秒，`KHZ2PICOS`） | 对应 51.2MHz |

H/V sync 极性进入标准 fb sync 位（你为低有效 → **不**置 `FB_SYNC_*_HIGH_ACT`）。

```text

vtotal = 600 + 12 + 20 + 3     = 635

```

**③-b mxsfb 补 DE / 像素时钟极性（标准转换不处理这两项）**

```c
if (!(vm.flags & DISPLAY_FLAGS_DE_HIGH))      // 你是 DE_HIGH → 不置位
    fb_vm.sync |= FB_SYNC_OE_LOW_ACT;
if (vm.flags & DISPLAY_FLAGS_PIXDATA_NEGEDGE) // 你是 NEGEDGE → 置位
    fb_vm.sync |= FB_SYNC_CLK_LAT_FALL;
fb_add_videomode(&fb_vm, &fb_info->modelist);
```


> 多 timing 时 modelist 第一条取决于子节点遍历顺序，**不一定**等于 native-mode；单屏建议只保留一个 `timing0`。

#### ④ `fb_var` → LCDIF 寄存器（`mxsfb_set_par` / `enable_controller`）

**调用时机**：`mxsfb_probe` → `mxsfb_init_fbinfo` 之后 → `mxsfb_set_par(fb_info)`。

**④-a 分辨率 → TRANSFER_COUNT**

```c
writel(VCOUNT(yres) | HCOUNT(xres), ...);  // 600 × 1024
```

← `hactive` / `vactive`

**④-b 极性 → VDCTRL0**

```c
if (host->sync & FB_SYNC_HOR_HIGH_ACT)   // 否 → HSYNC 低有效
if (host->sync & FB_SYNC_VERT_HIGH_ACT)  // 否 → VSYNC 低有效
if (!(host->sync & FB_SYNC_OE_LOW_ACT))  // 真 → DE(ENABLE) 高有效
if (host->sync & FB_SYNC_CLK_LAT_FALL)   // 真 → DOTCLK 下降沿
VDCTRL0_SET_VSYNC_PULSE_WIDTH(vsync_len); // 3
```

← `*-active` + `vsync-len`

**④-c porch → VDCTRL1/2/3/4**

| 寄存器 | 计算 | 本项目值 |
|--------|------|----------|
| VDCTRL1 | upper+vsync+lower+yres | 20+3+12+600 = **635** |
| VDCTRL2 | left+hsync+right+xres | 140+20+160+1024 = **1344** |
| VDCTRL3 H wait | left+hsync | **160** |
| VDCTRL3 V wait | upper+vsync | **23** |
| VDCTRL4 | xres | **1024** |

**④-c 补充：VDCTRL 是什么意思？RGB 屏为什么也需要？**

RGB 并行屏（如 ATK-7RGBLCD）**不像 MIPI 带屏控**：模组通常只接收 **PCLK + HSYNC + VSYNC + DE + RGB 数据线**，**行/场时序必须由 SoC 的 LCDIF 产生**。  
dts 里 `timing0` 的 porch/sync 经驱动算进 VDCTRL，就是在告诉 LCDIF：**每一帧扫多少行、每一行多少个时钟、何时 DE 有效送像素**。

**物理信号（你板子原理图上的线）**

| 信号 | 作用 |
|------|------|
| **PCLK** | 像素时钟；每个 tick 推进一行内的时序 |
| **HSYNC** | 行同步：「新的一行开始」 |
| **VSYNC** | 场同步：「新的一帧开始」 |
| **DE（ENABLE）** | 数据有效：**仅 DE 有效时，DATA 上的才是该显示的像素** |
| **DATA0~23** | R/G/B 并行数据 |

屏不会自己推断「现在是第几个像素」；只按 HSYNC/VSYNC/DE/PCLK 约定采样 DATA。  
**没有 VDCTRL 这类配置 → 时序乱 → 黑屏、花屏、图像偏移。**

**一帧 / 一行里有什么（与 dts 字段对应）**

```text
一帧（垂直）
┌──────────────────────────────────────┐
│  upper porch(20) + vsync(3)          │  ← 场消隐 + 场同步
├──────────────────────────────────────┤
│  有效显示：vactive / yres = 600 行    │
├──────────────────────────────────────┤
│  lower porch(12)                     │
└──────────────────────────────────────┘
  总行数 = VDCTRL1 = 635

一行（水平）
┌────────┬──────┬──────────────────┬────────┐
│  back  │ hsync│      active      │ front  │
│  140   │  20  │    1024 px       │  160   │
└────────┴──────┴──────────────────┴────────┘
  left      ↑          xres           right
  总时钟 = VDCTRL2 = 1344
```

| dts | fb_var | 本项目 | 在时序里的角色 |
|-----|--------|--------|----------------|
| `vback-porch` | upper_margin | 20 | 场同步后、有效区前的空行 |
| `vsync-len` | vsync_len | 3 | 场同步脉冲宽度（行数） |
| `vfront-porch` | lower_margin | 12 | 有效区后的空行 |
| `vactive` | yres | 600 | 有效显示行数 |
| `hback-porch` | left_margin | 140 | 行同步后、有效像素前的时钟 |
| `hsync-len` | hsync_len | 20 | 行同步脉冲宽度 |
| `hfront-porch` | right_margin | 160 | 有效像素后的时钟 |
| `hactive` | xres | 1024 | 有效像素数 |

**各寄存器一句话**

| 寄存器 | 含义 | 本项目 |
|--------|------|--------|
| **VDCTRL1** | **一帧总共多少行**（含消隐+同步+有效区） | 635 行/帧 |
| **VDCTRL2** | **一行总共多少 PCLK**（含 porch+HSYNC+有效像素）；含 HSYNC 脉宽 | 1344 时钟/行 |
| **VDCTRL3 HOR_WAIT** | 行开始后，过 **back porch + HSYNC** 再开 DE、送像素 | 160 |
| **VDCTRL3 VERT_WAIT** | 场开始后，过 **upper porch + VSYNC** 再扫有效行 | 23 |
| **VDCTRL4** | **一行里有效像素个数**（DE 有效期间送多少像素） | 1024 |
| **VDCTRL0** | HSYNC/VSYNC/DE/PCLK **极性**（高/低有效、上升/下降沿） | 见 `*-active` |

**VDCTRL1 = 635**：垂直场周期行数。数满 635 行 = 一帧结束，再 VSYNC 下一帧。偏小 → 帧不完整；偏大 → 多余黑行、刷新率不对。

**VDCTRL2 = 1344**：水平行周期时钟数。每行从 HSYNC 到下一 HSYNC 共 1344 个 PCLK。与屏规格不一致 → 横向拉伸/压缩、右侧花屏。

**VDCTRL3 WAIT**：定 DE 有效窗口的起点——有效像素不能紧跟 HSYNC，必须等 porch+sync 过去。WAIT 错 → 整幅图左/上偏、彩色条纹。

**VDCTRL4 = 1024**：DE 有效期间从 fb 读 1024 像素送 DATA。与 HSYNC_PERIOD 配合：1344 时钟里只有 1024 是「真图像」，其余是消隐。

**与 PCLK、刷新率的关系**

```text
PCLK = clock-frequency = 51.2 MHz
htotal = 1344,  vtotal = 635
刷新率 ≈ 51200000 / (1344 × 635) ≈ 60 Hz
```

**简化时间线（一帧怎么扫）**

可以把 LCDIF 想象成**逐行扫描的打印机**：从上到下扫 600 行，每行从左到右送 1024 个像素；扫完一整页（一帧）后 VSYNC 一下，再扫下一页。约每秒扫 60 页 ≈ 60Hz。

**① 垂直方向：一帧从上到下**

```text
时间 ↓

VSYNC 脉冲 ──► 「新的一帧开始」
     │
     ├─ 空等 23 行（upper porch 20 + vsync 3）     ← VERT_WAIT，屏还在「场消隐」
     │
     ├─ 第 1 行 ────────────────────────────────┐
     ├─ 第 2 行                                    │ 600 行有效显示
     ├─  ...                                       │ （每行结构见 ②）
     ├─ 第 600 行 ────────────────────────────────┘
     │
     ├─ 空等 12 行（lower porch）                  ← 帧尾消隐
     │
     └─ 共 635 行 → 一帧结束，VSYNC 下一帧         ← VDCTRL1
```

**② 水平方向：单行从左到右（重复 600 次）**

```text
PCLK  →  →  →  →  →  →  →  →  →  →  →  →  →  →  →  →  →  →  →  →  →  →

HSYNC ────┐                        ┌────────────────────────────────────────────┐
          └────────────────────────┘                                            └── 下一行

          │←── 140 back ──→│←20→   │←────────── 1024 有效像素 ───────→│← 160 front→│
          │                │       │                                 │             │
          └──── HOR_WAIT = 160 ────┘                                 │             │
                                    │                                │             │
                              DE ───┴────────────────────────────────┘             │
                                                                                   │
                              DATA    (黑/无效)      R G B 像素…      (黑/无效)      │
                                      ↑                                            │
                              从这里开始送 fb 里的真图像                              │
                                      │                                            │
                              └────────────── 共 1344 个 PCLK（VDCTRL2）────────────┘
```

**③ 三个关键动作（记这三句就够）**

| 时刻 | 信号 | 在做什么 |
|------|------|----------|
| 帧开始 | **VSYNC** | 告诉屏：「新的一帧，准备从第 1 行扫起」 |
| 每行开始 | **HSYNC** | 告诉屏：「新的一行，光标回到行首」 |
| 有效区 | **DE 高 + DATA** | 这 1024 个 PCLK 上的 RGB 才是屏幕上能看到的像素 |

**④ 和上面 dts 数字的对应**

```text
一帧 = VSYNC 后等 23 行 + 扫 600 行 + 再等 12 行 = 635 行（VDCTRL1）
一行 = HSYNC 后等 160 时钟 + DE 送 1024 像素 + 再等 160 时钟 = 1344 时钟（VDCTRL2）
刷新 = 51.2MHz ÷ (1344 × 635) ≈ 60 次/秒
```

**和 dts / 驱动的闭环**

```text
timing0 (dts)
  → fb_var (xres/yres/margin/sync_len)
  → mxsfb_set_par → VDCTRL0（极性）+ VDCTRL1/2/3/4（行场几何）
  → 引脚 PCLK/HSYNC/VSYNC/DE/DATA → 屏
```

| 配错时典型现象 |
|----------------|
| VDCTRL1/2 与屏规格不符 | 花屏、闪、刷新率不对 |
| VDCTRL3 WAIT 不对 | 图像整体偏移 |
| VDCTRL4 ≠ xres | 斜纹、裁切、重复 |
| VDCTRL0 极性错 | 有背光无图像、颜色异常 |

**④-d 像素时钟 → clk_pix**

```c
clk_set_rate(host->clk_pix, PICOS2KHZ(var.pixclock) * 1000);
// ≈ 51200000 Hz ← clock-frequency
```

**④-e 帧缓冲地址 → NEXT_BUF**

```c
writel(fix.smem_start + line_length * yoffset, ... NEXT_BUF);
```

（内存分配见 Step 7。）

### Step 7 — 帧缓冲内存与 mmap

**分配（mxsfb_map_videomem）**

```c
fb_info->fix.smem_len = SZ_32M;   /* 上限；单帧约 1024×2×600 ≈ 1.2MiB */
fb_info->screen_base = dma_alloc_writecombine(
    dev, fix.smem_len, &fix.smem_start, GFP_DMA);
fix.line_length = xres * (bpp/8);   /* 2048 */
```

| 字段 | 用途 |
|------|------|
| `fix.smem_start` | 物理地址，写入 **LCDC_NEXT_BUF**，LCDIF DMA 读 |
| `screen_base` | 内核虚拟地址，CPU 写像素 |
| writecombine | 顺序写优化，适合 framebuffer |

**用户态访问（mxsfb_mmap）**

```text
mmap(/dev/fb0) / dd of=/dev/fb0
  → remap_pfn_range(fix.smem_start)
  → 用户进程写 WC DDR
  → LCDIF 按 VDCTRL 时序 DMA 读出 → RGB 并行接口 → 屏
```

**刷图数据路径**

```text
应用写像素 → screen_base/smem (DDR)
           → LCDIF DMA @ NEXT_BUF
           → 24bit RGB + HSYNC/VSYNC/DE/PCLK
           → ATK-7RGBLCD
```

### Step 8 — 独立匹配链（不经 mxsfb 主逻辑）

> **pinctrl 机制总线**见 **§3-B B.6.1**；本节按「外设维度」列 dts 与验证。

#### 8.1 pinctrl — 引脚复用

> **`<>` 语义** 见 **Step 1.1.1**；**`fsl,pins` 单行 `MX6UL_PAD_... 0x79`** 见 **Step 1.1.2**；机制总线见 **§3-B B.6.1**。

**匹配方式**：**phandle + group 节点名**，不是 group 上的 `compatible`。

```dts
/* 定义（在 &iomuxc / &iomuxc_snvs 下） */
&iomuxc {
    imx6ul-evk {
        pinctrl_lcdif_dat: lcdifdatgrp {
            fsl,pins = < MX6UL_PAD_LCD_DATA00__LCDIF_DATA00 0x79 ... >;
        };
        pinctrl_lcdif_ctrl: lcdifctrlgrp { ... };
    };
};
&iomuxc_snvs {
    imx6ul-evk {
        pinctrl_lcdif_reset: lcdifresetgrp {
            fsl,pins = < MX6ULL_PAD_SNVS_TAMPER9__GPIO5_IO09 0x79 >;
        };
    };
};

/* 引用（在 &lcdif 上） */
&lcdif {
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_lcdif_dat &pinctrl_lcdif_ctrl &pinctrl_lcdif_reset>;
};
```

```text
启动顺序（简化）：
  arch_initcall 注册 imx6ul-pinctrl 驱动
  → populate iomuxc / iomuxc_snvs → imx_pinctrl_probe（登记全部 group）
  → populate lcdif → mxsfb_probe
       → devm_pinctrl_get_select_default
       → 对 pinctrl-0 每个 phandle：找所属 iomuxc → imx_pmx_set 写 MUX+PAD
```

| 检查 | 命令 / 现象 | 通过标准 |
|------|-------------|----------|
| mxsfb 已 probe | `dmesg \| grep mxsfb` | 有 **`initialized`**（pinctrl 失败则 probe  abort，不会有此行） |
| lcdif 节点含 pinctrl | `ls /proc/device-tree/soc/aips-bus@02100000/lcdif@021c8000/` | 有 `pinctrl-0`、`pinctrl-names` |
| phandle 二进制 | `xxd .../lcdif@021c8000/pinctrl-0` | 三个 big-endian u32（见 Step 1.1.1） |
| 可选 debug | `mount -t debugfs none /sys/kernel/debug` 后看 `/sys/kernel/debug/pinctrl/` | 能看到 `imx6ul-pinctrl` 与 state（需内核打开 DEBUG_FS） |

**典型故障**：`virtual_size=1024,600` 正常但屏无 RGB 波形 / 全黑（背光已开）→ 查 pinctrl group 是否遗漏、reset 是否误放在主 `iomuxc` 而非 `iomuxc_snvs`。

#### 8.2 背光 — pwm-backlight

| 功能 | dts 示例 | 驱动 | 验证 |
|------|----------|------|------|
| 背光 | `backlight { compatible = "pwm-backlight"; pwms = <&pwm1 ...>; }` | pwm-backlight | `echo 7 > /sys/class/backlight/backlight/brightness`（0~7） |
| PWM 引脚 | `&pwm1 { pinctrl-0 = <&pinctrl_pwm1>; }` | imx PWM + pinctrl | 与 lcdif **独立**；背光灭 ≠ timing 错 |

#### 8.3 复位 / enable-gpio

| 功能 | dts | 说明 |
|------|-----|------|
| 屏复位脚 MUX | `pinctrl_lcdif_reset` | pinctrl 只负责切 GPIO 功能；**拉高/拉低时序**若由驱动 `enable-gpio` 控制，需看基线是否声明 |
| LCD 电源 | 部分板 `enable-gpio` / regulator | 本板 ATK 7 寸多靠背光 + 模组上电时序 |

可组合故障：**有 fb 尺寸但黑屏**（背光/pinctrl）；**有背光无图像**（timing/pinctrl/reset 时序）。

## 五、完整启动时序（两链 + 三种形态）

```text
[PC] 形态 A: dts → dtc → 形态 B 文件 → tftpboot/

[U-Boot]
  tftp → 形态 B @ 83000000
  bootz → fixup（改 B：bootargs/memory/MAC）→ r2 = B'

[内核 early — NFS 链，读形态 B]
  setup_machine_fdt → scan /chosen、/memory
  unflatten → 形态 C（of_root）

[内核 init — 显示链，读形态 C]
  §3-B：mxsfb_probe A～H → /dev/fb0 + pwm-backlight

[用户态]
  virtual_size=1024,600 ; brightness=7 ; dd → fb0
```

### 6.3 易踩坑说明

| 现象 | 说明 |
|------|------|
| `ls tftpboot/...dtb` → No such file（在板子上） | `tftpboot` 在 **PC**；板子只通过 TFTP 下载进内存 |
| `cat .../status` → No such file | 文档 `...` 是省略，须写全路径 |
| `find /proc/device-tree -name hactive` 无输出 | **不一定**表示无 timing；属性路径可能不同。以 **`virtual_size=1024,600`** 为准 |
| `failed to find mxc display driver` | mxsfb 在找可选 mxc encoder（`disp-dev`）；纯 RGB/LCDIF **可忽略**，只要后面有 `initialized` |
| `/proc/.../lcdif/` 下出现 `display#1` | dts 合并重复 display 子节点痕迹；`virtual_size` 正确且能显示则可忽略（见 `08`） |


| mxsfb OK 但黑屏 | Step 6~8 | 背光、pinctrl、极性 |

| `Duplicate name display#1` | dts 合并 | 通常可忽略 |
