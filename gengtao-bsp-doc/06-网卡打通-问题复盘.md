# 06 网卡打通-问题复盘

> 文档编号：06  
> 日期：2026-09-01  
> 板卡：正点原子 ATK-MX6ULL ALPHA|MINI（eMMC，双 SR8201F）  
> 关联：`03`（U-Boot/dtb）、`04`（原理图）、`05`（分析与落地顺序）、`10`（设备树匹配机制）  
> 结果：✅ NFS 根文件系统可登录；`eth0` UP；`ping` 主机通

---

## 一、目标与启动链

```
U-Boot TFTP(zImage + dtb) → 内核 → IP-Config(eth0) → NFS rootfs → login
板：192.168.3.51    主机：192.168.3.52
```

目标：在 NXP 纯净基线 + overlay 框架下，打通底板 **SR8201F** 网口，使内核 NFS 启动可用。

---

## 二、现象时间线（结合日志）

| 阶段 | 关键日志 / 现象 | 结论 |
|------|-----------------|------|
| A. 最初 | TFTP 拉官方 `imx6ull-14x14-evk-emmc.dtb`；内核 `IP-Config: Device 'eth0' not found` | 内核能起，网口/NFS 不通 |
| B. 改 `fdt_file` | `saveenv` 后仍拉官方 evk-emmc.dtb | `bootcmd` 硬编码，变量未用 |

## 三、问题分层与根因定位

```
┌──────────────────────────────────────────────────────────────┐
│ L1 U-Boot bootcmd 硬编码 dtb / 忽略 fdt_file                 │ ✅
├──────────────────────────────────────────────────────────────┤
│ L2 fdt_file 被板级覆盖；${fdt_file} 不可靠                   │ ✅
├──────────────────────────────────────────────────────────────┤
│ L3 TFTP File not found 仍用内存旧 dtb 启动                   │ ✅（规避）
├──────────────────────────────────────────────────────────────┤
│ L4 定制 dtb 一度与官方同 md5（仅改名无实质差异）               │ ✅
├──────────────────────────────────────────────────────────────┤
│ L5 dts 缺 PHY 复位；spi4 占用 GPIO5_IO07/08                  │ ✅
├──────────────────────────────────────────────────────────────┤
│ L6 fec 缺 SR8201F 复位后等待 + TX_CLK pad 强写（IMX6 补丁）  │ ✅ 最终关键
└──────────────────────────────────────────────────────────────┘
```

### 问题 1：U-Boot 未加载预期 dtb（L1–L3）

**现象：** `setenv fdt_file` 无效；后改 `${fdt_file}` 却拉出厂 7 寸 dtb 名并 File not found。

**根因：**

1. 出厂 `bootcmd` 写死 `imx6ull-14x14-evk-emmc.dtb`
2. 板级 init 会改写 `fdt_file`，`${fdt_file}` 不可靠
3. TFTP 失败后 `bootz` 仍用 `0x83000000` 残留 dtb —— **不可靠**

**解决：**

```bash
setenv bootcmd 'tftp 80800000 zImage; tftp 83000000 imx6ull-14x14-evk-emmc-gengtao0901-1024-600.dtb; bootz 80800000 - 83000000'
saveenv
```

必须以日志出现 `Loading: ... done` 为准。

---

### 问题 2：日志 `Device eth0 not found` 易误判（L5 阶段）

**现象（加复位后仍失败时）：**

```
fec 20b4000.ethernet eth0: registered PHC device 0
fec 2188000.ethernet eth1: registered PHC device 1
...
IP-Config: Failed to open eth0
IP-Config: Device `eth0' not found
```

**根因（读 `net/ipv4/ipconfig.c`）：**

| 日志 | 真实含义 |
|------|----------|
| `registered PHC` | netdev **已存在** |
| `Failed to open eth0` | `IFF_UP` 失败（`fec_enet_open` → `of_phy_connect` 失败） |
| `Device eth0 not found` | **二次误导报错**：指定了 `ip=...::eth0:` 但没有任何设备成功 UP |

关键缺失：**没有** `Freescale FEC PHY driver [Generic PHY]`。

---

### 问题 3：eth0 / eth1 与 U-Boot FEC1 的对应关系

| Linux | SoC 地址 | dts | U-Boot |
|-------|----------|-----|--------|
| eth0 | `020b4000` | fec2 / ENET2 | 通常非默认 |
| eth1 | `02188000` | fec1 / ENET1 | 日志 **FEC1**（TFTP 口） |

本板最终 **eth0（ENET2）** 链路 UP 并完成 NFS；验证时 `eth1` 未 UP 亦可（网线在 eth0 这一路）。

---

### 问题 4：仅 dts 复位不够（L5 做完仍失败）

**已做：**

- `phy-reset-gpios` / `phy-reset-duration`
- `pinctrl_fec*_reset`（SNVS_TAMPER7/8 = GPIO5_IO07/08）
- `spi4`（EVK 74HC595）改为 `disabled`（释放复位脚）
- mdio：`ieee802.3-c22`，地址 ENET1=`2`、ENET2=`1`

**仍失败：** 无 Generic PHY，`Failed to open eth0`。

**根因：** ALPHA 板 SR8201F 还需要 **fec 驱动板级适配**（出厂 IMX6 分支已有，基线没有）。

对照：

```bash
git diff master-gengtao-0901 origin/IMX6 -- drivers/net/ethernet/freescale/fec_main.c
```

---

### 问题 5：最终根因 —— fec + TX_CLK（L6）

硬件：底板双 **SR8201F**，RMII，25MHz 晶振，复位脚见原理图（`04`）。  
MCU 资料（`SR8201F/`）只说明标准 Clause22 / 复位语义，**不应移植**到 Linux；Linux 路径是 FEC + Generic PHY。

**最终必须同时具备：**

| 项 | 作用 |
|----|------|
| dts PHY 复位 + 关 spi4 | 内核侧能驱动 `PHYRSTB`，脚不被占用 |
| `fec_reset_phy` 后 `msleep(150)` | SR8201F 复位释放后需额外稳定时间 |
| probe 中 TX_CLK pad 写 `0x14` | RMII 参考时钟脚电气配置（对齐 IMX6） |
| dts `ENET*_TX_CLK` = `0x4001B009` | 与出厂 pad 配置一致（原 EVK 为 `0x4001b031`） |

缺 L6 时：MDIO 扫不到/挂不上 PHY → open 失败 → NFS 挂不上。  
补上 L6 后：立刻出现 Generic PHY + Link Up + NFS。

**不是根因（曾排查但非本板最终阻塞）：**

- 移植 MCU 的 `stm32_eth.c` / GD 驱动  
- 强绑 `CONFIG_SMSC_PHY`（出厂 dts 用 generic `ieee802.3-c22`；SR8201F ID 偏 `0x001C` 系）

## 四、最终解决方案（overlay 落点）

### 1. 板级 dts

`projects/gengtao-bsp-0901/arch/arm/boot/dts/imx6ull-14x14-evk-gengtao0901.dts`

- `&fec1` / `&fec2`：`phy-reset-gpios`、`phy-reset-duration`、`pinctrl_fec*_reset`
- `iomuxc_snvs`：复位 pinctrl（TAMPER7/8）
- `spi4`：`status = "disabled"`
- `ENET*_TX_CLK`：`0x4001B009`

### 2. fec 驱动补丁

`projects/gengtao-bsp-0901/drivers/net/ethernet/freescale/fec_main.c`  
（`.baseline/.../fec_main.c` + MANIFEST `M` 登记）

- 复位拉高后再 `msleep(150)`
- probe 中 `ioremap` ENET1/2 TX_CLK pad，`writel(0x14)`（并 `iounmap`）

### 3. U-Boot（板端环境，不在 git overlay）

- `bootcmd` 写死定制 dtb 文件名，确认 TFTP `done`

### 4. 构建部署


## 五、分析方法论（可复用）

1. **先看 U-Boot 实际 TFTP 文件名**，再看 `printenv`；失败必须以 `done` 为准。  
2. **U-Boot 通、内核不通** → 优先 dts/驱动板级配置，不先怀疑硬件。  
3. **读懂 IP-Config 两句报错**：先看有无 `Failed to open` 与有无 `Generic PHY`。  
4. **分清 eth0/eth1 与 FEC1/FEC2**，对照 SoC 地址。  
5. **原理图 + 出厂 IMX6 diff** 比抄 MCU 工程更快；MCU 资料只取语义。  
6. **改驱动必须重编 zImage**；只改 dts 时看 dtb 体积/md5 是否变化。

## 七、一句话总结

网卡打通经历了两段：先把 **U-Boot 真正加载到定制 dtb**，再在内核侧补齐 **ALPHA 板 SR8201F 的 dts 复位 + fec 驱动时序/时钟脚适配**。  

日志里的 `Device eth0 not found` 多数时候是 **UP/PHY 失败的二次误报**；最终根因是基线 fec **缺少 IMX6 中针对 SR8201F 的复位等待与 TX_CLK pad 配置**，补上后 Generic PHY 挂上、链路 100M Full、NFS 根文件系统即可登录。
