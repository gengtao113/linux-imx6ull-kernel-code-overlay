## 一、导读

### 1.1 一句话结论

KEY0 设备树里两处看似"并列"的节点，走的是**三条各自独立的匹配机制**（与 LED0 完全相同），外加一条 LED0 没有的**运行时数据链（中断 → input_event）**：

```text
gpio_keys {                             ← compatible = "gpio-keys" → gpio-keys 驱动（platform 匹配）
    compatible = "gpio-keys";
    pinctrl-0 = <&pinctrl_gpio_keys>;   ← 不是匹配，是"引用" pin group → pinctrl 子系统
    key0 { gpios = <&gpio1 18 GPIO_ACTIVE_LOW>; linux,code = <114>; }
                                        ← phandle → gpiolib 拿 GPIO（输入）+ 反相 + 键值
};
pinctrl_gpio_keys: gpio-keys {          ← iomuxc 控制器下的"数据"，无独立驱动
    fsl,pins = <MX6UL_PAD_UART1_CTS_B__GPIO1_IO18 0x80000000>;
};
```

- **`compatible` 决定"谁来管"**：`gpio-keys` 让内核把整个 `gpio_keys` 节点交给 **gpio-keys** 驱动（`drivers/input/keyboard/gpio_keys.c`）。
- **`pinctrl-0` 决定"脚怎么复用"**：引用 `pinctrl_gpio_keys`，让 **iomuxc pinctrl 驱动**把 GPIO1_IO18 mux 成 GPIO。
- **`gpios` 决定"用哪根脚、极性如何、当输入还是输出"**：phandle `&gpio1` + 脚号 `18` + `GPIO_ACTIVE_LOW`，交给 **gpiolib** 拿 GPIO 作为**输入**，并按 active-low 反相。
- **`linux,code` 决定"上报成哪个键值"**：`114`（`KEY_VOLUMEDOWN`），写进 input 子系统的 keybit 位图。

四件事齐了之后，**按/松一次 KEY0** 会走一条 LED0 没有的路：GPIO 电平跳变 → 边沿中断 → 去抖 work → `input_event()` → `/dev/input/event2` 刷出一帧 `EV_KEY code=114 value=1/0`。这是本文比 `26` 多出来的**链 D**（§7），而"按键最终怎么变成 input 子系统里的一员"则是 **§4** 专门讲的注册流程。

### 1.2 硬件 ↔ 节点 ↔ 驱动（速查）

| 硬件 | 设备树 | 驱动 / 子系统 |
|------|--------|----------------|
| KEY0（底板，VCC_3V3→10K 上拉→GPIO1_IO18，按下接 GND） | `key0` 子节点 | **gpio-keys** → input → `/dev/input/event2` |
| GPIO1_IO18（IOMUX pad，ALT5=GPIO） | `pinctrl_gpio_keys` + `fsl,pins` | **pinctrl-imx**（iomuxc 控制器） |
| GPIO 控制器 `0x0209c000` | `gpio1`（`compatible = "fsl,imx6ul-gpio"`） | **gpio-mxc**（gpiolib 后端） |
| 按键键值 / 上报 | `label` / `linux,code` | **input 子系统**（`input_set_capability`） |
| 按键按下触发 | （无 dts 字段，驱动内部 `gpio_to_irq`） | **GIC 中断控制器** → `request_irq` |

> 对比 LED0：LED0 的"产出物"是 `/sys/class/leds/sys-led/brightness`（**输出**、可读写）；KEY0 的"产出物"是 `/dev/input/event2`（**输入**、只读）。一张表看方向：

| | LED0（`24`/`26`） | KEY0（`27`/本文） |
|---|---|---|
| 驱动绑定名 | `gpio-leds` | `gpio-keys` |
| 内核驱动 | `drivers/leds/leds-gpio.c` | `drivers/input/keyboard/gpio_keys.c` |
| 子系统 | LED class | input 子系统 |
| GPIO 方向 | **输出**（点亮） | **输入**（读电平） |
| 极性 | `GPIO_ACTIVE_LOW`（共阳低亮） | `GPIO_ACTIVE_LOW`（下拉低按） |
| pinctrl 配置值 | `0x17059`（显式电气） | `0x80000000`（保持默认） |
| 用户态接口 | `/sys/class/leds/sys-led/` | `/dev/input/event2` |

### 1.3 匹配总览（从 dts 到 /dev/input/event2）

```text
形态 A  板级 dts（gpio_keys + pinctrl_gpio_keys）
           │ dtc
形态 B  dtb 二进制块
           │ unflatten
形态 C  device_node 树
           │
           ├─ ① gpio_keys 节点 compatible="gpio-keys" ──► gpio_keys_of_match[] → gpio_keys_probe
           │        └─ gpio_keys_get_devtree_pdata 遍历子节点 key0
           │                ├─ 读 linux,code  → 114（KEY_VOLUMEDOWN）
           │                ├─ 读 label      → "KEY0"（button->desc，非设备名）
           │                └─ 读 gpios      → of_get_gpio_flags 拿到 GPIO 全局号 + active_low
           │                          ↓
           ├─ ② gpios = <&gpio1 18 GPIO_ACTIVE_LOW> ──► gpiolib（gpio-mxc 控制器）
           │        └─ devm_gpio_request_one(GPIOF_IN)：当"输入"请求，active-low 反相
           │
           ├─ ③ pinctrl-0 = <&pinctrl_gpio_keys> ──► pinctrl_bind_pins()
           │        └─ iomuxc（fsl,imx6ul-iomuxc）写 MUX 寄存器（0x80000000 = 不写 PAD_CTL）
           │
           └─ ④ input_register_device ──► input 子系统注册（§4）
                    └─ ⑤ gpio_to_irq(18) → request_irq(双沿) ──► 按下/松开触发中断
                         └─ gpio_keys_gpio_isr → 去抖 work → input_event(EV_KEY,114,1/0)
                         └─ evdev 字符设备 → /dev/input/event2
```

## 二、三段匹配链 + 一条运行时链总览

KEY0 的 dts 虽然只有几行，却牵扯**三段各自独立**的匹配（与 LED0 一一对应），外加一段**运行时**才动起来的链路。先建立整体认识。

| 链 | dts 关键字段 | 匹配键 | 内核入口 | 结果 |
|----|--------------|--------|----------|------|
| **A. 按键驱动链** | `gpio_keys` 的 `compatible = "gpio-keys"` | **字符串对表** | `gpio_keys_of_match[]` → `gpio_keys_probe` | 建 input 设备，注册进 input 子系统 |
| **B. pinctrl 链** | `gpio_keys` 的 `pinctrl-0` + `pinctrl-names` | **phandle 引用**（非 compatible） | `pinctrl_bind_pins()` → iomuxc 写寄存器 | GPIO1_IO18 mux 成 GPIO |
| **C. GPIO 链** | `key0` 的 `gpios = <&gpio1 18 GPIO_ACTIVE_LOW>` | **phandle + 脚号 + 标志** | `of_get_gpio_flags()` → gpiolib | 拿到带反相的 GPIO（当输入） |
| **D. 中断/事件链** | （无 dts 字段，驱动内部） | **GPIO → IRQ 映射** | `gpio_to_irq()` → `request_irq` → `input_event` | 按键事件刷到 `/dev/input/event2` |

**核心分界（与 LED0 同一条）：只有链 A 走"compatible 对表匹配"。** 链 B、链 C 都是**按 phandle 引用**，不是按 compatible 匹配；链 D 更是**运行时**才发生，压根不在"匹配"范畴里——它是"中断 + 事件上报"的数据流。链 A 的最终落点是 §4 的 `input_register_device`，它把按键变成 input 子系统的一员。

## 三、链 A：`gpio_keys` 节点如何匹配 gpio-keys 驱动

> 源码：`drivers/input/keyboard/gpio_keys.c`（内核树 / overlay 同源）
> 辅助：`drivers/base/platform.c`、`drivers/of/device.c`

### 3.1 platform 匹配：compatible 对表

gpio-keys 是一个 **platform 驱动**，其匹配表只有一项（与 leds-gpio 完全同构）：

```c
/* drivers/input/keyboard/gpio_keys.c:673 */
static const struct of_device_id gpio_keys_of_match[] = {
	{ .compatible = "gpio-keys", },
	{ },
};
MODULE_DEVICE_TABLE(of, gpio_keys_of_match);

/* drivers/input/keyboard/gpio_keys.c:842 */
static struct platform_driver gpio_keys_device_driver = {
	.probe		= gpio_keys_probe,
	.remove		= gpio_keys_remove,
	.driver		= {
		.name	= "gpio-keys",
		.pm	= &gpio_keys_pm_ops,
		.of_match_table = of_match_ptr(gpio_keys_of_match),   /* ← 指向上面那张表 */
	}
};

/* drivers/input/keyboard/gpio_keys.c:852 / 862 */
static int __init gpio_keys_init(void)
{
	return platform_driver_register(&gpio_keys_device_driver);
}
late_initcall(gpio_keys_init);
```

| dts | 内核 |
|-----|------|
| `compatible = "gpio-keys";` | `gpio_keys_of_match[0].compatible` 命中 |
| 命中后 | 调用 `gpio_keys_probe()` |

**一句话：** dts 里的 `compatible = "gpio-keys"` 字符串，必须和驱动 `of_device_id[]` 里的 `.compatible = "gpio-keys"` 完全一致，驱动才会被调用。

> **和 LED0 的一处小差异（不本质）：** leds-gpio 用 `module_platform_driver`（展开成 `device_initcall` 级注册）；gpio-keys 用 `late_initcall(gpio_keys_init)` 手动 `platform_driver_register`。两者注册时机都**晚于** `arch_initcall` 的 `of_platform_populate`（设备先建、驱动后注册、`driver_register` 时再回头绑定），只是 gpio-keys 更晚一点。这个"晚"对 §4 的注册顺序也有影响（见 §4.7）。

### 3.2 通用机制快速回指（of_platform_populate / platform_match）

"设备树节点 → platform_device → 驱动"这条通用机器，`26` §3.1.1（`of_platform_populate` 内部）、§3.1.2（`platform_device` / `platform_match` 四步回退）已经**完整展开**，本文不重复。只需记住 KEY0 与 LED0 **落在同一位置**：

- `gpio_keys` 节点在根 `/` 下，有 `compatible`、`status` 默认 okay → `of_platform_populate` 把它建成一个 `platform_device`。
- 但 `gpio_keys` 的 compatible `"gpio-keys"` **不在** `of_default_bus_match_table`（`simple-bus` 等）里 → `of_platform_bus_create` 建完 `gpio_keys` 设备后**不递归** → **`key0` 子节点不被建成独立 platform_device**。
- 于是 `key0` 和 `26` 里的 `led0` 一样，**由驱动在 probe 时自己遍历**（gpio-keys 用 `gpio_keys_get_devtree_pdata` 的 `for_each_child_of_node`，见 §3.3）。
- `platform_match` 四步回退里，KEY0 同样命中**第 ② 步** `of_driver_match_device`（compatible 对表），其余①③④⑤都不走。

**一句话：** 匹配机制与 `26` 完全同一套，唯一换掉的是**驱动名**（`gpio-keys`）和**配套源文件**（`gpio_keys.c`）；`key0` 不是独立 platform_device 这件事，和 `led0` 一模一样。

### 3.3 `gpio_keys_probe` → `gpio_keys_get_devtree_pdata`：把子节点解析成平台数据

probe 先拿"平台数据"，DT 路径走 `gpio_keys_get_devtree_pdata`：

```c
/* drivers/input/keyboard/gpio_keys.c:689 */
static int gpio_keys_probe(struct platform_device *pdev)
{
	...
	pdata = dev_get_platdata(dev);
	if (!pdata) {
		pdata = gpio_keys_get_devtree_pdata(dev);   /* ← DT 路径，本板走这里 */
		if (IS_ERR(pdata))
			return PTR_ERR(pdata);
	}
	...
}
```

`gpio_keys_get_devtree_pdata`（`gpio_keys.c:591`）做的事，是把**子节点数组**翻译成 `gpio_keys_platform_data`：

```c
node = dev->of_node;
nbuttons = of_get_child_count(node);                 /* 数子节点：本板 = 1（key0） */
pdata->buttons = (struct gpio_keys_button *)(pdata + 1);
pdata->nbuttons = nbuttons;

for_each_child_of_node(node, pp) {                   /* 遍历每个子节点 */
	button = &pdata->buttons[i++];

	button->gpio = of_get_gpio_flags(pp, 0, &flags); /* 读 gpios 三元组 → 全局号 */
	button->active_low = flags & OF_GPIO_ACTIVE_LOW; /* 读极性标志 */

	button->irq = irq_of_parse_and_map(pp, 0);       /* 读 interrupts（本板没写，无） */

	if (of_property_read_u32(pp, "linux,code", &button->code)) {  /* ★ 读键值，缺了就报错 */
		dev_err(dev, "Button without keycode: 0x%x\n", button->gpio);
		return ERR_PTR(-EINVAL);
	}

	button->desc = of_get_property(pp, "label", NULL);          /* 读 label */

	if (of_property_read_u32(pp, "linux,input-type", &button->type))
		button->type = EV_KEY;                       /* 默认 EV_KEY */

	button->wakeup = !!of_get_property(pp, "gpio-key,wakeup", NULL);
	button->can_disable = !!of_get_property(pp, "linux,can-disable", NULL);

	if (of_property_read_u32(pp, "debounce-interval", &button->debounce_interval))
		button->debounce_interval = 5;               /* ★ 默认去抖 5ms */
}
```

**本板 `gpio_keys` 节点有一个子节点 `key0`**，所以 `for_each_child_of_node` 只循环一次，处理 `key0`。

### 3.4 `key0` 子节点三个属性的读法

对照本板 dts：

```dts
key0 {
    label = "KEY0";
    linux,code = <114>;    /* KEY_VOLUMEDOWN */
    gpios = <&gpio1 18 GPIO_ACTIVE_LOW>;
};
```

| 属性 | 驱动读取 | 本板值 | 效果 |
|------|----------|--------|------|
| `linux,code` | `of_property_read_u32(pp, "linux,code", ...)` | `114` | 上报键值 = `KEY_VOLUMEDOWN`，写进 input 的 keybit（**必填**，缺了 probe 报错） |
| `label` | `of_get_property(pp, "label", ...)` → `button->desc` | `"KEY0"` | 按钮**描述名**，用于 GPIO/中断请求时的名字（见 §3.5），**不是** input 设备名 |
| `gpios` | `of_get_gpio_flags(pp, 0, &flags)` | `&gpio1 18 ACTIVE_LOW` | 拿到 GPIO 全局号 `18` + `active_low=1`（见 §6） |
| `linux,input-type`（可选，本板没写） | `of_property_read_u32(pp, ...)` | 默认 `EV_KEY` | 事件类型，按键默认 EV_KEY |
| `debounce-interval`（可选，本板没写） | `of_property_read_u32(pp, ...)` | 默认 `5` | 软件去抖毫秒数 |

**关键对比 LED0：`label` 的语义不一样。** 在 LED0 里，`label="sys-led"` 是**设备在 sysfs 里的名字**（`/sys/class/leds/sys-led/`）；在 KEY0 里，`label="KEY0"` 只是**按钮描述**（`button->desc`），真正决定 `/proc/bus/input/devices` 里 `Name=` 的是 `input->name = pdata->name ?: pdev->name`，本板为 **`gpio_keys`**（`gpio_keys.c:726`）。所以 `/proc` 显示 `Name="gpio_keys"`，而 `KEY0` 只出现在中断名 / GPIO 请求名里。

### 3.5 `gpio_keys_setup_key`：请求 GPIO 为输入 + 映射中断 + 申请中断

probe 拿到 platform_data 后，对每个按钮调 `gpio_keys_setup_key`（`gpio_keys.c:437`），这是 KEY0 和 LED0 差异最大的地方——**LED 是"输出"，KEY 是"输入 + 中断"**：

```c
if (gpio_is_valid(button->gpio)) {
	/* ① 以"输入"方向请求 GPIO（对比 LED 的 gpiod_direction_output） */
	error = devm_gpio_request_one(&pdev->dev, button->gpio, GPIOF_IN, desc);
	...
	/* ② 软件去抖（gpio 硬件去抖不支持时回退到 workqueue 延时） */
	if (button->debounce_interval) {
		error = gpio_set_debounce(button->gpio, button->debounce_interval * 1000);
		if (error < 0)
			bdata->software_debounce = button->debounce_interval;
	}

	/* ③ GPIO 全局号 → IRQ 号（链 D 的起点） */
	if (button->irq) {
		bdata->irq = button->irq;
	} else {
		irq = gpio_to_irq(button->gpio);       /* ★ 18 → GIC 中断号 */
		...
		bdata->irq = irq;
	}

	/* ④ 双沿触发的中断处理函数 + 去抖 work */
	INIT_DELAYED_WORK(&bdata->work, gpio_keys_gpio_work_func);
	isr = gpio_keys_gpio_isr;
	irqflags = IRQF_TRIGGER_RISING | IRQF_TRIGGER_FALLING;   /* ★ 按下/松开都要触发 */
}

/* ⑤ 把这个键值登记进 input 设备的 keybit 位图 */
input_set_capability(input, button->type ?: EV_KEY, button->code);   /* EV_KEY + code 114 */

/* ⑥ 申请中断（不共享时加 IRQF_SHARED） */
error = devm_request_any_context_irq(&pdev->dev, bdata->irq, isr, irqflags, desc, bdata);
```

| 点 | 说明 |
|----|------|
| `GPIOF_IN` | 把 GPIO1_IO18 当**输入**，方向由 gpiolib 配好；对应 LED 的 `gpiod_direction_output` |
| `gpio_to_irq(18)` | 把 GPIO 全局号 18 映射到 GIC 的中断号，是"按键能中断上报"的关键 |
| `IRQF_TRIGGER_RISING \| FALLING` | **双沿**触发：按下（1→0）、松开（0→1）都会进 ISR |
| `input_set_capability` | 往 input 设备里 `__set_bit(EV_KEY)` 和 `__set_bit(114)`，`/proc` 里 `EV=3`、`KEY=...` 就是它产生的 |
| `desc = "KEY0"` | 来自 `button->desc`（=label），用于 `request_irq` 的中断名 |

### 3.6 `input_register_device`：把按键注册进 input 子系统（详见 §4）

probe 末尾调 `input_register_device(input)`（`gpio_keys.c:760`），这是"按键最终怎样注册到 input 子系统"的**总入口**。它内部做了什么、`/dev/input/event2` 是怎么长出来的，是本文重点，**单独放在 §4** 展开。

## 四、按键如何注册进 input 子系统（`input_register_device` 全流程）

> 本章是 §3（链 A）的收尾。gpio_keys_probe 最后那句 `input_register_device()`，把一颗按键变成内核 input 子系统里的一员。这里用源码讲清"注册"到底发生了什么、`/dev/input/event2` 是怎么凭空长出来的。

### 4.1 先分清三个"名字"（其实是两个对象）

注册完 KEY0 后，板上会同时出现三个名字，对应**两个不同层次的对象**：

| 名字 | 是什么 | 出处 | 落在哪 |
|------|--------|------|--------|
| `gpio_keys` | **逻辑 input 设备**的显示名 | `input->name = pdev->name`（gpio_keys.c:726） | `/proc/bus/input/devices` 的 `Name=`、dmesg |
| `input2` | 逻辑设备**内嵌 device** 的名字 | `dev_set_name("input%lu", input_no)`（input.c:1798） | `/sys/class/input/input2` |
| `event2` | **evdev 字符设备**的名字 | `dev_set_name("event%d", dev_no)`（evdev.c:1172） | `/dev/input/event2`（字符设备 13:66） |

```text
struct input_dev（逻辑设备，显示名 "gpio_keys"）
   └─ 内嵌 struct device（名字 "input2"）── device_add → /sys/class/input/input2
        └─ 挂一个 input_handle ──► struct evdev（字符设备 "event2"）
                                     └─ cdev_add + device_add → /dev/input/event2
```

**关键认知：注册是两层的。** 内核先注册一个"逻辑 input 设备"（`input_dev`，描述"我能上报什么键"），再由一个叫 **handler** 的"消费者接口"（evdev）为它建一个字符设备节点，用户态通过这个字符设备读事件。`gpio_keys` 是逻辑设备，`event2` 是读它的字符设备。

### 4.2 起点：`devm_input_allocate_device` → 分配 `input_dev`

gpio_keys_probe 里那句 `input = devm_input_allocate_device(dev)`（gpio_keys.c:713），最终调到：

```c
/* drivers/input/input.c:1782 */
struct input_dev *input_allocate_device(void)
{
	static atomic_t input_no = ATOMIC_INIT(-1);
	struct input_dev *dev;

	dev = kzalloc(sizeof(struct input_dev), GFP_KERNEL);
	if (dev) {
		dev->dev.type = &input_dev_type;
		dev->dev.class = &input_class;           /* ★ 属于 "input" 类 */
		device_initialize(&dev->dev);            /* ★ 初始化内嵌 device（还没注册） */
		...
		dev_set_name(&dev->dev, "input%lu",
			     (unsigned long)atomic_inc_return(&input_no));   /* ★ 名字 = input2 */
		__module_get(THIS_MODULE);
	}
	return dev;
}
```

要点：

- `struct input_dev` 里**内嵌 `struct device dev`**（值，非指针），和 `platform_device` 内嵌 device 是同一个套路。
- `dev->dev.class = &input_class`：input 子系统在 `subsys_initcall(input_init)`（input.c:2450）里 `class_register(&input_class)`，所以 `/sys/class/input/` 目录很早就建好了。
- `dev_set_name(..., "input%lu", input_no)`：全局原子计数器。本板 gpio_keys 是第 3 个 input 设备，所以叫 **`input2`**（input0=snvs-powerkey、input1=goodix-ts）。

> `devm_` 前缀表示 device-managed 版本：设备移除时内核自动 `input_free_device`，驱动不用自己清理，probe 失败也无需手动 free。

### 4.3 填身份 + 声明能力

分配完空壳，gpio_keys_probe 填进三样东西：

**(1) 身份（name / phys / id）** —— 让 `/proc` 和 dmesg 认得它（gpio_keys.c:726~735）：

```c
input->name = pdata->name ? : pdev->name;   /* "gpio_keys" */
input->phys = "gpio-keys/input0";
input->id.bustype = BUS_HOST;               /* 0x0019 */
input->id.vendor  = 0x0001;
input->id.product = 0x0001;
input->id.version = 0x0100;
```

**(2) 能力位图（evbit / keybit）** —— 声明"我是按键，能上报键值 114"：

```c
/* gpio_keys.c:511（在 gpio_keys_setup_key 里） */
input_set_capability(input, button->type ?: EV_KEY, button->code);
```

`input_set_capability` 宏干两件事：`__set_bit(EV_KEY, dev->evbit)`（声明支持"按键类事件"）和 `__set_bit(114, dev->keybit)`（声明支持键值 114）。`/proc` 里的 `EV=3`（EV_SYN+EV_KEY）和 `KEY=40000...`（bit18=114）就是这两张位图打印出来的（见 §10）。

### 4.4 `input_register_device`：五步注册（核心）

```c
/* drivers/input/input.c:2080 */
int input_register_device(struct input_dev *dev)
{
	...
	/* ① 兜底：每个 input 设备都支持 EV_SYN（帧分隔符，见 §7） */
	__set_bit(EV_SYN, dev->evbit);
	__clear_bit(KEY_RESERVED, dev->keybit);
	input_cleanse_bitmasks(dev);              /* 清掉 evbit 没提的位图 */

	/* ② 分配事件缓冲 */
	dev->vals = kcalloc(dev->max_vals, ...);

	/* ③ 注册内嵌 device → 出现在 /sys/class/input/input2 */
	error = device_add(&dev->dev);

	/* ④ 打一行 dmesg：input: gpio_keys as .../input/input2 */
	path = kobject_get_path(&dev->dev.kobj, GFP_KERNEL);
	pr_info("%s as %s\n", dev->name ? dev->name : "Unspecified device", path);

	/* ⑤ 挂进全局链表 + 对每个 handler 尝试 attach */
	list_add_tail(&dev->node, &input_dev_list);       /* ← /proc 的数据源 */
	list_for_each_entry(handler, &input_handler_list, node)
		input_attach_handler(dev, handler);           /* ← 触发 evdev 连接，长出 event2 */

	input_wakeup_procfs_readers();
	...
}
```

| 步 | 代码 | 产物 |
|----|------|------|
| ① 能力兜底 | `__set_bit(EV_SYN, ...)` | 保证能发 EV_SYN 分隔帧（§7 链 D 每帧结尾那个） |
| ② 事件缓冲 | `dev->vals` | 后面 `input_event` 写事件用的缓冲 |
| ③ 注册设备 | `device_add(&dev->dev)` | `/sys/class/input/input2` 出现 |
| ④ dmesg | `pr_info("%s as %s", ...)` | 板上 `input: gpio_keys as .../input/input2` 这行 |
| ⑤ 挂链表 + attach | `list_add_tail` + 遍历 handler | `/proc` 能枚举到它 + **`event2` 在这里被 evdev 建出来** |

### 4.5 第二层匹配：`input_attach_handler` → `input_match_device`

第 ⑤ 步是整章的高潮。它走的是 input 子系统**自己的**匹配，和前面 dts 的 `compatible` 匹配**不是一回事**——这是"输入设备 vs 输入处理器（handler）"的匹配：

```c
/* drivers/input/input.c:991 */
static int input_attach_handler(struct input_dev *dev, struct input_handler *handler)
{
	const struct input_device_id *id;
	id = input_match_device(handler, dev);   /* 匹配 handler 的 id_table */
	if (!id)
		return -ENODEV;
	return handler->connect(handler, dev, id);   /* ★ 命中 → 调 handler 的 connect */
}
```

```c
/* drivers/input/input.c:934 */
static const struct input_device_id *input_match_device(struct input_handler *handler,
							struct input_dev *dev)
{
	for (id = handler->id_table; id->flags || id->driver_info; id++) {
		if (id->flags & INPUT_DEVICE_ID_MATCH_BUS)
			if (id->bustype != dev->id.bustype) continue;      /* 比总线类型 */
		...
		if (!bitmap_subset(id->keybit, dev->keybit, KEY_MAX))   /* 比能力位图 */
			continue;
		...
		if (!handler->match || handler->match(handler, dev))
			return id;
	}
	return NULL;
}
```

**evdev 的 id_table 是"通配"**——匹配一切输入设备：

```c
/* drivers/input/evdev.c:1223 */
static const struct input_device_id evdev_ids[] = {
	{ .driver_info = 1 },	/* Matches all devices */
	{ },
};
```

所以 KEY0 的 `input_dev`（bustype=BUS_HOST，evbit 含 EV_KEY）**必然命中 evdev**，于是 `handler->connect = evdev_connect` 被调用。

> 对比记忆：`compatible` 匹配是"设备树节点 → 驱动"（platform 总线）；这里的 `input_match_device` 是"input 设备 → input 处理器"（input 子系统自己的链表）。后者比较的是 `id.bustype/vendor/product` + **能力位图**，不碰设备树。

### 4.6 `evdev_connect`：长出 `/dev/input/event2`

```c
/* drivers/input/evdev.c:1141 */
static int evdev_connect(struct input_handler *handler, struct input_dev *dev,
			 const struct input_device_id *id)
{
	struct evdev *evdev;
	int minor;

	/* ① 从 evdev 区段领一个 minor 号（64 ~ 95） */
	minor = input_get_new_minor(EVDEV_MINOR_BASE, EVDEV_MINORS, true);  /* 66 */

	evdev = kzalloc(sizeof(struct evdev), ...);

	dev_no = minor - EVDEV_MINOR_BASE;             /* 66 - 64 = 2 */
	dev_set_name(&evdev->dev, "event%d", dev_no);  /* ★ 名字 "event2" */

	evdev->handle.dev = input_get_device(dev);     /* handle 指向逻辑设备 */
	evdev->handle.handler = handler;

	evdev->dev.devt = MKDEV(INPUT_MAJOR, minor);   /* ★ MKDEV(13, 66) */
	evdev->dev.class = &input_class;               /* 同属 input 类 */
	device_initialize(&evdev->dev);

	/* ② 把 handle 挂进逻辑设备的 h_list（设备 ↔ handler 建立双向关系） */
	error = input_register_handle(&evdev->handle);

	/* ③ 创建字符设备，绑定 evdev_fops */
	cdev_init(&evdev->cdev, &evdev_fops);
	error = cdev_add(&evdev->cdev, evdev->dev.devt, 1);

	/* ④ 注册设备 → udev/mdev 据此在 /dev/input/ 下建 event2 节点 */
	error = device_add(&evdev->dev);
	...
}
```

| 步 | 作用 | 结果 |
|----|------|------|
| `input_get_new_minor(64, 32)` | 从 evdev 专属 minor 区段（64~95）领号 | 本板第 3 个 → minor **66** |
| `dev_set_name("event%d", 2)` | 字符设备名 | `event2` |
| `MKDEV(13, 66)` | 主设备号 13（`INPUT_MAJOR`，`uapi/linux/major.h:29`）+ 次 66 | `/dev/input/event2` 的 devt |
| `cdev_add` | 登记一个字符设备，绑 `evdev_fops`（read/write/ioctl） | 用户 `read(fd,...)` 走 `evdev_read` |
| `device_add` | 触发 `input_class` 的 `devnode` 回调 → `"input/event2"` | udev/mdev 建 `/dev/input/event2` 节点 |

> 主设备号 13 是 `subsys_initcall(input_init)` 里 `register_chrdev_region(MKDEV(INPUT_MAJOR, 0), 1024, "input")`（input.c:2428）提前占好的，所以 evdev 只需领一个 minor 就能用。

### 4.7 为什么注册顺序一定对：三个 initcall 的先后

注册能成功，靠的是 initcall 的先后保证"基础设施先于使用方就绪"：

```text
subsys_initcall(input_init)             input.c:2450   → class_register(input_class) + 占主设备号 13
module_init(evdev_init)                 evdev.c:1251   → input_register_handler(&evdev_handler)
                                                          （evdev handler 挂进 input_handler_list）
late_initcall(gpio_keys_init)           gpio_keys.c:862 → platform_driver_register → ... → gpio_keys_probe
                                                          → input_register_device
                                                          → 遍历 handler 列表，命中已就绪的 evdev
                                                          → evdev_connect → /dev/input/event2
```

`subsys_initcall < module_init(device_initcall) < late_initcall`，所以当 gpio_keys_probe 走到 `input_register_device` 时，evdev 早已在 `input_handler_list` 里等着了。

### 4.8 小结：一次注册，两个对象、三个名字

```text
gpio_keys_probe
  └─ devm_input_allocate_device   → 分配 input_dev，内嵌 device 名 "input2"
  └─ 填 name/phys/id + input_set_capability(EV_KEY, 114)
  └─ input_register_device(input)
        ├─ device_add(&input->dev)            → /sys/class/input/input2
        ├─ pr_info("gpio_keys as ...input2")  → dmesg 那行
        ├─ list_add_tail(&input_dev_list)     → /proc/bus/input/devices 可枚举
        └─ input_attach_handler(evdev)
             └─ input_match_device 命中 evdev_ids（通配）
             └─ evdev_connect
                   ├─ 领 minor 66 → dev_set_name("event2")
                   ├─ cdev_init + cdev_add（字符设备 13:66，绑 evdev_fops）
                   └─ device_add → udev/mdev 建 /dev/input/event2
```

**一句话：** 所谓"注册到 input 子系统"，就是 gpio_keys_probe 分配一个 `input_dev` 并 `input_register_device`——内核先把它注册成 `/sys/class/input/input2` 的逻辑设备、挂进全局 `input_dev_list`，再经 input 子系统自己的"设备↔handler"匹配命中通配的 evdev，由 `evdev_connect` 领 minor、`cdev_add`、`device_add` 生成 `/dev/input/event2`。之后链 D 里 `input_event` 写的事件，就是从 `input_dev` 经 `input_handle` 流进这个 evdev 字符设备、被 `read` 读走。

## 五、链 B：`pinctrl_gpio_keys` 为什么这样写（独立链）

> 源码：`drivers/pinctrl/freescale/pinctrl-imx.c`、`pinctrl-imx6ul.c`、`drivers/base/pinctrl.c`、`drivers/pinctrl/devicetree.c`
> 通用机制与 `26` §4 是**同一套 pinctrl 子系统**，这里只讲 KEY0 与 LED0 的不同点。

### 5.1 核心结论：pinctrl 组不走 compatible 匹配

```dts
pinctrl_gpio_keys: gpio-keys {
    fsl,pins = <
        MX6UL_PAD_UART1_CTS_B__GPIO1_IO18	0x80000000
    >;
};
```

它**没有 `compatible`**，只是 iomuxc 控制器节点下的一份"引脚配置数据"，不是设备、不被单独 probe。它被消费的唯一方式是 `gpio_keys` 节点通过 `pinctrl-0 = <&pinctrl_gpio_keys>` **按 phandle 引用它**。这一结论与 `26` §4.1 完全相同。

### 5.2 控制器链：iomuxc 才是被"匹配"的设备

真正被 `compatible` 匹配的仍是 `fsl,imx6ul-iomuxc`（`imx6ul_pinctrl_of_match`，`pinctrl-imx6ul.c:326`）。KEY0 与 LED0 **共用同一个 iomuxc 控制器**，只是多了一个 group `pinctrl_gpio_keys`。`26` §4.2 已展开，不重复。

### 5.3 消费链：`pinctrl-0` → `pinctrl_bind_pins()`（probe 前完成）

和 LED0 一样，真正"写寄存器、把脚 mux 成 GPIO"发生在 **gpio_keys_probe 之前**，由设备核心自动完成：

```text
gpio_keys 的 platform_device 创建后、gpio_keys_probe 调用前
        ↓
device core → pinctrl_bind_pins(&pdev->dev)          /* drivers/base/pinctrl.c */
        ↓
读 pinctrl-names（="default"）+ pinctrl-0（phandle → pinctrl_gpio_keys）
        ↓
pinctrl_dt_to_map → imx_dt_node_to_map                /* 解析 fsl,pins 成 pin map */
        ↓
pinctrl_select_state("default") → imx_pmx_set         /* 写 IOMUXC 的 MUX 寄存器 */
        ↓
GPIO1_IO18 被 mux 成 GPIO 功能（ALT5），PAD_CTL 因 0x80000000 跳过不写
```

### 5.4 `fsl,pins` 单行：`MX6UL_PAD_UART1_CTS_B__GPIO1_IO18  0x80000000`

```text
MX6UL_PAD_UART1_CTS_B__GPIO1_IO18	0x80000000
│                    │                 │
│                    │                 └─ 0x80000000 = 不写 PAD_CTL（保持默认电气）
│                    └─ 复用功能：把 UART1_CTS_B pad 选为 GPIO1_IO18（ALT5 = GPIO）
└─ 物理 pad 名（UART1_CTS_B，B = 低有效逻辑）
```

宏展开（`imx6ul-pinfunc.h:188` 里 `MX6UL_PAD_UART1_CTS_B__GPIO1_IO18` 的 5 个值）：

```text
0x008C   mux_reg    → 物理 0x020E008C（IOMUXC_SW_MUX_CTL_PAD_UART1_CTS_B）
0x0318   conf_reg   → 物理 0x020E0318（IOMUXC_SW_PAD_CTL_PAD_UART1_CTS_B）
0x0000   input_reg  → 无输入寄存器（本脚不需）
0x5      mux_mode   → ALT5 = GPIO1_IO18
0x0      input_val
```

**`0x80000000` 是关键差异点**（与 LED0 的 `0x17059` 对比）：

```c
/* drivers/pinctrl/freescale/pinctrl-imx.c:32 */
#define IMX_NO_PAD_CTL  0x80000000
```

它是 pinctrl-imx 的**软件标志位**，含义是"**只写 MUX 寄存器（复用成 GPIO），不写 PAD_CTL 寄存器**"，让 pad 保持复位默认电气。pinctrl-imx 里 `if (!(config & IMX_NO_PAD_CTL))` 才去写 conf 寄存器。

| 对比 | LED0（`0x17059`） | KEY0（`0x80000000`） |
|------|------------------|---------------------|
| 方向 | **输出**（灌电流点亮 LED） | **输入**（读按键电平） |
| 为什么 | 要配推挽/驱动强度/压摆率才能正常灌电流 | 输入不需要驱动强度；上拉靠底板 R15 10K 外部电阻 |
| 寄存器 | 写 SW_PAD_CTL（HYS/PUS/PUE/PKE/SPEED/DSE/SRE） | **不写**，保持复位默认 |

> 这句话 `27` 附录 D 也讲过，这里再落一次脚：**输出（LED）要配电气；输入（KEY）外接上拉后 PAD_CTL 保持默认即可，`0x80000000` = "别动电气、只切复用"。** 这也是为什么 KEY0 的 `fsl,pins` 值看起来"简单"，而 LED0 的 `0x17059` 看起来"复杂"。

## 六、链 C：`gpios = <&gpio1 18 GPIO_ACTIVE_LOW>` 如何解析

### 6.1 三元组结构

```dts
gpios = <&gpio1 18 GPIO_ACTIVE_LOW>;
         │    │  │
         │    │  └─ 极性标志：0x1 = 低电平有效（active-low）
         │    └─ 该控制器内的引脚号：18 → GPIO1_IO18
         └─ phandle：指向哪个 GPIO 控制器（gpio1）
```

编译成 dtb 后（板上 `dtc` 反编译）：

```text
gpios = <0x08 0x12 0x01>;
         │    │    └─ 0x01 = GPIO_ACTIVE_LOW
         │    └─ 0x12 = 0x12 = 18（脚号）
         └─ 0x08 = gpio1 的 phandle
```

（`0x12` 是 18 的十六进制；phandle `0x08` 与 `26` 里 LED0 的 `&gpio1` 是同一个控制器。）

### 6.2 `&gpio1` phandle → gpio-mxc 控制器

与 LED0 完全同一控制器（`26` §5.2）：

```dts
gpio1: gpio@0209c000 {
    compatible = "fsl,imx6ul-gpio", "fsl,imx35-gpio";
    ...
};
```

| 元素 | 含义 |
|------|------|
| `gpio1` | SoC 第 1 组 GPIO（Bank1），物理基址 `0x0209c000` |
| `18` | Bank1 里的第 18 根（offset 18）→ **GPIO1_IO18** |
| GPIO 全局号 | (bank-1)×32 + offset = **18** |

### 6.3 驱动读取路径（与 LED0 不同：用 `of_get_gpio_flags`）

LED0 用 `devm_get_gpiod_from_child`（拿描述符），gpio-keys 走的是**另一条 gpiolib 旧接口**——直接拿**全局号 + 标志**：

```text
gpio_keys_get_devtree_pdata（key0 子节点）
  → of_get_gpio_flags(pp, 0, &flags)         /* gpio_keys.c:626 */
      → 解析 phandle &gpio1 + 脚号 18 + 标志 GPIO_ACTIVE_LOW
      → 返回全局号 18，flags 里带 OF_GPIO_ACTIVE_LOW
  → button->gpio = 18
  → button->active_low = flags & OF_GPIO_ACTIVE_LOW   /* = 1 */
```

之后在 `gpio_keys_setup_key`（§3.5）里，用 `devm_gpio_request_one(..., GPIOF_IN, ...)` 真正**占用**这根 GPIO 并设成输入。

### 6.4 `GPIO_ACTIVE_LOW`：gpiolib 反相 + 当输入

`GPIO_ACTIVE_LOW = 0x1`。对按键来说它的作用：**告诉驱动"低电平 = 按下"**，让 ISR 采样后反相，上层事件统一"value=1 = 按下"。

```text
物理事实：VCC_3V3 → 10K 上拉 → GPIO1_IO18，KEY0 另一脚接 GND → 按下 = 0，松开 = 1
逻辑需求：input 事件里"按下"应该上报 value=1
解决办法：active_low=1，采样时 state = 物理电平 ^ active_low

松开：物理 1 ^ 1 = 0 → input_event value=0（松开）
按下：物理 0 ^ 1 = 1 → input_event value=1（按下）✅
```

这段反相就在 `gpio_keys_gpio_report_event`（`gpio_keys.c:334`）：

```c
int state = (gpio_get_value_cansleep(button->gpio) ? 1 : 0) ^ button->active_low;
...
input_event(input, type, button->code, !!state);
```

**一句话：** `gpios` 三元组 = "哪个控制器（phandle）+ 哪根脚（18）+ 什么极性（active-low）"，gpiolib 拿到 GPIO 作为输入，驱动按 `active_low` 反相，让上层统一用"value=1=按下"的逻辑——**这一步与 LED0 的"1=亮"是同一个反相套路，只是方向从输出换成输入。**

## 七、链 D：中断 → `input_event` → `/dev/input/eventX`（KEY0 独有）

这是本文比 `26` 多出来的部分，也是 KEY0 与 LED0 的**本质区别**：LED0 是"往 GPIO 写电平"，KEY0 是"从 GPIO 收中断、往外报事件"。

### 7.1 中断如何建立：`gpio_to_irq` + `request_irq`

链 C 拿到的是 **GPIO 全局号 18**，但按键要"按下立刻知道"，必须把它转成 **GIC 中断号**再挂中断处理函数（已在 §3.5 列出）：

```c
irq = gpio_to_irq(button->gpio);               /* 18 → GIC 的某个 irq 号 */
isr = gpio_keys_gpio_isr;
irqflags = IRQF_TRIGGER_RISING | IRQF_TRIGGER_FALLING;
devm_request_any_context_irq(&pdev->dev, bdata->irq, isr, irqflags, desc, bdata);
```

| 点 | 说明 |
|----|------|
| `gpio_to_irq` | gpio-mxc 控制器把"某根 GPIO 电平变化"映射到 GIC 中断；这是中断式按键的核心一步 |
| 双沿触发 | 按下（1→0）和松开（0→1）都要进 ISR，才能报出 value=1 和 value=0 两个事件 |
| `desc="KEY0"` | 中断名，`cat /proc/interrupts` 里能看到 `KEY0` 那一行 |

### 7.2 一次按下的完整事件流（含去抖）

```text
按下 KEY0：GPIO1_IO18 物理电平 1 → 0（下降沿）
        ↓ 双沿触发，进 ISR
gpio_keys_gpio_isr(irq, bdata)                         /* gpio_keys.c:361 */
        ↓ 去抖：不立即读电平，排一个 5ms 延时 work（mod_delayed_work）
gpio_keys_gpio_work_func(work)                          /* gpio_keys.c:350，5ms 后 */
        ↓ 现在才读电平 + 反相
gpio_keys_gpio_report_event(bdata)                      /* gpio_keys.c:334 */
        ↓ state = 物理电平(0) ^ active_low(1) = 1
input_event(input, EV_KEY, 114, 1)                      /* 按下：value=1 */
input_sync(input)                                       /* EV_SYN 分隔符 */

松开 KEY0：物理电平 0 → 1（上升沿）
        ↓ 再进 ISR → 5ms work → 采样 state = 1 ^ 1 = 0
input_event(input, EV_KEY, 114, 0)                      /* 松开：value=0 */
input_sync(input)
```

**去抖为什么在 work 里做：** 机械按键在按下瞬间会抖动，如果 ISR 里立刻读电平，可能读到中间态。gpio-keys 用 `INIT_DELAYED_WORK` + 默认 `debounce_interval=5`ms（§3.4），ISR 只负责**排任务**，5ms 后再读稳定电平。i.MX6ULL 的 gpio-mxc 若不支持硬件去抖（`gpio_set_debounce` 返回负），就退到这套软件 workqueue 去抖。

### 7.3 事件如何到用户态：evdev 层

`input_event()` 把事件写进 `input_dev` 的事件缓冲，`input_sync()` 打一帧边界；`evdev`（`CONFIG_INPUT_EVDEV=y`）负责把它变成 `read()` 能读到的 `/dev/input/eventX`。每帧事件 = 一个 `struct input_event`（32 位平台 16 字节）：

```text
time(8) + type(2) + code(2) + value(4)，小端
```

KEY0 按/松各产生 **2 个事件 = `EV_KEY` + `EV_SYN`**：

```text
type=1(EV_KEY) code=114 value=1   → 按下
type=0(EV_SYN) code=0             → 帧结束（分隔符）
type=1(EV_KEY) code=114 value=0   → 松开
type=0(EV_SYN) code=0
```

板上 `hexdump /dev/input/event2` 看到的就是这 4 行 × 16 字节（见 §10 验证对照）。

**一句话：** 链 D 是"运行时"才动的——`gpio_to_irq` 把 GPIO 变成中断，双沿 ISR 排 5ms 去抖 work，work 采样反相后 `input_event` 上报 `EV_KEY 114 value=1/0`，evdev 把它送进 `/dev/input/event2`。

## 八、各链的时序（一次启动 + 一次按下的完整顺序）

```text
① subsys_initcall / module_init 阶段（先于 probe，见 §4.7）
   input_init：class_register(input_class) + 占主设备号 13
   evdev_init：input_register_handler(&evdev_handler)

② arch_initcall 阶段
   iomuxc（fsl,imx6ul-iomuxc）probe → 登记所有 group（含 pinctrl_gpio_keys）
   gpio1（fsl,imx6ul-gpio）probe → gpio-mxc 控制器就绪，注册到 gpiolib

③ of_platform_populate 到 gpio_keys 节点
   → 建 platform_device（status 默认 okay）
   → device core：pinctrl_bind_pins()          ← 链 B 生效：写 IOMUXC MUX，脚 mux 成 GPIO
   → platform_match：compatible "gpio-keys"    ← 链 A 匹配
   → gpio_keys_probe
        → gpio_keys_get_devtree_pdata：遍历 key0
            读 linux,code=114
            读 label="KEY0" → button->desc
            读 gpios=<&gpio1 18 ACTIVE_LOW>    ← 链 C 生效：全局号 18 + active_low
        → gpio_keys_setup_key：
            devm_gpio_request_one(GPIOF_IN)     ← 当输入请求
            gpio_to_irq(18)                      ← 链 D 起点
            request_irq(双沿, gpio_keys_gpio_isr)
            input_set_capability(EV_KEY, 114)
        → input_register_device                  ← 链 A 收尾：注册进 input（§4）
             → evdev_connect → /dev/input/event2

④ 用户按下 KEY0（运行时）
   物理电平 1→0 → 下降沿中断 → gpio_keys_gpio_isr
   → 5ms 去抖 work → gpio_keys_gpio_report_event
   → input_event(EV_KEY,114,1) + input_sync     → 用户态 read 到"按下"
   松开 0→1 → 上升沿中断 → ... → input_event(EV_KEY,114,0) → "松开"
```

注意顺序：**pinctrl（链 B）在 gpio_keys_probe（链 A）之前**由设备核心完成；**input 子系统基础设施（§4.7）先于 gpio_keys_probe 就绪**；**链 D 是用户按下那一刻才触发**，与启动时序无关。

## 九、为什么这样写（设计动机与最佳实践）

### 9.1 为什么要 `compatible = "gpio-keys"`，而不是自己写驱动

- `gpio-keys` 是 Linux **内核自带的按键驱动绑定名**，写在 `gpio_keys.c` 的 `gpio_keys_of_match[]` 里。
- 只要你写 `gpio-keys`，内核就自动有驱动接管按键，**不用自己写任何 C 代码**——这正是"改设备树就能读按键"的原因。对比 AP3216C（I2C 光感）、ICM-20608（SPI 六轴）那类有协议的器件才需要自写驱动，按键没有寄存器时序，用现成的就够了。
- 换成别的字符串（比如 `my-keys`）→ 没驱动匹配 → 节点被无视，按键无响应。

### 9.2 为什么要 `linux,code`，它和 `label` 分工是什么

- `linux,code` 是**功能键值**（`114 = KEY_VOLUMEDOWN`），决定应用层读到 `code=114`；它**必填**，缺了驱动直接 `Button without keycode` 报错返回。
- `label` 是**人类可读的描述名**（`"KEY0"`），只用于中断名/GPIO 请求名，不影响键值、也不是 input 设备名。
- 两者解耦：`label` 可以叫 `"KEY0"`，但 `linux,code` 可以是任意合法键值（改成 `KEY_ENTER`=28 也行，改法见 `27` L1 注释）。

### 9.3 为什么要分"逻辑设备 + handler 字符设备"两层

- **`input_dev`（逻辑设备）** 描述"我是什么、能上报什么"（name/phys/id + evbit/keybit），它**不关心**事件怎么到用户态。
- **`handler`（evdev）** 才是"消费者接口"，负责把事件变成 `/dev/input/eventX` 字符设备供 `read`。
- 分两层的意义：同一颗按键可以同时被多个 handler 消费（evdev 给应用、还有 joydev/mousedev/kbd 等），互不干扰。KEY0 只命中 evdev 是因为本内核只编了 evdev（`CONFIG_INPUT_EVDEV=y`）。

### 9.4 为什么 pinctrl 单独一个 group，且用 `0x80000000`

- 内核把"脚复用"（pinctrl）和"设备功能"（gpio-keys）**彻底分开**，与 LED0 同一套道理（`26` §7.3）。
- `0x80000000`（`IMX_NO_PAD_CTL`）表达的是"**这是输入脚，别写电气寄存器**"：按键上拉由底板 R15 10K 外部电阻提供，SoC 内 PAD_CTL 保持复位默认即可。反过来 LED0 是输出，才需要 `0x17059` 去配驱动强度等。
- 若误写成 `0x17059` 之类的输出配置，按键通常也能读，但语义错了（把输入脚当输出配了电气），且违背"输入脚外接上拉、内部别动"的原则（`27` 附录 B 把它列为坑）。

### 9.5 为什么要 `GPIO_ACTIVE_LOW`（而不是应用层自己反相）

- 下拉按键"低电平按下"是**硬件事实**（VCC→10K 上拉，按键→GND）。
- 用 `GPIO_ACTIVE_LOW` 在 dts 里声明极性，驱动采样时 `物理电平 ^ active_low` 自动反相，上层永远用"value=1=按下"的直觉。
- 不写它 → 驱动默认 active-high → 按下（物理 0）会被当成"松开"上报，方向反（`27` 附录 B 列为坑）。

### 9.6 为什么按键能"按下即知"，而不是轮询

- 因为 gpio-keys 走了**中断**（链 D）：`gpio_to_irq` + 双沿 `request_irq`。按下/松开立刻触发 ISR，再经 5ms 软件去抖上报。
- 这是它比"老 sysfs GPIO 轮询"（`/sys/class/gpio`）强的地方：不占 CPU 空转，且自带去抖。内核 4.x 后 `/sys/class/gpio` 已废弃，只适合临时调试（`27` §二.5）。

### 9.7 一句话设计原则

**dts 描述"硬件真相"（哪根脚、什么极性、什么键值），内核各子系统据此匹配并驱动；`compatible` 选驱动、phandle 引资源、`fsl,pins` 配复用、`linux,code` 定键值——按键与 LED 只有"输入 vs 输出"和"中断 vs 轮询"之差，匹配骨架完全同一套。**

**`KEY=40000 0 0 0` 倒序解码（`drivers/input/input.c:1115`）：**

```c
/* input_seq_print_bitmap：从最高位字往回打印，前面全是 0 的字会被 skip_empty 跳过 */
for (i = BITS_TO_LONGS(max) - 1; i >= 0; i--) { ... }
```

`KEY_CNT` 超过 96，keybit 占 4 个 `unsigned long`（32 位平台一字 32 位）。`/proc` 打印的是 `word[3] word[2] word[1] word[0]`（**高位在前**），所以 `40000 0 0 0` 里：

```text
word[3] = 0x40000 = 1 << 18
word[2] = 0, word[1] = 0, word[0] = 0

word[3] 覆盖键值 96 ~ 127，bit18 → 键值 96 + 18 = 114 = KEY_VOLUMEDOWN ✅
```

**这正是 `linux,code = <114>` 落进 keybit 的证据**——别把 `40000` 误读成"键值 0x40000"或"键值 18"。

## 十一、一句话

KEY0 设备树的匹配本质是三条链的接力、外加一条运行时链：**`compatible = "gpio-keys"` 让 gpio-keys 驱动接管、遍历出 `key0` 并 `input_register_device` 注册成 input 设备（逻辑设备 `input2` + evdev 字符设备 `event2`）；`pinctrl-0` 让 iomuxc 在 probe 前把 GPIO1_IO18 mux 成 GPIO（`0x80000000` 只切复用不动电气）；`gpios = <&gpio1 18 GPIO_ACTIVE_LOW>` 让 gpiolib 把脚当输入、按下拉极性反相；`linux,code = <114>` 把键值写进 keybit——最后 `gpio_to_irq` 挂双沿中断，按下/松开经去抖后 `input_event` 上报 `EV_KEY 114 value=1/0`，`/dev/input/event2` 才读得到一次按键。**
