## 一、先定结论（避免走弯路）

1. **KEY0 走内核 input 子系统，不自己写驱动。** 内核已带 `drivers/input/keyboard/gpio_keys.c`，且 defconfig 已开 `CONFIG_KEYBOARD_GPIO=y`；按键本质是「GPIO 输入 + 中断上报」，没有寄存器时序，不值得自写 misc 驱动（对比 AP3216C / ICM-20608 那类有 I2C/SPI 协议的才需要自写）。
2. **KEY0 = GPIO1_IO18（UART1_CTS 复用），低电平按下（active-low）。** 底板 KEY0 一端接 GND、另一端经 10K 上拉接 GPIO1_IO18，按下 = 0。
3. **正确路径：**

   ```text
   应用（read /dev/input/eventX）
        ↑
   /dev/input/eventX（EV_KEY 事件）
        ↑
   input 子系统（input_event / input_register_device）
        ↑
   gpio-keys 驱动（compatible = "gpio-keys"）
        ↑
   设备树 gpio_keys 节点 + gpios = <&gpio1 18 GPIO_ACTIVE_LOW>
        ↑
   硬件：VCC_3V3 → 10K 上拉 → GPIO1_IO18，按键 → GND（按下 = 低电平）
   ```

4. **进度（相对 `gengtao-bsp-0901`，2026-09-05）：** L0～L5 均未开始，本文为首次落地。
5. **推荐顺序：** L0 辨脚 → L1 加 dts 节点 → L2 核对内核配置 → L3 编译 + 反编译核对 → L4 板载读原始事件 → L5 应用层读按键 / 按键点灯联动。

> **为什么是「低电平按下」？** 底板 KEY0 是**下拉按键**接法：`VCC_3V3 → 10K(R15) → GPIO1_IO18`，`KEY0 另一端 → GND`。松开时上拉把 GPIO 拉到 1，按下时被 GND 拉成 0 → **按下 = 0**。内核 input 框架用 `GPIO_ACTIVE_LOW` 帮你把「按键按下」反相成「value=1 上报」，应用层读到的是 `1=按下 / 0=松开`，别自己再取反。

## 二、分析思路（为什么这样判断）

### 1. 从原理图抽出信号链

资料（`gengtao-bsp-doc/` 下两份 PDF）：

- `IMX6ULL_ALPHA_V2.4(底板原理图).pdf` → KEY0 按键、`R15 10K` 上拉、底板网 **`UART1_CTS`**、核心板座 **J2_48**
- `IMX6ULL_CORE_V2.0(核心板原理图).pdf` → J2_48 → SoC **GPIO1_IO18**（`UART1_CTS/ENET1_RX_CLK/.../GPIO1_IO18`，K15 球）

```text
KEY0 按键 ── 底板网 "UART1_CTS" ── 核心板座 J2_48 ── SoC GPIO1_IO18
KEY0 按键另一脚 ── GND
VCC_3V3 ── R15 10K ── UART1_CTS 网（上拉）
```

### 2. 底板排针 `GPIO_1` ≠ KEY0，别搞混（本次最关键）

底板上那批座子网名是 **`GPIO_1`、`GPIO_2`…`GPIO_9`** 等，是**底板自己起的排针名**。但它们和「按键」不是一回事——本板 KEY0 **不在 `GPIO_1` 上，而在 `UART1_CTS` 上**：

| 核心板座 J2 | 底板网名 | 底板实际功能 | SoC 脚 |
|------------|---------|-------------|--------|
| J2_47 | `GPIO_3` | **LED0**（`24` 文档） | GPIO1_IO03 |
| **J2_48** | **`UART1_CTS`** | **KEY0（独立按键）** | **GPIO1_IO18** |
| J2_49 | `GPIO_1` | GBC_KEY（游戏卡带键）/ AP_INT（AP3216C 中断） | GPIO1_IO01 |
| J2_43 | `UART1_RTS` | USDHC1_CD_B（SD 卡检测） | GPIO1_IO19 |

- 排针上相邻两脚：`GPIO_1`（=GPIO1_IO01）和 `UART1_CTS`（=GPIO1_IO18）**是两个不同的脚**，别看到「排针上写着 KEY0」就往 `GPIO_1`（GPIO1_IO01）上写。
- 所以 **KEY0 = GPIO1_IO18**，在 dts 里写 `gpios = <&gpio1 18 ...>`（第 1 组 GPIO、脚 18），**不是** `&gpio1 1`，也不是 `&gpio18`。

> ⚠️ **顺带勘误 `24` 文档：** `24` 文档第二节写过一句「`GPIO_1` → GPIO1_IO01（AP3216C 中断 / KEY0 跳线共用）」，其中「KEY0」应为「GBC_KEY（游戏卡带键）」。KEY0 独立按键实际在 **UART1_CTS（GPIO1_IO18）**，与 GPIO_1（GPIO1_IO01）无关。本文以底板原理图 J2 座映射 + 出厂 dts `gpios = <&gpio1 18 ...>` 为准。

### 3. GPIO1_IO18 标号含义（命名规则）

`GPIO1_IO18` 是 i.MX6ULL 的引脚命名，拆成两段：

```text
GPIO1   +   IO18
  │          │
  │          └── 组内第 18 号脚（0～31）
  └── 第 1 组 GPIO 控制器（bank）
```

| 部分 | 含义 |
|------|------|
| `GPIO1` | 第 1 组 GPIO（i.MX6ULL 共 5 组：GPIO1～GPIO5） |
| `IO18` | 组内第 18 个脚（每组 32 个：IO00～IO31） |

**与 dts 写法对应：** 设备树不写 `GPIO1_IO18`，写成「控制器 + 组内偏移」：

```dts
gpios = <&gpio1 18 GPIO_ACTIVE_LOW>;
           │    └── 组内偏移 18（= IO18）
           └── 引用 GPIO1 控制器节点
```

即 `&gpio1 18` = `GPIO1_IO18`。

**与 Linux 全局号对应：**

```text
全局号 = (组号 - 1) × 32 + 组内偏移 = (1 - 1) × 32 + 18 = 18
```

所以 `GPIO1_IO18` 的全局号是 **gpio18**。用 gpio-keys 时**不必碰全局号**，dts 里 `&gpio1 18` 即可。

**原理图里 `UART1_CTS/ENET1_RX_CLK/USDHC1_2_WP/.../GPIO1_IO18` 的 `/` 是什么意思：** 一个物理焊盘（pad）有多个复用功能，靠 IOMUX 切换：

- 复用成 GPIO → `GPIO1_IO18`
- 复用成串口 1 流控输入 → `UART1_CTS`

同一时刻只能选一个。KEY0 要用它，就把它 mux 成 GPIO（L1 里 `MX6UL_PAD_UART1_CTS_B__GPIO1_IO18`），前提是 `UART1_CTS`（串口流控）没被占用——L0 已确认本板 uart1 只走 TX/RX 两线，CTS 空闲。

### 4. 按键电路 → 低电平按下（active-low）

- 原理图：KEY0 一端接 **GND**，另一端接 `UART1_CTS` 网（GPIO1_IO18），并有 `R15 10K` 上拉到 `VCC_3V3` → **下拉按键**。
- 结论：`GPIO1_IO18 = 0` → 按下；`= 1` → 松开。dts 里用 **`GPIO_ACTIVE_LOW`** 表达。
- 好处：内核 input 框架据此自动反相，应用层读到的 `value=1` 就是「按下」，`value=0` 就是「松开」，不用记低电平。

### 5. 驱动选型对比

| 方案 | 是否推荐 | 理由 |
|------|---------|------|
| **A. `gpio-keys`（`compatible="gpio-keys"`）** | **首选** | 内核自带、defconfig 已开、出厂 dts 同款，标准做法 |
| B. 老 sysfs GPIO（`/sys/class/gpio` 读电平） | 不推荐 | 内核 4.x 后已废弃，且只能轮询、无中断上报，仅临时调试 |
| C. 自写 misc/字符驱动 | 不必要 | 按键无协议时序，学习性 > 必要性；gpio-keys 已含中断去抖 |

### 6. 出厂 dts 就是现成答案

`origin/IMX6` 分支 `imx6ull-14x14-evk.dts` 里已有完整节点（本次基本照搬）：

```dts
gpio_keys: gpio_keys@0 {
    compatible = "gpio-keys";
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_gpio_keys>;
    #address-cells = <1>;
    #size-cells = <0>;
    autorepeat;

    key1@1 {
        label = "USER-KEY1";
        linux,code = <114>;       /* KEY_VOLUMEDOWN */
        gpios = <&gpio1 18 GPIO_ACTIVE_LOW>;
        gpio-key,wakeup;
    };
};
```

```dts
pinctrl_gpio_keys: gpio-keys {
    fsl,pins = <
        MX6UL_PAD_UART1_CTS_B__GPIO1_IO18	0x80000000
    >;
};
```

> 出厂节点用 `key1@1` 且带 `#address-cells/#size-cells/autorepeat/gpio-key,wakeup`，本文裁剪成单按键 `key0`（L1 说明裁剪理由）。

## 三、落地顺序（L0～L5）

### L0 — 辨硬件连接**【已完成 2026-09-05】**

不改代码，先确认脚对不对、会不会冲突。逐条核对了当前 dts，结果如下。

1. **看原理图**：KEY0 = `UART1_CTS` → GPIO1_IO18，下拉按键、低电平按下。✅（与 origin/IMX6 出厂 `gpio_keys` 节点 `gpios = <&gpio1 18 GPIO_ACTIVE_LOW>` 一致）

2. **确认 GPIO1_IO18 复用脚不被占** —— 串口流控 `UART1_CTS` 是本脚唯一潜在占用方：
   - **uart1 走两线，无流控。** 基板 dts `pinctrl_uart1`（515–520 行）只有 `UART1_TX_DATA` / `UART1_RX_DATA` 两行，**没有 UART1_CTS/RTS** → GPIO1_IO18（CTS）空闲。✅
   - **UART1_RTS（GPIO1_IO19）已被占用**：基板 dts 里 `MX6UL_PAD_UART1_RTS_B__GPIO1_IO19` 用作 SD 卡检测 `USDHC1_CD_B`（339 行）——但那是 IO19，与 KEY0 的 IO18 不冲突，仅说明「RTS 被占了，CTS 没被占」。✅

3. **记下 dts 写法**：`gpios = <&gpio1 18 GPIO_ACTIVE_LOW>`（**gpio1 + 脚号 18**，不是 `&gpio1 1`，也不是 `&gpio18`）。✅

**结论 / 通过判据：** KEY0 在 GPIO1_IO18、低电平按下；uart1 两线无 CTS，**无运行时冲突，L0 通过**。

> **约束：** 若哪天 uart1 要开硬件流控（加 `UART1_CTS` 进 `pinctrl_uart1`），会与 KEY0 抢 GPIO1_IO18，需先让出一个。当前两线调试串口无需流控，不影响。

### L4 — 板载读原始事件**【已完成 2026-09-06】**

烧写/启动后，先定位事件设备，再读原始事件：

```bash
dmesg | grep -i "gpio-keys\|input"          # 看有无 gpio-keys 注册/报错
ls -l /dev/input/                            # 看 eventX 设备
cat /proc/bus/input/devices                  # 找 "gpio-keys" 那一节的 Handlers=eventX
```

实测 KEY0 对应 `event2`（`cat /proc/bus/input/devices` 里 `Name="gpio_keys"` 那节 `Handlers=kbd event2`），按住/松开 KEY0 的同时读原始事件：

```bash
hexdump /dev/input/event2
```

| 现象 | 期望结果 | 说明 |
|------|---------|------|
| `dmesg` 无报错 | gpio-keys probe 成功 | 成功时不打印，报错才打印 |
| `cat /proc/bus/input/devices` | 有 `Name="gpio-keys"` 一节 | input 设备注册成功 |
| `hexdump event2` 按/松 KEY0 | 每按/松各输出 16 字节 | 见下方事件格式 |

**事件格式（`struct input_event`，32 位平台 16 字节）：** 每行 16 字节 = `time(8) + type(2) + code(2) + value(4)`。KEY0 按下/松开对应：

```text
type = 1 (EV_KEY)，code = 114 (KEY_VOLUMEDOWN)
按下：value = 1     松开：value = 0
```

> **读 raw 事件时怎么认「按下/松开」：** hexdump 是 little-endian 字节序，`struct input_event` 里 `type/code/value` 三个字段连读，认 `type=0001`、`code=0072`(=114)、`value=0001`(按)/`0000`(松) 即可。真正的判断交给应用层（L5）或 `evtest` 工具，比肉眼认 hexdump 直观。

**通过判据：** 按/松 KEY0 时 `hexdump` 能刷出事件，且 `value` 按下=1、松开=0（若反过来，说明 active-low 写反了）。下一步 L5。

> **本次已验收（2026-09-06）：** 定位阶段通过——`gpio_keys` 注册成功、无报错，KEY0 对应 **`/dev/input/event2`**：
> - `dmesg | grep -i "gpio-keys\|input"` → `input: gpio_keys as .../input/input2`（probe 成功；成功不打印，报错才打印）。
> - `ls -l /dev/input/` → `event0`(snvs-powerkey) / `event1`(goodix-ts) / `event2`(**gpio_keys**)。
> - `cat /proc/bus/input/devices` 的 `Name="gpio_keys"` 一节：`Phys=gpio-keys/input0`、`Handlers=kbd event2`、`EV=3`（=EV_SYN+EV_KEY）、`KEY=40000 0 0 0`；`Bus=0019 Vendor=0001 Product=0001 Version=0100` 与 `gpio_keys.c` probe 里的 `BUS_HOST / 0x0001 / 0x0001 / 0x0100` 完全一致。
> - **`KEY=40000 0 0 0` 解码：** `/proc` 的 `KEY=` 按**高位字在前（倒序）**打印，`40000` 是第 4 个字（覆盖键值 96~127），`0x40000 = 1<<18` → 键值 96 + 18 = **114（KEY_VOLUMEDOWN）**，与 dts `linux,code = <114>` 一致 ✅。
> - **`hexdump /dev/input/event2`（按/松实测）：** 每按/松各刷出 **2 行 16 字节 = `EV_KEY` + `EV_SYN` 一对**，实测按下/松开共 9 组全部正常。一行 16 字节 = 一个 `struct input_event`（`time(8) + type(2) + code(2) + value(4)`，小端），8 个 16 位字依次 = `tv_sec低 tv_sec高 tv_usec低 tv_usec高 type code value低 value高`。前两行解码：
>
>   ```text
>   1ad9 0003 3881 0005 0001 0072 0001 0000  → type=1(EV_KEY) code=0x72(114) value=1  按下
>   1ad9 0003 3881 0005 0000 0000 0000 0000  → type=0(EV_SYN)  code=0(SYN_REPORT) value=0 同步分隔
>   1ad9 0003 826e 0007 0001 0072 0000 0000  → type=1(EV_KEY) code=114       value=0  松开
>   1ad9 0003 826e 0007 0000 0000 0000 0000  → EV_SYN
>   ```
>
>   `value=1` 按下、`0` 松开，方向正确（**active-low 反相生效** ✅）。`type=0/code=0` 的 `EV_SYN(SYN_REPORT)` 是 input 子系统的**事件边界分隔符**，每次 `EV_KEY` 后都跟一条，读事件时以它为一帧的结尾。

### L5 — 应用层读按键 / 按键点灯联动**【已完成 2026-09-06 · 代码已备，待板上验证】**

1. **`evtest`（最直观，若系统里有）——本板没有：** busybox rootfs 未装 `evtest`（实测 `/bin/sh: evtest: not found`），跳过。若有 `evtest`，则 `evtest /dev/input/event2` 按 KEY0 直接打印 `EV_KEY KEY_VOLUMEDOWN 1`（按下）/ `0`（松开）。

2. **自己写 C 读事件 + 按键点灯（一步到位，推荐）：** `read` 出 `struct input_event`，过滤 `type==EV_KEY(1) && code==114`，`value==1` 即按下；按下瞬间翻转 LED0（写 `sys-led/brightness`），把 `24`（LED 输出）和 `27`（KEY 输入）串成闭环。完整源码 `key0_led.c`：

   ```c
   /* key0_led.c —— 读 KEY0 事件，按一下翻转一次 LED0 */
   #include <stdio.h>
   #include <fcntl.h>
   #include <unistd.h>
   #include <linux/input.h>

   int main(int argc, char **argv)
   {
       const char *dev = argc > 1 ? argv[1] : "/dev/input/event2";
       int fd, led_state = 0;               /* LED 状态：0=灭 1=亮 */
       struct input_event ev;

       fd = open(dev, O_RDONLY);
       if (fd < 0) {
           perror("open");
           return 1;
       }

       while (read(fd, &ev, sizeof(ev)) == sizeof(ev)) {
           if (ev.type != EV_KEY)           /* 跳过 EV_SYN 等非按键事件 */
               continue;

           if (ev.code == KEY_VOLUMEDOWN) { /* 114，dts 里的 linux,code */
               if (ev.value == 1)
                   printf("KEY0 pressed\n");
               else if (ev.value == 0)
                   printf("KEY0 released\n");

               if (ev.value == 1) {         /* 按下瞬间翻转 LED */
                   int lfd = open("/sys/class/leds/sys-led/brightness", O_WRONLY);
                   led_state = !led_state;
                   if (lfd >= 0) {
                       write(lfd, led_state ? "1" : "0", 1);
                       close(lfd);
                   }
               }
           }
       }

       close(fd);
       return 0;
   }
   ```

   交叉编译（工具链见 `scripts/common.sh` 的 `TOOLCHAIN`：Linaro 4.9.4，`arm-linux-gnueabihf`）：

   ```bash
   /usr/local/arm/gcc-linaro-4.9.4-2017.01-x86_64_arm-linux-gnueabihf/bin/arm-linux-gnueabihf-gcc key0_led.c -o key0_led
   ```

   拷到板子运行 `./key0_led`（`Ctrl+C` 退出）。每按一次 KEY0：打印 `KEY0 pressed/released` 且 LED0 翻转。

   > 要点：`read` 一次 16 字节 = 一个 `struct input_event`（同 L4 的 hexdump）；只认 `ev.type == EV_KEY`，自动跳过 `EV_SYN`；`value=1` 按下、`0` 松开。LED0 那边 `24` 里已设 `default-state="on"` 且无 trigger，所以直接 `write "1"/"0"` 即亮/灭。

**通过判据：** 应用层能稳定读到 KEY0 按下/松开；「按键点灯」跑通，说明 GPIO 输入（按键）与输出（LED）两套子系统全部打通。

## 附录 D：pinctrl 单行拆解（`MX6UL_PAD_...__...  0x80000000`）

L1 里那行：

```dts
MX6UL_PAD_UART1_CTS_B__GPIO1_IO18  0x80000000
```

由「宏 + 配置值」两部分组成，整体含义：**把 GPIO1_IO18 这颗 pad 复用成 GPIO（ALT5），且不写 PAD_CTL 寄存器（保持复位默认电气）**。

### 宏 `MX6UL_PAD_<焊盘>__<功能>`

命名格式是 `MX6UL_PAD_<焊盘>__<功能>`：

| 部分 | 含义 |
|------|------|
| `UART1_CTS_B`（`__` 左边） | 要配置的**物理引脚**（pad 名，B = 低有效逻辑） |
| `GPIO1_IO18`（`__` 右边） | 复用成的**功能** = GPIO1 组第 18 号 GPIO |

定义在 `imx6ul-pinfunc.h`，展开成 5 个数字：

```c
#define MX6UL_PAD_UART1_CTS_B__GPIO1_IO18  0x008C 0x0318 0x0000 0x5 0x0
```

| 字段 | 值 | 含义 |
|------|-----|------|
| `0x008C` | mux 寄存器偏移 | `SW_MUX_CTL_PAD_UART1_CTS_B`，决定复用成哪个功能 |
| `0x0318` | conf 寄存器偏移 | `SW_PAD_CTL_PAD_UART1_CTS_B`，决定电气属性（`0x80000000` 表示**不写**它） |
| `0x0000` | input 寄存器偏移 | 输入复用（daisy）选择，0 = 本脚不需要 |
| `0x5` | **mux 模式** | **ALT5 = GPIO**（把 pad 复用成 GPIO1_IO18） |
| `0x0` | input 选择值 | 配 input 寄存器用，这里为 0 |

### 配置值 `0x80000000` = 不写 PAD_CTL（和 LED0 的 `0x17059` 关键区别）

`0x80000000` 不是电气参数，而是 pinctrl-imx 的**软件标志位**：

```c
/* drivers/pinctrl/freescale/pinctrl-imx.c */
#define IMX_NO_PAD_CTL  0x80000000
```

含义：**只写 MUX 寄存器（复用成 GPIO），不写 PAD_CTL 寄存器**，让该 pad 保持复位默认电气。内核据此跳过 PAD_CTL 配置（`pinctrl-imx.c` 里 `if (!(config & IMX_NO_PAD_CTL))` 才写 conf 寄存器）。

| 对比 | LED0（`0x17059`） | KEY0（`0x80000000`） |
|------|------------------|---------------------|
| 方向 | **输出**（点亮 LED） | **输入**（读按键） |
| 为什么 | 要配推挽/驱动强度/斜率才能正常灌电流 | 输入不需要驱动强度，上拉靠底板 R15 10K 外部电阻 |
| 寄存器 | 写 SW_PAD_CTL | **不写**，保持复位默认 |

> **一句话：** 输出（LED）要配电气；输入（KEY）外接上拉后，PAD_CTL 保持默认即可，`0x80000000` 就是「别动电气、只切复用」。

## 附录 E：内核配置逆向确定方法（从 compatible 追到要开哪些 CONFIG）

L2 里「怎么知道要开这几个宏」的完整套路，一句话：**从 dts 的 `compatible` 出发，逆向追到 `Makefile` 的 `obj-$(CONFIG_X)`，再到 `Kconfig` 的 `depends on`**。以后任何外设都能照此办。以 KEY0 为例走一遍：

### 第 1 步：`compatible` → 驱动源文件

dts 里 `compatible = "gpio-keys"`，内核据此匹配驱动。查 `drivers/input/keyboard/gpio_keys.c`：

```c
static const struct of_device_id gpio_keys_of_match[] = {
    { .compatible = "gpio-keys", },
    { },
};
```

→ 命中 `gpio_keys.c`，这就是要编进内核的驱动。

### 第 2 步：驱动源文件 → CONFIG 宏

该源文件是否编译，由所在目录的 `Makefile` 决定。`drivers/input/keyboard/Makefile`：

```make
obj-$(CONFIG_KEYBOARD_GPIO) += gpio_keys.o
```

→ 要编 `gpio_keys.c` 就得开 `CONFIG_KEYBOARD_GPIO`。

### 第 3 步：CONFIG 宏 → 依赖（depends on）

`drivers/input/keyboard/Kconfig`：

```kconfig
config KEYBOARD_GPIO
    tristate "GPIO Buttons"
    depends on GPIOLIB
    select INPUT_POLLDEV
```

→ `KEYBOARD_GPIO` 依赖 `GPIOLIB`（GPIO 子系统，ARM 平台必开）。`INPUT_POLLDEV` 是轮询框架（gpio-keys 用中断，不常触发，但作为依赖被 select）。

### 第 4 步：input 子系统 + 事件接口

光有驱动还不够，得把事件从内核送到用户态 `/dev/input/eventX`：

| 需求 | 对应 CONFIG | 说明 |
|------|-------------|------|
| input 子系统总开关 | `CONFIG_INPUT` | 所有 input 驱动的前置 |
| 事件设备接口 | `CONFIG_INPUT_EVDEV` | `/dev/input/eventX`，应用 read 的就是它 |

### 汇总（本 KEY0 最小集合）

| 需求 | 对应 CONFIG | 本板状态 |
|------|-------------|---------|
| input 子系统总开关 | `CONFIG_INPUT` | =y |
| `/dev/input/eventX` 接口 | `CONFIG_INPUT_EVDEV` | =y |
| `gpio-keys` 驱动 | `CONFIG_KEYBOARD_GPIO` | =y |

> **通用口诀：** `compatible`（dts）→ `of_match`（.c）→ `obj-$(CONFIG_X)`（Makefile）→ `depends on`（Kconfig）→ `menuconfig` 总开关。拿到任何一个外设，先找它的 `compatible` 字符串，剩下顺着这条链走就全知道了。
