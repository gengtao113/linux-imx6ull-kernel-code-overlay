## 一、导读

### 1.1 一句话结论

**U-Boot 能 TFTP ≠ 内核网口可用。**  
Linux 正确路径是：

```text
NFS / ping
    ↑
内核协议栈 + IP-Config
    ↑
FEC MAC（内核已有）  ←→ RMII ←→ SR8201F PHY
    ↑
设备树：pinctrl + phy-mode + phy-handle + phy-reset-gpios
    +
fec 板级补丁：复位后再等 150ms、TX_CLK pad 写 0x14
```

不要移植 `SR8201F/` 下的 MCU（GD32/STM32）驱动；那是裸机示例。Linux 用 **FEC + Generic PHY（Clause22）**。

### 1.2 硬件 ↔ 节点 ↔ 驱动（速查）

| 硬件 | 设备树 | 驱动 / 子系统 |
|------|--------|----------------|
| FEC2 @ `0x020b4000` | `fec2: ethernet@020b4000` | **fec** → 通常 **eth0** |
| FEC1 @ `0x02188000` | `fec1: ethernet@02188000` | **fec** → 通常 **eth1**（U-Boot 的 FEC1） |
| SR8201F（ENET1，地址 0x02） | `ethphy0: ethernet-phy@2` | **Generic PHY** |
| SR8201F（ENET2，地址 0x01） | `ethphy1: ethernet-phy@1` | **Generic PHY** |
| `ENET1_RST` / `ENET2_RST` | `phy-reset-gpios` + `pinctrl_fec*_reset` | `fec_reset_phy()` |
| RMII 数据线 / 时钟脚 | `pinctrl_enet1` / `pinctrl_enet2` | **pinctrl** |
| MDIO 总线 | `&fec2` 下 `mdio { ... }` | phylib / MDIO bus |
| NFS 参数 | `/chosen/bootargs`（`ip=` / `nfsroot=`） | early IP-Config（见 `09`） |

### 1.3 两条独立配置链（同份 dtb）

| 链路 | 设备树 | 内核入口 | 作用 |
|------|--------|----------|------|
| **启动/NFS** | `/chosen/bootargs` | `early_init_dt_scan_chosen()` | 命令行、`ip=...::eth0:`、NFS 根 |
| **网口** | `fec*` → `mdio` → `ethernet-phy@*` | `fec_probe` → `of_phy_connect` | MAC、PHY 复位、MDIO 地址 |

改网口主要动 **FEC/PHY 链**；cmdline 的 `ip=...::eth0:` 只指定 **哪张已 UP 的网卡** 做 IP-Config。两链并存，读取路径不同（详见 `09` §1.2）。

### 1.4 匹配总览（从 dts 到 NFS）

```text
形态 A  板级 dts（&fec1 / &fec2 / mdio / pinctrl）
           │ dtc
形态 B  dtb 二进制块（TFTP → U-Boot → 内核）
           │ unflatten（见 09）
形态 C  device_node 树
           │
           ├─ compatible = "fsl,imx6ul-fec" ──► fec_probe
           │       ├─ fec_reset_phy（phy-reset-gpios + 150ms）
           │       ├─ TX_CLK pad writel(0x14)
           │       └─ 注册 eth0 / eth1（registered ≠ PHY 已挂）
           │
           ├─ phy-handle / ethernet-phy@x ──► of_phy_connect
           │       └─ Generic PHY（ieee802.3-c22）
           │
           └─ bootargs ip=...::eth0: ──► IP-Config → NFS login
```

## 三、内核驱动匹配全过程（本板）

> 源码：`projects/gengtao-bsp-0901/drivers/net/ethernet/freescale/fec_main.c`  
> 辅助：`drivers/of/platform.c`、`drivers/of/of_mdio.c`、`drivers/net/phy/phy_device.c`  
> 下文 **A～G** 为启动到 NFS 的 **七段匹配链**；**§4 分步** 对其中各段展开 dts 字段细节。

### 3.1 总览：七段匹配链

```text
A. 设备树展开 + 创建设备
   unflatten → of_platform_populate → platform_device（fec2 先于 fec1）

B. Platform 驱动匹配（MAC）
   compatible "fsl,imx6ul-fec" ↔ fec_dt_ids[] → fec_probe

C. 板级资源绑定（仍在 fec_probe，每颗 FEC 各跑一遍）
   pinctrl / reg ioremap / phy-handle / phy-reset / TX_CLK 补丁 / clocks

D. MDIO 总线 + PHY 设备（仅 dev_id==0 那颗 FEC）
   fec_enet_mii_init → of_mdiobus_register → get_phy_device → phy_device_register

E. 注册 netdev（probe 末尾，PHY 尚未连 MAC）
   register_netdev → eth0 / eth1 出现；carrier off

F. 打开网卡 + 绑 PHY（IP-Config 或 ifconfig up 触发）
   fec_enet_open → fec_enet_mii_probe → of_phy_connect → phy_attach_direct → Generic PHY

G. 链路与 NFS
   phy_start → Link Up → IP-Config(eth0) → mount nfs
```

**关键分界：**

| 阶段 | 已完成 | 尚未完成 |
|------|--------|----------|
| `fec_probe` 返回 | eth0/eth1 存在；mdio 上 phy_device 已建 | MAC **未**绑 PHY；链路 **down** |
| `fec_enet_open` 成功 | Generic PHY 挂上；可 Link Up | 应用层 ping/NFS 另说 |

### 3.2 A 段：从 dtb 到 platform_device

```text
dtb（形态 B）→ unflatten_device_tree() → device_node 树（形态 C）
        ↓
of_platform_populate(/soc/aips-bus@.../aips2@...)
        ↓ for_each_child_of_node（顺序 ≈ dtsi 兄弟顺序）
先 ethernet@020b4000（fec2）→ platform_device + dev.of_node
后 ethernet@02188000（fec1）→ platform_device + dev.of_node
```

仅 `status = "okay"` 的节点会创建设备；dtsi 默认 `disabled`，板级 `&fec*` 覆盖为 `okay`。

### 3.3 B 段：FEC platform 驱动如何匹配

```c
static const struct of_device_id fec_dt_ids[] = {
    { .compatible = "fsl,imx6ul-fec", .data = &fec_devtype[IMX6UL_FEC], },
    { .compatible = "fsl,imx6q-fec", .data = &fec_devtype[IMX6Q_FEC], },
    ...
};
static struct platform_driver fec_driver = {
    .driver.of_match_table = fec_dt_ids,
    .probe = fec_probe,
};
module_platform_driver(fec_driver);
```

| dts | 内核 |
|-----|------|
| `compatible = "fsl,imx6ul-fec", "fsl,imx6q-fec"` | 按表顺序匹配，**先命中 imx6ul-fec** |
| 匹配成功 | `of_match_device()` → `fep->quirks = IMX6UL_FEC 的 driver_data` |

本板 `IMX6UL_FEC` 含 **`FEC_QUIRK_ENET_MAC`**（双 FEC 共用 MDIO、第二颗复用总线）等；后续 `fec_enet_mii_init` 分支依赖此 quirk。

### 3.4 C 段：`fec_probe` 内板级绑定（按代码顺序）

两颗 FEC **各执行一遍** `fec_probe`；下列为关键步骤（简化）：

| 顺序 | 函数 / 动作 | 读的 dts / 硬件 |
|------|-------------|-----------------|
| 1 | `writel(0x14)` TX_CLK pad | 板级补丁（IMX6 ALPHA） |
| 2 | `of_match_device` → `fep->quirks` | `compatible` |
| 3 | `pinctrl_pm_select_default_state` | `pinctrl-0 = pinctrl_enet* + fec*_reset` |
| 4 | `devm_ioremap_resource` → `fep->hwp` | `reg = <0x020b4000/0x02188000>` |
| 5 | `fep->dev_id = dev_id++` | **probe 顺序**，非 fec1/fec2 标签 |
| 6 | `of_parse_phandle(np, "phy-handle", 0)` → `fep->phy_node` | `phy-handle = <&ethphyN>` |
| 7 | `of_get_phy_mode` → `fep->phy_interface` | `phy-mode = "rmii"` |
| 8 | `devm_clk_get` ipg/ahb/ptp/... | `clocks` / `clock-names` |
| 9 | **`fec_reset_phy(pdev)`** | `phy-reset-gpios` + duration + **150ms** |
| 10 | `fec_enet_init`、申请 IRQ | `interrupts` |
| 11 | **`fec_enet_mii_init(pdev)`** | 见 D 段 |
| 12 | **`register_netdev(ndev)`** | 出现 eth0/eth1；日志 `PHC device N` |

此阶段 **只保存** `fep->phy_node` 指针，**不调用** `of_phy_connect`。

#### 3.4.1 C 段展开：pinctrl 匹配全过程（网卡）

> **`<>` 与 `fsl,pins` 单行语义** 见 **Step 1.1 / 1.2**；与屏文档 **`09` §3-B B.6.1** 同一套 pinctrl 子系统，本节只写 **FEC 本板差异**。

**核心结论**：网卡 pinctrl **不走** FEC 的 `compatible`；是 **iomuxc 控制器登记 group → fec probe/open 按 phandle 引用 → 写 IOMUXC** 的独立链。与 lcdif 的差别主要在 **API 调用点** 和 **RMII 特殊脚（TX_CLK / MDIO）**。

##### 两层结构（本板）

```text
【控制器链 — 与屏相同，arch_initcall】
iomuxc@020e0000           fsl,imx6ul-iomuxc
  └─ imx6ul-evk/
       enet1grp / enet2grp     ← RMII 数据 + MDIO(fec2) + TX_CLK
iomuxc-snvs@02290000      fsl,imx6ull-iomuxc-snvs
  └─ imx6ul-evk/
       fec1_resetgrp / fec2_resetgrp   ← PHY 复位脚 MUX 为 GPIO

【消费链 — 每颗 FEC 各一条】
&fec1 {
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_enet1 &pinctrl_fec1_reset>;
};
&fec2 {
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_enet2 &pinctrl_fec2_reset>;
};
```

| 层级 | 匹配键 | 内核入口 |
|------|--------|----------|
| IOMUXC / SNVS 控制器 | `fsl,imx6ul-iomuxc` 等 | `imx6ul_pinctrl_probe`（登记 group） |
| pin group | **phandle + 节点名**（`enet1grp` 等） | 无独立驱动 |
| FEC 消费 | `pinctrl-0` + `pinctrl-names` | **`pinctrl_pm_select_default_state`** |

##### 与 mxsfb（屏）的 API 对比

| 外设 | 调用时机 | API |
|------|----------|-----|
| **fec** | **`fec_probe` 开头**（匹配后、ioremap 前） | `pinctrl_pm_select_default_state` |
| **fec** | **`fec_enet_open`**（IP-Config / ifconfig up） | 再次 `pinctrl_pm_select_default_state` |
| lcdif / mxsfb | probe 内（init_fbinfo 之后） | `devm_pinctrl_get_select_default` |

效果等价：都是 `pinctrl_get` + 选 `"default"` state + `imx_pmx_set` / `imx_pinconf_set`。

##### 本板三组 group 分工

| label | group | 控制器 | 内容 |
|-------|-------|--------|------|
| `pinctrl_enet1` | `enet1grp` | iomuxc | ENET1 RMII 8 脚 + **TX_CLK/REF_CLK** |
| `pinctrl_enet2` | `enet2grp` | iomuxc | ENET2 RMII 8 脚 + **MDC/MDIO**（GPIO1_IO07/06）+ TX_CLK |
| `pinctrl_fec1_reset` | `fec1_resetgrp` | **iomuxc_snvs** | SNVS_TAMPER7 → GPIO5_IO07 |
| `pinctrl_fec2_reset` | `fec2_resetgrp` | iomuxc_snvs | SNVS_TAMPER8 → GPIO5_IO08 |

**fec2 的 `enet2grp` 多 MDC/MDIO**：本板 MDIO 总线挂在 fec2，`of_mdiobus_register` 需物理 MDIO 脚已 mux；故 **MDC/MDIO 写在 fec2 的 pinctrl group**，不在 fec1。

##### pinctrl 与 `phy-reset-gpios` 的分工（勿混）

| 机制 | dts | 作用 |
|------|-----|------|
| **pinctrl** | `pinctrl_fec*_reset` + `fsl,pins` | 把复位 pad **复用成 GPIO**（MUX） |
| **GPIO 驱动** | `phy-reset-gpios = <&gpio5 7 ...>` | `fec_reset_phy()` **拉低/拉高**复位 PHY（时序） |

pinctrl 只负责「脚能当 GPIO 用」；**200ms duration + 150ms msleep** 在 `fec_reset_phy`，见 Step 3。

##### `fec_probe` 内与 pinctrl 相关的真实顺序

```text
fec_probe（每颗 FEC 各跑一遍；下列 ① 对两颗 FEC 都会写两个 TX_CLK）
  ① writel(0x14) @ 0x020E00DC / 0x020E00FC   ← 早于 pinctrl，强写 TX_CLK MUX+SION
  ② of_match_device → quirks
  ③ pinctrl_pm_select_default_state            ← 应用 pinctrl-0 全部 group（含 TX_CLK PAD 0x4001B009）
  ④ devm_ioremap_resource(reg)
  ⑤ of_parse_phandle("phy-handle")
  ⑥ fec_reset_phy(phy-reset-gpios)             ← GPIO 复位，依赖 ③ 已 mux 成 GPIO
  ...
  ⑪ fec_enet_mii_init（仅 dev_id==0 / 通常 fec2）
```

**TX_CLK 双保险**：dts `fsl,pins` 配 **PAD_CTL（0x4001B009）+ mux_mode（含 SION 位）**；驱动 ① 再 **硬写 MUX 寄存器 0x14**。只改复位、不改 pinctrl/① 时本板仍可能无 Generic PHY（见 Step 5、`06`）。

##### open 阶段再次 select default

```text
fec_enet_open
  → pinctrl_pm_select_default_state   ← 从 sleep 恢复或确保 RMII 脚有效
  → fec_enet_mii_probe → of_phy_connect
```

验证：pinctrl 在 probe 失败不会单独打日志；以 **eth 注册 + open 后 Generic PHY** 为旁证（§6）。

### 3.5 D 段：MDIO 与 PHY 设备匹配（phylib）

仅在 **`fec_enet_mii_init`** 中；本板 **dev_id==0（通常 fec2）** 走完整路径：

```text
mdiobus_alloc
  .read  = fec_enet_mdio_read    → 写 FEC_MII_DATA（MMFR），PA=reg
  .write = fec_enet_mdio_write
        ↓
of_get_child_by_name(fec_of_node, "mdio")
        ↓
of_mdiobus_register(bus, mdio_node)
  对每个 ethernet-phy@* 子节点：
    addr = reg
    get_phy_device(bus, addr)     → MDIO 读 PHYSID1/2 → phy_id
    phy->dev.of_node = 该 phy 节点
    phy_device_register(phy)      → phy_map[addr] = phy
        ↓
device_add → mdio 总线匹配 phy_driver（或稍后 open 时 genphy）
```

**dev_id==1（通常 fec1）**：

```c
if ((fep->quirks & FEC_QUIRK_ENET_MAC) && fep->dev_id > 0) {
    fep->mii_bus = fec0_mii_bus;   /* 复用第一颗的 mii_bus */
    return 0;                      /* 不读 fec1 下的 mdio */
}
```

| 匹配对象 | 匹配键 | 驱动 |
|----------|--------|------|
| FEC MAC | `compatible` → `fec_dt_ids` | **fec**（platform） |
| PHY 芯片 | MDIO 读出的 **phy_id**（+ 可选 fixup） | 专用 phy_driver 或 **genphy** |
| dts `ieee802.3-c22` | 只定 Clause22 探测方式 | **不**指定 SR8201F 驱动名 |

### 3.6 E 段：`register_netdev` 与 eth 命名

```c
ret = register_netdev(ndev);   /* fec_probe 末尾 */
```

| 现象 | 含义 |
|------|------|
| `fec 20b4000.ethernet eth0: registered PHC device 0` | fec2 → **eth0**，**dev_id=0** |
| `fec 2188000.ethernet eth1: registered PHC device 1` | fec1 → **eth1**，**dev_id=1** |
| 此时无 `Generic PHY` | **正常**——PHY 在 **open** 时才 connect |

eth 序号由内核 **网络设备分配** 决定，与 dts 标签 fec1/fec2 **无固定 1:1**；本板实测 fec2→eth0。

### 3.7 F 段：open 时 MAC ↔ PHY 最终绑定

NFS 启动时 **IP-Config** 会对 `ip=...::eth0:` 指定接口做 **`dev_open()`** → `fec_enet_open`：

```text
fec_enet_open(ndev)
  pinctrl_pm_select_default_state
  fec_enet_clk_enable(true)
  fec_restart(ndev)
  fec_enet_mii_probe(ndev)
        ↓
    if (fep->phy_node)
        of_phy_connect(ndev, fep->phy_node, fec_enet_adjust_link, ..., RMII)
            ↓
        of_phy_find_device(phy_np)     /* dev->of_node == phy-handle 指向的节点 */
            ↓
        phy_connect_direct → phy_attach_direct
            ↓
        若无专用 driver → 绑定 genphy（Generic PHY）
  phy_start(phy_dev)                   /* 自协商、链路监测 */
  netif_tx_start_all_queues
```

失败路径（L5/L6 未打通时常见）：

```text
of_phy_connect 失败 → fec_enet_open 返回 -ENODEV
  → IP-Config: Failed to open eth0
  → IP-Config: Device `eth0' not found   （二次误报）
```

成功日志：

```text
Freescale FEC PHY driver [Generic PHY] (mii_bus:phy_addr=20b4000.ethernet:01, ...)
fec 20b4000.ethernet eth0: Link is Up - 100Mbps/Full
```

### 3.8 G 段：与 NFS 链汇合

```text
bootargs: ip=192.168.3.51:...::eth0:off  （/chosen，见 09）
        ↓
eth0 open 成功 + Link Up
        ↓
IP-Config: Complete → mount nfs → login
```

### 3.9 本板双 FEC 一次启动的完整顺序（对照表）

| 次序 | 事件 | 匹配/绑定结果 |
|------|------|----------------|
| 1 | populate fec2@020b4000 | platform_device |
| 2 | **fec_probe** fec2，dev_id=0 | quirks=IMX6UL；phy_node→ethphy1 |
| 3 | fec_enet_mii_init(fec2) | **of_mdiobus_register**；phy_map[1]、[2] |
| 4 | register_netdev | **eth0** |
| 5 | populate / probe fec1@02188000，dev_id=1 | phy_node→ethphy0；**复用 mii_bus** |
| 6 | register_netdev | **eth1** |
| 7 | IP-Config open **eth0** | of_phy_connect→ethphy1→Generic PHY |
| 8 | Link Up + NFS | 根文件系统挂载 |

### 3.10 驱动匹配 vs dts 属性（速查）

| dts 属性 | 匹配/使用阶段 | 内核入口 |
|----------|---------------|----------|
| `compatible` (fec) | B：platform 匹配 | `of_match_device` / `fec_probe` |
| `status` | A：是否创建设备 | of_platform_populate |
| `reg` (fec) | C：ioremap | `devm_ioremap_resource` |
| `pinctrl-0` | C：引脚 | `pinctrl_pm_select_default_state`（见 **§3.4.1**、**Step 1.1**） |
| `fsl,pins`（group 内） | C | `imx_pinctrl_parse_groups` → `imx_pmx_set` / `imx_pinconf_set`（**Step 1.2**） |
| `fsl,imx6ul-iomuxc` | C | `imx6ul_pinctrl_probe`（控制器链，同 **`09`**) |
| `phy-mode` | C/F：RMII | `of_get_phy_mode` / `of_phy_connect` |
| `phy-reset-gpios` | C：复位 PHY | `fec_reset_phy` |
| `phy-handle` | C 存指针；**F 绑定** | `of_parse_phandle` / `of_phy_connect` |
| `mdio` / `ethernet-phy@*` | D：PHY 设备 | `of_mdiobus_register` |
| `reg` (phy) | D：MDIO 站号 | `get_phy_device(bus, addr)` |
| `bootargs ip=::eth0:` | G：选哪张网卡 | IP-Config（非 fec 驱动） |

### Step 1 — FEC 节点匹配（出 eth0 / eth1）

SoC 定义在 `imx6ull.dtsi`：

| Linux 名 | SoC 地址 | dts 标签 | U-Boot |
|----------|----------|----------|--------|
| **eth0** | `0x020b4000` | **fec2** / ENET2 | 通常非默认口 |
| **eth1** | `0x02188000` | **fec1** / ENET1 | 日志里的 **FEC1**（TFTP 常用） |

```text
compatible = "fsl,imx6ul-fec", "fsl,imx6q-fec"
        ↓
fec_dt_ids[] 匹配
        ↓
fec_probe()
        ↓
日志：fec 20b4000.ethernet eth0: registered PHC device 0
      fec 2188000.ethernet eth1: registered PHC device 1
```

**关键：** `registered` / `PHC` 只说明 **netdev 已注册**，**不等于** PHY 已挂上。  
本板最终 NFS 走的是 **eth0（fec2 / ENET2）**；U-Boot TFTP 走的是 **FEC1（eth1）**——插线口与 `ip=...::eth0:` 要对上（见 `06`）。

板级在 `imx6ull-14x14-evk-gengtao0901.dts` 为每颗 FEC 合并 pinctrl（与 `status = "okay"` 同节点）：

```dts
&fec1 {
	pinctrl-names = "default";
	pinctrl-0 = <&pinctrl_enet1
		     &pinctrl_fec1_reset>;
	/* phy-mode / phy-handle / phy-reset-gpios ... */
	status = "okay";
};

&fec2 {
	pinctrl-names = "default";
	pinctrl-0 = <&pinctrl_enet2
		     &pinctrl_fec2_reset>;
	/* mdio { ethphy0/1 ... } */
	status = "okay";
};
```

#### Step 1.1 — `pinctrl-0 = <&...>` 里的 `<>` 如何理解（网卡）

> pinctrl **通用 phandle 机制**与 **`09` Step 1.1.1** 相同；本节只写 **FEC 本板三个要点**。

**一句话**：`<&pinctrl_enet1 &pinctrl_fec1_reset>` = fec1 在 default 状态下启用 **RMII 数据/时钟组** + **复位脚 GPIO 组**；编译后 label 变 phandle，内核 `pinctrl_pm_select_default_state` 解析。

##### （1）`<>` 里两个 phandle 各指什么

| phandle（源码 label） | group 节点 | 定义位置 | 作用 |
|----------------------|------------|----------|------|
| `&pinctrl_enet1` | `enet1grp` | `&iomuxc` | ENET1 RMII 8 线 + REF_CLK |
| `&pinctrl_fec1_reset` | `fec1_resetgrp` | **`&iomuxc_snvs`** | ENET1_RST → GPIO5_IO07 |
| `&pinctrl_enet2` | `enet2grp` | `&iomuxc` | ENET2 RMII + **MDC/MDIO** + REF_CLK |
| `&pinctrl_fec2_reset` | `fec2_resetgrp` | `&iomuxc_snvs` | ENET2_RST → GPIO5_IO08 |

一条 `pinctrl-0` 可混合 **主 iomuxc + snvs iomuxc** 两个控制器下的 group（与屏 `lcdif_reset` 同机制，见 **`09` Step 1.1.1**）。

##### （2）内核解析链（fec 消费侧）

```text
pinctrl_pm_select_default_state(&pdev->dev)
  → pinctrl_get(fec.dev)
  → pinctrl_dt_to_map：读 pinctrl-0 的 phandle 列表
  → 对每个 group：dt_to_map_one_config → imx_dt_node_to_map
  → pinctrl_select_state("default")
  → imx_pmx_set + imx_pinconf_set 写 IOMUXC
```

源码：`drivers/pinctrl/devicetree.c`、`drivers/pinctrl/freescale/pinctrl-imx.c`；**不是** `of_match_device` 匹配 group。

##### （3）与 `phy-handle`、MDIO 的边界

| 属性 | 匹配方式 | 阶段 |
|------|----------|------|
| `pinctrl-0` | phandle → pin group | **C：probe/open**，写 IOMUXC |
| `phy-handle` | phandle → `ethernet-phy@*` | C 存指针；**F：open** 才 `of_phy_connect` |
| `mdio` 子节点 | 节点名 `"mdio"` | D：`fec_enet_mii_init` |

pinctrl 错 → RMII/MDIO 波形出不来 → MDIO 读 PHY ID 失败 → 无 Generic PHY；与 **phy-handle  phandle 是否正确** 是不同层问题。

##### （4）板上验证

```bash
# fec2（eth0）节点上应有 pinctrl 属性
ls /proc/device-tree/soc/aips-bus@02100000/ethernet@020b4000/
xxd /proc/device-tree/soc/aips-bus@02100000/ethernet@020b4000/pinctrl-0

# 两颗 FEC 各一组 pinctrl-0（phandle 数量可能为 2）
ls /proc/device-tree/soc/aips-bus@02100000/ethernet@02188000/
```

#### Step 1.2 — `fsl,pins` 单行：`MX6UL_PAD_...  0x????` 如何理解（网卡）

> **6 cell 格式、宏名读法** 见 **`09` Step 1.1.2**；本节用本板 **三类典型行** 说明。

##### （1）RMII 数据线 — 普通 `0x1b0b0`

```dts
MX6UL_PAD_ENET1_RX_EN__ENET1_RX_EN  0x1b0b0
```

| 部分 | 含义 |
|------|------|
| `ENET1_RX_EN` | 物理 pad |
| `ENET1_RX_EN`（后者） | 复用到 ENET1 RMII RX_EN |
| `0x1b0b0` | PAD_CTL：驱动/上下拉/速度（RMII 常用，非 SION） |

`enet1grp` / `enet2grp` 中多数 RMII 数据/使能脚均为 **`0x1b0b0`**。

##### （2）RMII 参考时钟 — `TX_CLK` + `0x4001B009`（关键）

```dts
MX6UL_PAD_ENET1_TX_CLK__ENET1_REF_CLK1  0x4001B009
```

宏展开（`imx6ul-pinfunc.h`）：

```text
→ 0x00DC  mux_reg     → 物理 0x020E00DC
  0x0368  conf_reg    → 物理 0x020E0368
  0x0574  input_reg
  0x4     mux_mode    → ALT4 = ENET1_REF_CLK1（RMII 参考时钟）
  0x2     input_val
  0x4001B009  pad_config  ← dts 手写；高位 0x40000000 = IMX_PAD_SION
```

| 写什么 | 谁写 | 本板要点 |
|--------|------|----------|
| **PAD_CTL** `0x4001B009`（去 SION 后低位） | pinctrl `imx_pinconf_set` | 对齐 IMX6 ALPHA，非 EVK 默认 `0x4001b031` |
| **MUX + SION** | pinctrl `imx_pmx_set`（SION 并入 mux_mode） | 与 **`fec_probe` 里 `writel(0x14)`** 目标一致 |
| **MUX 再强写** | `fec_main.c` ① | `0x14` = mux_mode 4 \| SION bit |

详见 **Step 5**；**只改 dts 复位、不改此处与驱动 ①** 本板实测仍挂不上 PHY。

##### （3）fec2 独有 — MDIO 脚在 `enet2grp`

```dts
MX6UL_PAD_GPIO1_IO07__ENET2_MDC   0x1b0b0
MX6UL_PAD_GPIO1_IO06__ENET2_MDIO  0x1b0b0
```

| 含义 | 说明 |
|------|------|
| 物理 pad 名带 GPIO1_IO07/06 | 芯片 Ball 名；复用功能为 **ENET2_MDC/MDIO** |
| 为何在 fec2 group | `mdio` 子节点在 `&fec2` 下，`of_mdiobus_register` 由 **dev_id==0（fec2）** 执行 |
| 与 PHY `reg=<1>/<2>` | **无直接关系**：`reg` 是 MDIO 站号；pinctrl 管 **MAC 侧 MDIO 引脚** |

##### （4）PHY 复位脚 — SNVS + `0x79`

```dts
/* &iomuxc_snvs { imx6ul-evk { ... } } */
MX6ULL_PAD_SNVS_TAMPER7__GPIO5_IO07  0x79
```

与屏 `pinctrl_lcdif_reset` 同类：**SNVS 域 pad** + 复用 GPIO + `phy-reset-gpios = <&gpio5 7 ...>` 配合拉复位。

##### （5）enet1grp / enet2grp 脚位速查

**enet1grp（8 行）**

| fsl,pins 行 | RMII 信号 |
|-------------|-----------|
| ENET1_RX_EN / RX_ER / RDATA00/01 | 接收 |
| ENET1_TX_EN / TDATA00/01 | 发送 |
| ENET1_TX_CLK → REF_CLK1 | **参考时钟**（`0x4001B009`） |

**enet2grp（10 行）**

| 额外两行 | MDIO |
|----------|------|
| GPIO1_IO07 → ENET2_MDC | MDIO 时钟 |
| GPIO1_IO06 → ENET2_MDIO | MDIO 数据 |
| 其余同 fec1 结构 | RMII + TX_CLK `0x4001B009` |

##### （6）一句话速记（TX_CLK）

```text
MX6UL_PAD_ENET1_TX_CLK__ENET1_REF_CLK1  0x4001B009
│                                         │
│                                         └─ PAD 电气 + SION 相关（pinctrl）
└─ RMII REF_CLK：MUX @ 0x020E00DC；驱动再 writel(0x14) 双保险
```

### Step 2 — phandle：`phy-handle` ↔ mdio 子节点

板级现状（`6be237e` 之后）：

```dts
&fec1 {
	phy-mode = "rmii";
	phy-handle = <&ethphy0>;          /* → ethernet-phy@2，地址 2 = ENET1 */
	phy-reset-gpios = <&gpio5 7 GPIO_ACTIVE_LOW>;
	phy-reset-duration = <200>;
	/* ... pinctrl ... */
};

&fec2 {
	phy-mode = "rmii";
	phy-handle = <&ethphy1>;          /* → ethernet-phy@1，地址 1 = ENET2 */
	phy-reset-gpios = <&gpio5 8 GPIO_ACTIVE_LOW>;
	phy-reset-duration = <200>;

	mdio {
		ethphy0: ethernet-phy@2 {
			compatible = "ethernet-phy-ieee802.3-c22";
			reg = <2>;
		};
		ethphy1: ethernet-phy@1 {
			compatible = "ethernet-phy-ieee802.3-c22";
			reg = <1>;
		};
	};
};
```

| 字段 / 概念 | 含义 |
|-------------|------|
| `mdio { }` | 挂在 `&fec2` 下；`fec` 用 `of_get_child_by_name(..., "mdio")` 后调用 `of_mdiobus_register` |
| `ethphy0:` / `&ethphy0` | label → 编译成 **phandle**（与 `09` 里 `display0` 同机制），给 `phy-handle` 用 |
| `reg = <1>` / `<2>` | **PHY 硬件 MDIO 地址**（原理图拉脚），**不是** Linux `eth0`/`eth1` 编号 |
| `ieee802.3-c22` | 声明走 **Clause 22** 标准 MDIO；**不是**「必须匹配名为 SR8201F 的驱动」 |

#### `phy-handle = <&ethphy0>` 与 `ethphy0: ethernet-phy@2` 如何对应

这是 **dts 里的「定义 + 引用」**，和 C 里「先定义变量、别处用指针」类似；编译后变成 **phandle 数字**，内核用 **device_node 指针** 串起来。

**① dts 源码里三个名字，别混**

| 写法 | 是什么 | 例子 |
|------|--------|------|
| **`ethphy0:`** | **label（标签）**，给人写引用用的别名 | 标在 `ethernet-phy@2 {` 前面 |
| **`ethernet-phy@2`** | **节点名**；`@2` 习惯上与 `reg=<2>` 一致，但本质是节点标识 | 出现在 `/proc/device-tree/.../ethernet-phy@2/` |
| **`&ethphy0`** | **按 label 引用**该节点 | 写在 `phy-handle = <&ethphy0>` 里 |

```text
定义（在 mdio 下）                    引用（在 fec1 上）
─────────────────                    ─────────────────
ethphy0: ethernet-phy@2 { ... }  ←──  phy-handle = <&ethphy0>;
         ↑                                    ↑
      贴标签                              用标签指过去
```

**② dtc 编译后：label 消失，变成 phandle**

```text
形态 A（.dts 源码）
  ethphy0: ethernet-phy@2 { reg = <2>; phandle = <0x12>; ... };
  &fec1 { phy-handle = <&ethphy0>; };     → 编译为 phy-handle = <0x12>;

形态 B（.dtb 二进制块）
  ethernet-phy@2 节点带 phandle=0x12
  fec1 节点带 phy-handle 属性 = 0x12（u32）

形态 C（内核 unflatten 后）
  device_node「ethernet-phy@2」  ←── 指针 ──  fec1 里解析 phy-handle 得到
```

内核**不识别**字符串 `ethphy0`；只认编译后的 **phandle** 或展开后的 **device_node 指针**。

**③ 内核两条线：先「建 PHY 对象」，再「MAC 指过去」**

本板 `mdio { }` 挂在 **`&fec2` 下**，两路 PHY 子节点都在此；**fec1 的 `phy-handle` 仍可引用 `ethphy0`**——phandle 全 dtb 唯一，与节点物理挂载位置无关。

```text
时间线（简化）

fec2_probe（ENET2 / 通常 eth0）
  ├─ of_mdiobus_register(mdio)
  │     ├─ 子节点 ethernet-phy@2, reg=2 → get_phy_device → phy_map[2]
  │     │     phy->dev.of_node = 「ethernet-phy@2」节点
  │     └─ 子节点 ethernet-phy@1, reg=1 → phy_map[1]
  │           phy->dev.of_node = 「ethernet-phy@1」节点
  │
  └─ phy_node = of_parse_phandle(np, "phy-handle", 0)   // fec2 → ethphy1
        fep->phy_node = 「ethernet-phy@1」的 device_node

fec1_probe（ENET1 / 通常 eth1）
  └─ phy_node = of_parse_phandle(np, "phy-handle", 0)   // fec1 → ethphy0
        fep->phy_node = 「ethernet-phy@2」的 device_node

fec_enet_open（例如 eth1 = fec1 被 UP）
  └─ of_phy_connect(ndev, fep->phy_node, ...)
        └─ of_phy_find_device(phy_np)
              在 mdio 总线上找 dev->of_node == phy_np 的 phy_device
              → 找到 probe 阶段已建好的、of_node 指向 ethernet-phy@2 那颗
              → MAC 与 PHY 绑定，开始自协商
```

对应源码：

| 阶段 | 文件 | 函数 |
|------|------|------|
| 解析引用 | `fec_main.c` | `phy_node = of_parse_phandle(np, "phy-handle", 0);` → `fep->phy_node` |
| 建 phy_device | `of_mdio.c` | `of_mdiobus_register` → `phy->dev.of_node = child` |
| MAC 绑 PHY | `of_mdio.c` | `of_phy_connect` → `of_phy_find_device(phy_np)` → `phy_connect_direct` |
| open 时调用 | `fec_main.c` | `fec_enet_mii_probe` → `of_phy_connect(ndev, fep->phy_node, ...)` |

**④ 和 `reg=<2>` 的分工**

| | `phy-handle` / `&ethphy0` | `reg = <2>` |
|--|---------------------------|-------------|
| 作用 | **fec1 用哪颗 PHY 节点**（逻辑绑定） | **该节点对应 MDIO 站号几**（硬件访问） |
| 谁读 | `of_parse_phandle` / `of_phy_connect` | `of_mdiobus_register_phy` → `get_phy_device(bus, 2)` |
| 类比 | MAC 的「网线插到哪个 PHY 口」 | 该口在总线上的 **门牌号** |

`fec1` → `phy-handle=<&ethphy0>` → 节点 `ethernet-phy@2` → `reg=<2>` → MDIO 访问 **PA=2** 那颗 SR8201F（ENET1）。

**⑤ 为何 label 叫 ethphy0 而不是 ethphy2**

label **可随意命名**，与 `reg`、ENET 编号无强制关系；这里只是习惯把「给 ENET1 用的那颗」叫 `ethphy0`。  
重要的是 **`phy-handle` 引用的 label** 与 **`mdio` 下定义 label 的节点** 是同一个；`reg` 才必须和原理图 PHY 地址一致。

原理图对照（`04`）：ENET1 地址 **0x02** → `ethphy0` / `reg=<2>`；ENET2 地址 **0x01** → `ethphy1` / `reg=<1>`；MDIO 两路共用 GPIO1_IO06/07。

#### 设备树合并：dtsi + 板级 `&fec` 如何合成一棵树

**先澄清：合并发生在 `dtc` 编译时**，把多个 `.dts/.dtsi` **拼成一棵完整的树**，再输出一个 `.dtb`。  
内核启动时 **不再做 dts 合并**；U-Boot fixup 改的是已编好的 dtb 二进制（见 `09`），与这里说的 `#include` + `&label` 不是同一回事。

**① 你们网口相关的三层文件**

```text
imx6ull.dtsi                          ← SoC 芯片定义（NXP 官方）
    #include
imx6ull-14x14-evk-gengtao0901.dts     ← 板级：ALPHA 网口/屏/pinctrl
    #include（可选）
imx6ull-14x14-evk-emmc-gengtao0901-1024-600.dts  ← 变体：屏参等追加
```

| 层 | 网口相关内容 | 典型状态 |
|----|--------------|----------|
| **dtsi** | 定义 `fec1:` / `fec2:` 节点：`compatible`、`reg`、时钟、中断 | `status = "disabled"` |
| **板级 dts** | `&fec1 { ... }` / `&fec2 { ... mdio { ... } }` | 打开网口、绑 PHY、加复位 |
| **变体 dts** | 一般**不再拆** fec；屏参写在 `&lcdif` | 与网口链独立 |

**② `&fec1` 不是新建节点，是「补丁」**

SoC 里已有（`imx6ull.dtsi`）：

```dts
fec1: ethernet@02188000 {
    compatible = "fsl,imx6ul-fec", "fsl,imx6q-fec";
    reg = <0x02188000 0x4000>;
    /* clocks / interrupts ... */
    status = "disabled";
};
```

板级写：

```dts
&fec1 {
    phy-handle = <&ethphy0>;
    phy-mode = "rmii";
    status = "okay";          /* 覆盖 dtsi 里的 disabled */
    /* 新增 pinctrl / phy-reset-gpios 等 */
};
```

`dtc` 合并规则（概念）：

| 操作 | 结果 |
|------|------|
| 同名属性（如 `status`） | **后者覆盖前者** → `okay` |
| 板级新增属性 | **追加**到同一节点 → `phy-handle`、`mdio` 不出现两份 fec1 |
| 板级新增子节点 | **挂到**该节点下 → `&fec2` 下新增 `mdio { ... }` |

合并后 **仍然只有一个** `ethernet@02188000`，不会变成两个 fec1。

```text
                                      };

【合并后 · 一棵 dtb 树】

    compatible = "fsl,imx6ul-fec";

    status = "okay";                    ← 已覆盖
```

**④ 为何 `mdio` 写在 `fec2` 下？必须吗？能写别处吗？**

**内核硬约束：`mdio` 必须是某个 FEC 节点的直接子节点**

`fec_enet_mii_init()` 只在本 FEC 的 `of_node` 下查找 `"mdio"`：

```c
node = of_get_child_by_name(pdev->dev.of_node, "mdio");
if (node)
    of_mdiobus_register(fep->mii_bus, node);
else
    mdiobus_register(fep->mii_bus);
```

| 写法 | 行不行 |
|------|--------|
| `&fec2 { mdio { ethernet-phy@... }; }` | ✅ 标准（NXP EVK 同款） |
| `&fec1 { mdio { ... }; }` | ✅ 可以，须满足下面 probe 顺序 |
| 根 `/` 或其他节点下 | ❌ 驱动不会去那里找 |
| `fec1`、`fec2` 各写一份 `mdio` | ❌ 第二路只共享总线，不再解析自己的 mdio |

**双 FEC 共用一条 MDIO：总线只注册一次**

i.MX6ULL 两路 PHY 共用 MDC/MDIO；`fec_main.c` 中第二个 FEC（`dev_id > 0`）**复用**第一个的 `mii_bus`，不再读自己节点下的 `mdio`。

```text
先 probe 的 FEC（dev_id=0，常为 fec2@020b4000）
  → 分配 mii_bus → 读 本节点/mdio → of_mdiobus_register → phy_map[1/2]

后 probe 的 FEC（dev_id=1，常为 fec1@02188000）
  → 直接复用 fec0_mii_bus → 不读 fec1 下的 mdio（即使有）
```

因此 `mdio` 必须写在 **先 probe、负责注册总线的那颗 FEC** 下。EVK 放在 `&fec2`，因 **`fec2` 在典型启动下先于 `fec1` 完成 probe**（见下节分析）。

**④-b FEC probe / 注册顺序：怎么知道谁先谁后**

文档里「`020b4000` 通常先于 `02188000`」**不是猜的**，可由 **dtsi 节点顺序 + 驱动 dev_id + 板上 dmesg** 三条链互相印证。

**1. 驱动里的 `dev_id` 是什么**

`fec_probe()` 里（注意：与 dts 标签 `fec1`/`fec2` **不是同一个编号**）：

```c
static int dev_id;
...
fep->dev_id = dev_id++;    /* 每 probe 成功一颗 FEC 就 +1 */
...
netdev_info(ndev, "registered PHC device %d\n", fep->dev_id);
```

| 含义 | 说明 |
|------|------|
| `dev_id = 0` | **第一个** 进入 `fec_probe` 的 FEC |
| `dev_id = 1` | **第二个** probe 的 FEC |
| `fec_enet_mii_init` | 仅 `dev_id==0` 且本节点有 `mdio` 时 `of_mdiobus_register`；`dev_id>0` 复用 `fec0_mii_bus` |

**2. 设备树里 sibling 顺序：fec2 在 fec1 前面**

`imx6ull.dtsi` 同一父节点下（`aips2` 总线），**源码出现顺序**：

```text
... 其他节点 ...
fec2: ethernet@020b4000 { ... };    ← 约 dtsi 第 570 行
... 中间很多节点 ...
fec1: ethernet@02188000 { ... };    ← 约 dtsi 第 880 行
```

`dtc` 合并后，兄弟节点在 dtb / `device_node` 链表里的顺序 **一般保持这一顺序**（先 fec2，后 fec1）。  
`of_platform_populate()` → `for_each_child_of_node()` **按此顺序** 创建 `platform_device`；驱动已加载时，**创建后往往立刻 probe**，故 **多数情况下 fec2 先于 fec1**。

这与 **物理地址大小**（`0x020b4000` < `0x02188000`）在本例中一致，但顺序的**直接依据**是 **DT 兄弟节点链表顺序**，不是内核按地址排序。

**3. 板上 dmesg：实测印证（`06` 成功日志）**

```text
fec 20b4000.ethernet eth0: registered PHC device 0   ← fec2 先 probe，dev_id=0
fec 2188000.ethernet eth1: registered PHC device 1   ← fec1 后 probe，dev_id=1
```

| 日志字段 | 对应 |
|----------|------|
| `20b4000` | fec2 / ENET2 → 通常 **eth0** |
| `2188000` | fec1 / ENET1 → 通常 **eth1** |
| `PHC device 0/1` | 即 `fep->dev_id`，**probe 先后** |

因此：本板 **先 probe 的是 fec2** → `mdio` 写在 `&fec2` 下 → 第一个 probe 的 FEC 能读到 `mdio` → PHY 能注册。**与 EVK dts 布局一致，不是巧合。**

**4. 自己怎么验证 / 何时会反过来**

```bash
dmesg | grep -E 'fec 20b4000|fec 2188000|PHC device'
```

看 **`PHC device 0`** 对应哪个物理地址：

| 若 `PHC device 0` 是… | 则 `mdio` 应写在… |
|------------------------|-------------------|
| `20b4000`（fec2） | `&fec2`（当前做法）✅ |
| `2188000`（fec1） | 应改到 `&fec1`，否则可能扫不到 PHY |

**可能打乱顺序的情况**（较少见）：某路 `status=disabled` 只 probe 一颗；probe defer 延迟；改 dtsi 节点顺序。故文档用「**通常**」；**以板上 dmesg 为准最稳**。

**5. 小结：三条证据链**

```text
dtsi 顺序（fec2 在 fec1 前）
        ↓  of_platform_populate 按 sibling 顺序创建设备
fec_probe 调用顺序
        ↓  static dev_id++ 
dmesg: 20b4000 → PHC device 0，2188000 → PHC device 1
        ↓
mdio 放在先 probe 的 fec2 下 → of_mdiobus_register 成功
```

**`fec1` 的 `phy-handle` 为何仍能指 `fec2/mdio` 里的 `ethphy0`**

合并后是一整棵树；phandle **全局有效**，与父子路径无关。`fec1` 不必拥有 `mdio` 子节点。

```text
fec2_probe → fec2/mdio → 建 phy_map
fec1_probe → phy-handle → ethphy0 的 device_node
open       → of_phy_connect 绑到已建好的 phy_device
```

**⑤ 与「重复节点 / Duplicate name」**

若板级 **误写**成再声明一整棵 `fec1 { display... }` 式重复子树，或 `#include` 顺序不对导致同一属性冲突，可能编译告警或 `/proc/device-tree/` 里出现 `#1` 后缀。  
网口正确写法是：**dtsi 定义一次 + 板级 `&fec*` 补丁**；`mdio` 只出现一次。

**⑥ 和 overlay 工程的关系**

```text
源码合并（本文）          产物              启动时
──────────────          ────              ──────
dtsi + 板级 dts  ──dtc──►  .dtb  ──TFTP──►  内核 unflatten
                                              │
U-Boot fixup（可选）──────────────────────────┘ 改 bootargs 等字节
```

改网口：改 overlay 里板级 dts → 重编 dtb（+ 若改 fec 驱动则重编 zImage）。  
**不是**运行时再把两份 dts 合并。

#### mdio / ethernet-phy 与内核如何匹配（和 FEC 不同）

这段 **不是** platform 的「`compatible` 字符串对表」匹配（那是 Step 1 的 `fsl,imx6ul-fec`）。  
PHY 走的是：**按 MDIO 地址建设备 → 读芯片 ID → 再绑驱动**。

```text
① 注册 MDIO 总线 + 按 dts 建 phy_device
   fec_probe
     → mdiobus_alloc（读写函数 = fec 的 MDIO 寄存器访问）
     → of_mdiobus_register(mii_bus, mdio 节点)   // drivers/of/of_mdio.c
     → 遍历子节点，用 reg 得到 addr=1、addr=2

② 探测芯片 ID（真正「看见」PHY）
   compatible 是 ethernet-phy-ieee802.3-c22
   且没有 ethernet-phy-idAAAA.BBBB
     → of_mdiobus_register_phy() 走 get_phy_device(bus, addr)
     → 对地址 1/2 做 MDIO 读 ID 寄存器
     → 填 phy_device->phy_id，挂到 mii_bus->phy_map[addr]
     → phy->dev.of_node = 该 ethernet-phy 节点（供后面 of_phy_connect）

③ 绑 PHY 驱动（本板落到 Generic PHY）
   phy_device_register → 驱动模型按 phy_id 匹配
     → 没有专用驱动认这个 ID 时，回落到 genphy
     → 日志：Freescale FEC PHY driver [Generic PHY]
     → 用标准 BCR/BSR 做自协商 / 读链路（不必移植 MCU 的 SR8201F.c）
```

`of_mdiobus_register_phy()` 分支（概念）：

| dts `compatible` | 行为 |
|------------------|------|
| `ethernet-phy-ieee802.3-c45` | Clause 45 |
| `ethernet-phy-idAAAA.BBBB` | 直接用写死的 PHY ID，可不扫 |
| **`ethernet-phy-ieee802.3-c22`（本板）** | **`get_phy_device()`：靠 MDIO 读 ID** |

#### 和 FEC（MAC）匹配的对照

| | FEC（Step 1） | `ethernet-phy`（本段） |
|--|---------------|------------------------|
| 匹配键 | `compatible = "fsl,imx6ul-fec"` ↔ `fec_dt_ids[]` | 主要靠 **`reg` + MDIO 读 ID** |
| `compatible` 角色 | 决定调用哪个 platform 驱动 | `c22` 只定协议；芯片由 ID + Generic/专用驱动决定 |
| 何时完成 | `fec_probe` 注册 eth0/eth1 | open 时 `of_phy_connect(phy-handle)` 把 MAC 和已建好的 `phy_device` 连上（Step 4） |

要点：

- **不会**因为写了芯片名 `SR8201F` 才成功——dts 里根本没写芯片名。  
- **会**因为 `reg=<1>/<2>` 对、复位/时钟正常，MDIO 读到 ID，再落到 **Generic PHY**。  
- `phy-handle` 只负责「哪张网卡绑哪颗 PHY 节点」，**不负责**选驱动名。

成功日志怎么读：

```text
Freescale FEC PHY driver [Generic PHY] (mii_bus:phy_addr=20b4000.ethernet:01, ...)
                                                      ↑ MDIO 总线名        ↑ reg=1
```

`:01` / `:02` 对应 dts 的 `reg`；`Generic PHY` 就是上面第 ③ 步的回落驱动。

#### `reg = <1>` / `<2>` 详解：硬件、寄存器、内核三层面

**先澄清：`reg` 不是什么**

| 不是 | 是 |
|------|-----|
| SoC 外设物理基址（如 `0x020b4000`） | **MDIO 总线上的 PHY 站号（PHYAD）** |
| PHY 芯片内部某个寄存器编号 | 告诉 MAC「这次访问找总线上几号站」 |
| Linux `eth0` / `eth1` 编号 | 原理图拉脚决定的硬件地址 |

**① 硬件层面：两颗 PHY 共用一条 MDIO 总线**

底板两路 SR8201F 共用 **MDC / MDIO**（核心板 GPIO1_IO06 / GPIO1_IO07）。  
MAC 发 MDIO 帧时必须带「站号」，芯片只响应发给自己站号的访问。

| 板级 | 原理图 PHY 地址 | dts 节点 | `reg` |
|------|-----------------|----------|-------|
| ENET1（U14，fec1） | **0x02** | `ethernet-phy@2` | `<2>` |
| ENET2（U15，fec2） | **0x01** | `ethernet-phy@1` | `<1>` |

站号通常由 SR8201F 的 **PHYAD 引脚上下拉**在上电时锁死。  
`reg` 写错 → MAC 一直访问错误站号 → 读不到 ID → 挂不上 PHY。

Clause 22 规定站号为 **5 bit**，取值 **0～31**；本板用 1 和 2。

**② 寄存器层面：一次 MDIO 访问里有两个「地址」**

不要把下面两个概念混为一谈：

| 名称 | 含义 | 本板例子 |
|------|------|----------|
| **PA（PHY Address）** | MDIO 总线上**哪颗芯片** | 就是 dts 的 **`reg`** = 1 或 2 |
| **RA（Register Address）** | 该芯片**内部**哪个 MII 寄存器 | `MII_PHYSID1=0x02`、`MII_PHYSID2=0x03`、`BMCR=0x00`… |

FEC 把一次 MDIO 读写编码进 SoC 寄存器 **`FEC_MII_DATA`（MMFR）**：

```text
fec_enet_mdio_read(bus, mii_id, regnum)
        │
        ├─ mii_id  ← dts 的 reg（PA，站号 1 或 2）
        └─ regnum  ← PHY 内部寄存器号（RA，如读 ID 用 0x02/0x03）

writel(FEC_MMFR_ST | FEC_MMFR_OP_READ |
       FEC_MMFR_PA(mii_id) | FEC_MMFR_RA(regnum) |   // PA=reg, RA=内部寄存器
       FEC_MMFR_TA, fep->hwp + FEC_MII_DATA);
```

内核探测 PHY ID 时（`get_phy_id()`，`drivers/net/phy/phy_device.c`）：

```text
mdiobus_read(bus, addr=2, MII_PHYSID1)   // PA=2，读站号 2 的内部寄存器 0x02
mdiobus_read(bus, addr=2, MII_PHYSID2)   // PA=2，读站号 2 的内部寄存器 0x03
        ↓
拼成 phy_device->phy_id（用于后面选 Generic/专用驱动）
```

**注意数字巧合：** `reg=<2>` 里的 **2** 是 MDIO **站号 PA**；`MII_PHYSID1` 的内部寄存器号碰巧也是 **0x02**，但含义完全不同——一个是「找哪颗芯片」，一个是「读芯片里哪个寄存器」。

**③ 内核匹配层面：`reg` 在内核里怎么用**

```text
dts:  ethernet-phy@2 { reg = <2>; }
        ↓ of_mdio_parse_addr() 读 reg 属性
内核: addr = 2
        ↓ of_mdiobus_register_phy() → get_phy_device(bus, 2)
        ↓ mdiobus_read(bus, 2, PHYSID1/2)     ← FEC_MMFR_PA(2)
        ↓ phy_device_create() → phydev->addr = 2
        ↓ mii_bus->phy_map[2] = phydev
        ↓ dev_set_name(..., "...:02")           ← 日志 phy_addr=...:02
```

| 阶段 | `reg` 的作用 | 匹配什么 |
|------|--------------|----------|
| **建 phy_device** | 变成 `phydev->addr`，占 `phy_map[addr]` | **定位总线上哪颗 PHY** |
| **读 ID / 自协商** | 每次 MDIO 访问的 **PA 字段** | 访问该站号下的 BCR/BSR 等 |
| **绑 PHY 驱动** | 不直接参与 | 靠扫出的 **`phy_id`** → Generic PHY |
| **连 MAC** | `phy-handle` 指向节点；open 时 `of_phy_connect` | 找到已建好的 `phy_device`，之后仍用 `phydev->addr`（= `reg`）作 PA |

与 FEC（MAC）platform 匹配的对照：

| | `compatible = "fsl,imx6ul-fec"` | `reg = <1>/<2>` |
|--|--------------------------------|-----------------|
| 匹配对象 | 哪个 **platform 驱动**（fec） | 总线上 **哪颗 PHY** |
| 类比 | 驱动名对表 | **门牌号** |
| 写错后果 | 不出 eth0/eth1 | 扫错站号 → 无 Generic PHY → open 失败 |

**一句话：** `reg=<1>/<2>` = 该 SR8201F 在 MDIO 总线上的站号；内核把它写进 FEC `MII_DATA` 的 **PA** 字段选中芯片，并建 `phy_map[1/2]`；再用该站号去读芯片内部的 ID/BCR 等寄存器（**RA**），最终由读出的 **phy_id** 决定走 Generic PHY 还是专用驱动。

### Step 3 — PHY 复位链

**dts（L5，必要）**

| 项 | ENET1（fec1） | ENET2（fec2） |
|----|---------------|---------------|
| 复位 GPIO | GPIO5_IO07（SNVS_TAMPER7） | GPIO5_IO08（SNVS_TAMPER8） |
| 属性 | `phy-reset-gpios` + `phy-reset-duration = <200>` | 同左 |
| pinctrl 复位 MUX | `pinctrl_fec1_reset`（**Step 1.1**） | `pinctrl_fec2_reset` |
| pinctrl RMII | `pinctrl_enet1`（**Step 1.2**） | `pinctrl_enet2`（含 MDC/MDIO） |

**pinctrl 与复位链分工**：`pinctrl_fec*_reset` 把 pad mux 成 GPIO；`phy-reset-gpios` 由 `fec_reset_phy()` 拉低/拉高。缺任一侧 → 复位无效或 MDIO 不通。

**RMII / TX_CLK**：`pinctrl-0` 缺或 TX_CLK 配置错 → 无 Generic PHY；probe 内 `writel(0x14)` 须与 dts 一起改（**Step 5**，须重编 zImage）。

**为何关 `spi4`：** EVK 的 gpio-spi（74HC595）占用 GPIO5_IO07/08；ALPHA 上这两脚是 **PHYRSTB**，必须 `status = "disabled"`（与 IMX6 出厂 dts 一致）。

**驱动（`fec_reset_phy`）**

```text
of_get_named_gpio(..., "phy-reset-gpios")
  → 拉低（复位有效）
  → msleep(phy-reset-duration)   // dts 里 200ms
  → 拉高（释放复位）
  → msleep(150)                  // SR8201F 额外稳定时间（ALPHA / IMX6 补丁）
```

仅有 dts 复位、没有后面的 **150ms** 时，本板仍可能扫不到 PHY（见 Step 5 / `06` L6）。

```text
IP-Config / ifconfig up
        ↓
fec_enet_open()
        ↓
```

### Step 5 — TX_CLK / pad（为何「只改 dts 复位不够」）

> **pinctrl group 与 `fsl,pins` 单行语义** 见 **Step 1.1 / 1.2**、**§3.4.1**；本节聚焦 **TX_CLK 双保险** 与 **`writel(0x14)`**。

本板打通时：dts 复位 + 关 spi4 做完后，仍无 Generic PHY。最终还必须具备 **fec 板级适配**（对照 IMX6 出厂）：

| 项 | 位置 | 作用 |
|----|------|------|
| `ENET*_TX_CLK` pad `0x4001b031` → **`0x4001B009`** | 板级 dts `pinctrl_enet*` | RMII 参考时钟脚 **PAD 电气**（iomux） |
| probe 中 `writel(0x14)` | `fec_main.c`：`ioremap(0x020E00DC)` / `0x020E00FC` | 强制 ENET1/2 TX_CLK **MUX 功能** |
| 复位后再 `msleep(150)` | `fec_reset_phy` | SR8201F 出复位后稳定时间 |

这与「`compatible` 匹配」**并列**：匹配只保证驱动被叫起来；**电气与时序**不对，MDIO/链路仍起不来。

**必须重编 zImage**（不只更新 dtb），因为补丁在 `fec_main.c`。

#### `writel(0x14, 0x020E00DC)` 详解：RMII 参考时钟脚

**overlay 里的代码（`fec_probe` 开头）**

```c
/* ALPHA RMII: force ENET1/2 TX_CLK pad ctl (same as IMX6 vendor patch) */
void __iomem *enet1_tx_clk = ioremap(0x020E00DC, 4);
void __iomem *enet2_tx_clk = ioremap(0x020E00FC, 4);
writel(0x14, enet1_tx_clk);
writel(0x14, enet2_tx_clk);
```

| 部分 | 含义 |
|------|------|
| `0x020E00DC` / `0x020E00FC` | i.MX6ULL **IOMUXC** 里 `ENET1_TX_CLK` / `ENET2_TX_CLK` 的 **SW_MUX_CTL** 物理地址（`IOMUXC 基址 0x020E0000` + pinfunc 偏移 `0x00DC` / `0x00FC`） |
| `ioremap(..., 4)` | 把该物理地址映射成内核可写的 4 字节虚地址 |
| `writel(0x14, …)` | 往 **管脚复用（MUX）寄存器** 写入 `0x14`，不是写 FEC MAC 寄存器 |

**pinfunc 对照**（`arch/arm/boot/dts/imx6ul-pinfunc.h`）：

```text
MX6UL_PAD_ENET1_TX_CLK__ENET1_REF_CLK1
  mux_reg = 0x00DC   → 物理地址 0x020E0000 + 0x00DC = 0x020E00DC
  pad_reg = 0x0368   → 对应 dts 里 fsl,pins 第二个数（PAD 电气）
  mux_mode = 4       → alt4 = ENET*_REF_CLK（RMII 参考时钟）
```

**`0x14` 按位怎么读**（IOMUXC SW_MUX_CTL 常见布局）：

```text
0x14 = 0b0001_0100
         │    └── MUX_MODE = 4  → 选 ENET*_REF_CLK1（RMII 参考时钟功能）
         └─────── SION (bit4)   → Software Input On：时钟也回路到片内输入
```

RMII 模式下，这颗脚要当 **REF_CLK（25MHz 参考时钟）** 用；MAC 往往还要能「看见」这路时钟，所以需要 **mux=REF_CLK + SION**。  
出厂补丁在 `fec_probe` 里硬写 MUX 寄存器，避免 pinctrl 时序或 EVK 默认值不对。

#### 与 dts 里 `0x4001B009` 的关系（两套寄存器，常一起改）

| 配置 | 寄存器类型 | 谁写 | 本板值 |
|------|------------|------|--------|
| dts `MX6UL_PAD_ENET*_TX_CLK__ENET*_REF_CLK1  0x4001B009` | **PAD_CTL**（上下拉、驱动能力等；`0x40000000` 常含 SION 相关位） | pinctrl 子系统在 probe 早期 | 对齐 IMX6 出厂 ALPHA |
| `writel(0x14, 0x020E00DC)` | **MUX_CTL**（选 alt4=REF_CLK + SION） | `fec_probe` 开头再强写 | `0x14` |

原 NXP EVK dts 常用 **`0x4001b031`**；正点原子 ALPHA + SR8201F 改为 **`0x4001B009`**，并在驱动里再写 **`0x14`**。  
只改 dts 复位、不改这两处时，本板实测仍挂不上 Generic PHY（见 `06` L6）。

```text
RMII 参考时钟链（概念）
PHY 25MHz 晶振 → REF_CLK 脚 → SoC ENET*_TX_CLK pad
                              ↑ PAD_CTL（dts）+ MUX_CTL（writel 0x14）
                              ↓
                         FEC MAC / MDIO 能正常工作
```

#### 这段补丁从哪来（不是猜出来的）

| 证据 | 内容 |
|------|------|
| overlay 注释 | `same as IMX6 vendor patch` / `ALPHA RMII` |
| `origin/IMX6` 出厂 `fec_main.c` | 同样有 `ioremap(0x020E00DC)` + `writel(0x14)` |
| 排查命令（`05`） | `git diff ... origin/IMX6 -- drivers/net/ethernet/freescale/fec_main.c` |
| 提交 `6be237e` | 补丁纳入 overlay；板上才出现 Generic PHY + NFS |

结论：`0x14` / `0x020E00DC` 是 **正点原子针对 ALPHA 板 RMII + SR8201F 的已知工作配置**，来自对照出厂内核 diff，不是从零推导的魔术数。

### Step 6 — 接到 NFS

```text
bootargs（形态 B /chosen，见 09）
  root=/dev/nfs nfsroot=192.168.3.52:... 
  ip=192.168.3.51:192.168.3.52:...::eth0:off
        ↓
eth0 已 UP + Link Up
        ↓
IP-Config: Complete
Mounted root (nfs filesystem)
        ↓
login
```

- `ip=` / `nfsroot=` 来自 **bootargs 链**，不读 `fec` 节点属性。  
- 网口链没 ready → IP-Config 失败 → NFS 挂不上。  
- 本板验证：`eth0` Link 100M Full → NFS login → `ping 192.168.3.52` 通。

## 九、一句话

网口打通的设备树匹配，本质是：**`fsl,imx6ul-fec` 匹配出 MAC → `phy-handle`/`reg` 绑上 Generic PHY → `phy-reset-gpios` 做硬件复位**；本板还要叠加 **复位后 150ms + TX_CLK pad**，PHY 才能挂上，随后 `ip=...::eth0:` 才能完成 NFS 登录。
