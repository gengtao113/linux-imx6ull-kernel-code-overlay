## 一、一句话

Linux I2C 是 **两层总线、四类对象**：

```text
platform 总线：platform_device(i2c@021a0000)  ↔  platform_driver(i2c_imx)
                      ↓ probe 里「构造」
                 i2c_adapter（本板 i2c-0）+ i2c_algorithm（i2c_imx_xfer）

i2c 总线：     i2c_client(0-001e)             ↔  i2c_driver(ap3216c)
```

中间夹着 **`i2c-core.c`**：注册、匹配、`i2c_transfer`，把「设备驱动」和「控制器驱动」拆开。

## 二、图1：分层总览（用户空间 → 内核 → 硬件）

### 2.1 架构复述（按图）

```text
┌─────────────────────────── 用户空间 ───────────────────────────┐
│  应用程序（cat als / ioctl / i2cdetect）                        │
└───────────────────────────────┬────────────────────────────────┘
                                │ open / read / ioctl
┌─────────────────────────── 内核空间 ───────────────────────────┐
│                                                                │
│  【I2C 设备驱动层】                                             │
│     I2C 设备驱动 ──→ i2c_driver  ←匹配→  i2c_client            │
│     （本板：ap3216c.c）         （本板：0-001e，addr=0x1e）     │
│                                │                               │
│  ═══════════════════ I2C 核心（i2c-core.c）═══════════════════  │
│                                │ i2c_transfer                  │
│  【I2C 总线驱动层】                                             │
│     I2C 总线驱动 ──→ i2c_adapter ──→ i2c_algorithm             │
│     （本板：i2c-imx.c）  （i2c-0）     （.master_xfer）         │
│                                │                               │
│  ── 特定适配器硬件相关操作（读写 I2C 控制器寄存器）────────────  │
└───────────────────────────────┬────────────────────────────────┘
                                │ MMIO / IRQ
┌──────────────────────────── 硬件 ──────────────────────────────┐
│  I2C 适配器（SoC I2C1 @ 0x021a0000）                           │
│       ║ SCL/SDA                                                │
│  I2C 设备（AP3216C @ 0x1E 等从设备）                            │
└────────────────────────────────────────────────────────────────┘
```

### 2.2 图中对象 → 本板代码

| 图中概念 | 本板落点 | 文件 |
|----------|----------|------|
| I2C 设备驱动 | `ap3216c_driver` / `ap3216c_probe` | `drivers/char/ap3216c.c` |
| `i2c_client` | `0-001e`，`client->addr=0x1e` | 由 `i2c-core.c` 创建 |
| I2C 核心 | 匹配、`i2c_transfer`、注册适配器/驱动 | `drivers/i2c/i2c-core.c` |
| I2C 总线驱动 | `i2c_imx_driver` / `i2c_imx_probe` | `drivers/i2c/busses/i2c-imx.c` |
| `i2c_adapter` | 设备名 `i2c-0` | `i2c_imx_probe` 里填好再 `i2c_add_numbered_adapter` |
| `i2c_algorithm` | `i2c_imx_algo`，`.master_xfer = i2c_imx_xfer` | 同上 |
| 硬件相关操作 | `imx_i2c_write_reg` / `i2c_imx_write` / `read` | 同上 |

### 2.3 一次读数怎么穿过各层

```text
cat .../misc/ap3216c/als
  → show_als / ap3216c_read_als_data          【设备驱动层】
       → i2c_transfer(adapter, msg, …)        【I2C 核心】
            → adap->algo->master_xfer
                 → i2c_imx_xfer               【总线驱动 / algorithm】
                      → 写/读控制器寄存器      【硬件相关操作】
                           → SCL/SDA → 芯片   【硬件】
```

## 三、图2：双总线（platform + i2c）

图2 的关键信息：**控制器不直接挂在 i2c 总线上**，而是先走 **platform 总线**；probe 成功后才「构造」出 `i2c_adapter`，再挂到 **i2c 总线**一侧。

### 3.1 架构复述（按图，换成本板名字）

```text
应用层：  /dev/ap3216c（misc）          /dev/i2c-0（可选，i2c-dev）
                │                              │
                ▼                              ▼
内核：   i2c_driver(ap3216c)            i2c-dev 通用接口
                \                            /
                 \______ i2c bus ___________/
                        │         │
                   i2c_client   i2c_client …
                   (0-001e)
                        │
                   i2c_core.c
                        │
                   i2c_adapter 对象 (i2c-0)
                        ▲
                        │ 构造（probe 里）
         platform bus ──┤
              │         │
    platform_driver     platform_device
    (i2c_imx_driver)    (i2c@021a0000)   ← of_platform_populate 建出
              │
硬件：   i2c 控制器 ════ SCL/SDA ════ i2c 设备（AP3216C）
```

图中的 platform 侧总线驱动 → 本板就是 **`i2c_imx_driver`**。  
图中的 `i2c_board_info` → 本板主要用 **设备树子节点**（`ap3216c@1e`），经 `of_i2c_register_device` 填成 `i2c_board_info` 再 `i2c_new_device`（见 `13`）。

### 3.2 左半：platform 侧如何「构造」适配器

```text
① of_platform_populate（设备先到，详见 [§3.4](#34-of_platform_populate--platform_devicei2c021a0000-详解)）
   dtb → device_node i2c@021a0000
   → platform_device 挂到 platform 总线
   （详见下文 3.4）

② platform_driver_register(&i2c_imx_driver)（驱动后到）
   → platform_match（OF：fsl,imx21-i2c）
   → i2c_imx_probe
        ├─ 填 i2c_adapter（algo、of_node、nr…）
        └─ i2c_add_numbered_adapter → 注册进 i2c 核心
             → 出现 /sys/.../i2c-0，并 of_i2c_register_devices
```

对应代码骨架：

```c
/* mach-imx6ul.c：设备侧 */
of_platform_populate(NULL, of_default_bus_match_table, NULL, NULL);

/* i2c-imx.c：驱动侧 */
platform_driver_register(&i2c_imx_driver);
/* probe 内： */
i2c_imx->adapter.algo = &i2c_imx_algo;          /* .master_xfer = i2c_imx_xfer */
i2c_imx->adapter.dev.of_node = pdev->dev.of_node;
i2c_add_numbered_adapter(&i2c_imx->adapter);    /* 「构造」完成并登记 */
```

### 3.3 右半：i2c 侧 client ↔ driver

```text
of_i2c_register_devices(adap)
  → 遍历 &i2c1 下 available 子节点
  → i2c_new_device → i2c_client(0-001e) 挂到 i2c 总线

module_i2c_driver(ap3216c_driver)
  → i2c_add_driver → i2c_register_driver
  → i2c_device_match（OF：LiteOn,ap3216c）
  → ap3216c_probe
```

| 图2 元素 | 本板 |
|----------|------|
| platform bus 上的控制器驱动 | `i2c_imx_driver` |
| 构造出的 `i2c_adapter` | `i2c-0` |
| i2c bus 上的 `i2c_client` | `0-001e` |
| i2c bus 上的 `i2c_driver` | `ap3216c` |
| 应用节点 | `/dev/ap3216c`（misc，**不是**必须走 i2c-dev） |
| i2c-dev / major 89 | `/dev/i2c-0`，给 `i2cdetect` 等通用工具 |

### 3.4 `of_platform_populate` → `platform_device(i2c@021a0000)` 详解

> 图2 左侧「设备从哪来」：本板**不手写** `platform_device_register`，而是由 **dtb → OF 设备树 → populate** 在内核启动早期自动实例化 `platform_device`，再与 `i2c_imx_driver` 在 platform 总线上匹配。

#### 3.4.1 启动时机：从 dtb 到 `imx6ul_init_machine`

```text
U-Boot 把 dtb 传给内核
  → setup_arch()
       └─ unflatten_device_tree()        ← dtb 展开为内存中的 device_node 树
            · 此时只有 OF 节点，尚无 platform_device / i2c_adapter
  → start_kernel() …
  → arch_initcall 阶段
       └─ customize_machine()            ← DT_MACHINE_START 注册
            └─ imx6ul_init_machine()     arch/arm/mach-imx/mach-imx6ul.c
```

`imx6ul_init_machine` 中与 populate 直接相关的代码（169～177 行）：

```c
static void __init imx6ul_init_machine(void)
{
    struct device *parent;

    parent = imx_soc_device_init();
    if (parent == NULL)
        pr_warn("failed to initialize soc device\n");

    of_platform_populate(NULL, of_default_bus_match_table, NULL, NULL);
    imx6ul_enet_init();
    ...
}
```

| 参数 | 本板含义 |
|------|----------|
| `root = NULL` | 从设备树根 `/` 开始遍历 |
| `matches = of_default_bus_match_table` | 只对 **simple-bus / simple-mfd** 类节点递归子节点 |
| `lookup = NULL` | 不用 auxdata 表 |
| `parent = NULL` | 顶层 pdev 挂在 platform 总线根上 |

**时序要点**：`of_platform_populate` 在 **`i2c_imx_driver` 注册之前**执行（`init_machine` 很早；`i2c_imx` 在 `subsys_initcall` 才 `platform_driver_register`）。因此是 **设备（pdev）先到，驱动后到**——与图2 左半一致。

#### 3.4.2 dts 节点树：populate 如何「看见」`i2c@021a0000`

本板相关节点（`imx6ull.dtsi` + 板级 `&i2c1` 覆盖）：

```dts
/* imx6ull.dtsi */
/ {
    aliases {
        i2c0 = &i2c1;    /* SoC I2C1 → Linux 适配器编号 0 → i2c-0 */
        i2c1 = &i2c2;
        ...
    };
    soc {
        aips-bus@02100000 {
            compatible = "fsl,imx-aips-bus", "simple-bus";   /* ← 命中总线表 */
            ...
            i2c1: i2c@021a0000 {
                compatible = "fsl,imx6ul-i2c", "fsl,imx21-i2c";
                reg = <0x021a0000 0x4000>;
                interrupts = <GIC_SPI 36 IRQ_TYPE_LEVEL_HIGH>;
                clocks = <&clks IMX6UL_CLK_I2C1>;
                status = "disabled";          /* 板级 &i2c1 改为 okay */
            };
        };
    };
};

/* imx6ull-14x14-evk-gengtao0901.dts */
&i2c1 {
    clock-frequency = <100000>;
    pinctrl-0 = <&pinctrl_i2c1>;
    status = "okay";
    ap3216c@1e { compatible = "LiteOn,ap3216c", "ap3216c"; reg = <0x1e>; };
};
```

populate 递归路径（与 `of_default_bus_match_table` 配合）：

```text
/  （根，不直接建 pdev）
 └─ soc
      └─ aips-bus@02100000
           compatible 含 "simple-bus"  → of_match_node(matches) 命中
           │
           ├─ of_platform_device_create_pdata(aips-bus)  → 建 aips-bus pdev（总线壳）
           └─ for_each_child 递归：
                ├─ uart@... / gpio@... / …  → 各自建 platform_device
                └─ i2c@021a0000
                     compatible = "fsl,imx6ul-i2c", "fsl,imx21-i2c"
                     status = okay（板级覆盖后）
                     → of_platform_device_create_pdata  → **本板目标 pdev**
                     │
                     for_each_child:
                       ap3216c@1e  → **不匹配 simple-bus，不递归**
                                    → **不会**建成 platform_device
```

| 节点 | `of_device_is_available` | populate 结果 |
|------|--------------------------|---------------|
| `aips-bus@02100000` | okay | `platform_device`（总线容器） |
| `i2c@021a0000` | okay（`&i2c1` 覆盖） | **`platform_device(i2c@021a0000)`** |
| `mag3110@0e` | disabled | 跳过 |
| `ap3216c@1e` | okay | **不建 pdev**；留给 `of_i2c_register_devices` |

#### 3.4.3 核心函数走读：`of_platform_populate` → `of_platform_bus_create`

**入口**（`drivers/of/platform.c` 435～456 行）：

```c
int of_platform_populate(struct device_node *root, ...)
{
    root = root ? of_node_get(root) : of_find_node_by_path("/");

    for_each_child_of_node(root, child)
        of_platform_bus_create(child, matches, lookup, parent, true);
    ...
}
```

对 `/` 的每个一级子节点（如 `soc`）调用 `of_platform_bus_create`，`strict=true` 表示**无 `compatible` 的节点直接跳过**。

**`of_platform_bus_create`**（327～375 行）对每个 bus 节点：

```text
of_platform_bus_create(bus_node, matches, ...)
  │
  ├─ 1) of_platform_device_create_pdata(bus_node, ...)   ← 先为当前节点建 pdev
  │        · of_device_is_available?  （status != disabled）
  │        · OF_POPULATED 未置位?      （防重复注册）
  │        · of_device_alloc
  │        · of_device_add
  │
  ├─ 2) of_match_node(matches, bus_node)?
  │        · aips-bus: "simple-bus" → 命中 → 继续
  │        · i2c@021a0000: "fsl,imx6ul-i2c" → **不命中** → return 0，**不递归子节点**
  │
  └─ 3) for_each_child_of_node → 对子节点递归 of_platform_bus_create
```

因此 **`i2c@021a0000` 自身会建成 platform_device**，但其子节点 `ap3216c@1e` **不会**在 populate 阶段处理——这是 I2C 子系统与 platform 子系统的职责分界。

#### 3.4.4 `of_device_alloc`：从 dts 填 `platform_device` + `resource`

`of_device_alloc`（`platform.c` 105～149 行）为 `i2c@021a0000` 分配并初始化：

```text
of_device_alloc(np=i2c@021a0000, ...)
  ├─ platform_device_alloc("", -1)
  ├─ 遍历 reg → of_address_to_resource
  │     reg = <0x021a0000 0x4000>
  │     → resource[0]: start=0x021a0000, size=0x4000, IORESOURCE_MEM
  ├─ of_irq_count / of_irq_to_resource_table
  │     → resource[1]: GIC_SPI 36, IORESOURCE_IRQ
  ├─ dev->of_node = np              ← 保留 OF 节点（后续 match / pinctrl / of_i2c 都靠它）
  ├─ dev->parent = parent pdev      ← 父设备为 aips-bus pdev
  └─ of_device_make_bus_id(dev)
        → dev_set_name("021a0000.i2c")   /* 典型 OF 设备名 */
```

| `platform_device` 字段 | 本板 `i2c@021a0000` 来源 |
|------------------------|--------------------------|
| `dev.of_node` | dts 节点指针 |
| `dev.name` | `021a0000.i2c`（由 reg 地址 + 节点名生成） |
| `resource[0]` | MMIO `0x021a0000`，长度 `0x4000` |
| `resource[1]` | IRQ 36 |
| `num_resources` | 2 |

`i2c_imx_probe` 里通过 `platform_get_resource(pdev, IORESOURCE_MEM, 0)` 和 `platform_get_irq(pdev, 0)` 取回的，就是这里填好的 resource。

#### 3.4.5 `of_device_add`：挂入 platform 总线

```c
// drivers/of/device.c 54～69 行
int of_device_add(struct platform_device *ofdev)
{
    ofdev->name = dev_name(&ofdev->dev);   // "021a0000.i2c"
    ofdev->id = -1;                        // OF 设备默认 id=-1

    return device_add(&ofdev->dev);       // 进入驱动模型
}
```

`device_add` 链（与 `14` §4.1.1 的 i2c dev 链类似，但总线是 **platform**）：

```text
device_add(&pdev->dev)
  ├─ bus_add_device          → pdev 入 platform_bus_type 的 dev 链
  └─ bus_probe_device
        └─ device_attach
              └─ bus_for_each_drv → platform_match
                    · 此时 i2c_imx 驱动通常尚未注册 → 暂无 probe
                    · pdev 已存在，等 subsys_initcall 注册驱动后再 bind
```

此时 sysfs 可出现 `/sys/devices/platform/021a0000.i2c/`，但 **I2C 适配器 `i2c-0` 尚未创建**（要等 `i2c_imx_probe`）。

#### 3.4.6 驱动注册与 platform 匹配 → `i2c_imx_probe`

`i2c_imx` 模块初始化（`i2c-imx.c` 1131～1135 行）：

```c
static int __init i2c_adap_imx_init(void)
{
    return platform_driver_register(&i2c_imx_driver);
}
subsys_initcall(i2c_adap_imx_init);
```

`i2c_imx_driver` 的 OF 匹配表：

```c
static const struct of_device_id i2c_imx_dt_ids[] = {
    { .compatible = "fsl,imx1-i2c", .data = &imx1_i2c_hwdata },
    { .compatible = "fsl,imx21-i2c", .data = &imx21_i2c_hwdata },  /* ← 第二项命中 */
    { .compatible = "fsl,vf610-i2c", .data = &vf610_i2c_hwdata },
    { }
};
```

`platform_driver_register` → `bus_add_driver` → **`driver_attach`** 扫已有 pdev：

```text
driver_attach(i2c_imx_driver)
  └─ bus_for_each_dev(platform_bus, ..., __driver_attach)
        └─ pdev = 021a0000.i2c
              platform_match(dev, i2c_imx_driver)
                ├─ of_driver_match_device
                │     pdev->of_node compatible:
                │       "fsl,imx6ul-i2c", "fsl,imx21-i2c"
                │     与 i2c_imx_dt_ids 第二项 "fsl,imx21-i2c" 命中 ✓
                └─ really_probe → platform_drv_probe → i2c_imx_probe(pdev)
```

**`i2c_imx_probe` 如何把 pdev「变成」`i2c_adapter`**（与本节衔接 §4.1.1 / `15` §7.1）：

```text
i2c_imx_probe(pdev)          /* pdev->dev.of_node 仍指向 i2c@021a0000 */
  ├─ of_match_device(i2c_imx_dt_ids) → imx21_i2c_hwdata
  ├─ ioremap(0x021a0000) / clk / request_irq(i2c_imx_isr)
  ├─ adapter.algo = &i2c_imx_algo
  ├─ adapter.dev.of_node = pdev->dev.of_node   ← 关键：后续 of_i2c_register_devices 遍历子节点
  ├─ adapter.nr = pdev->id  (= -1)
  └─ i2c_add_numbered_adapter(&adapter)
        · nr==-1 → i2c_add_adapter
        · of_alias_get_id(of_node, "i2c") → aliases i2c0=&i2c1 → 返回 0
        · adapter.nr = 0 → 设备名 i2c-0
        · i2c_register_adapter → of_i2c_register_devices → 建 0-001e
```

| 阶段 | 对象 | 总线 | 本板实例 |
|------|------|------|----------|
| populate 后 | `platform_device` | platform | `021a0000.i2c` |
| `i2c_imx_probe` 后 | `i2c_adapter` | i2c | `i2c-0` |
| `of_i2c_register_devices` 后 | `i2c_client` | i2c | `0-001e` |

## 四、图3：注册对称（adapter ↔ driver）

图3 强调：`i2c_bus_type` 上有 **dev 链** 和 **drv 链**；**先注册哪边都可以**，另一边后到时再互相匹配。

### 4.1 架构复述（按图）

```text
                    Bus (i2c_bus_type)
                   /                  \
            dev 链表                    Drv 链表
         (adapter 等)                (i2c_driver 等)
              ▲                            ▲
              │                            │
     i2c_add_adapter                i2c_add_driver
              │                            │
   【总线驱动程序】                  【设备驱动程序】
   分配 i2c_adapter                  分配 i2c_driver
   设置 algo.master_xfer             设置 .probe / match 表
   注册                              注册
```

任一端注册成功后，都会去「另一侧链表」里找机会绑定；成功则得到（或绑定）**`i2c_client`**（含 `.addr` / `.adapter` / `.driver`）。

### 4.1.1 dev 链表与 Drv 链表：代码实现

图3 的「dev 链 / Drv 链」在本树 **4.1.15** 由驱动模型维护：挂在 `i2c_bus_type` 的私有结构 `subsys_private` 上（`drivers/base/bus.c`），不是 `i2c-core.c` 里单独维护的 adapters/drivers 表。

#### ① 链表挂在哪、节点是什么

```text
struct bus_type i2c_bus_type                    drivers/base/bus.c
        │                                     bus_register()
        ▼
  i2c_bus_type.p  ──►  struct subsys_private
                              │
              ┌───────────────┴────────────────┐
              │                                │
    klist_devices                    klist_drivers
    （dev 链表，图3 左）              （Drv 链表，图3 右）
              │                                │
    每个 struct device 的              每个 struct device_driver 的
    dev->p->knode_bus                  drv->p->knode_bus
```

| 链表 | 内核变量 | 入链函数 | 节点字段 | 链上成员 |
|------|----------|----------|----------|----------|
| **dev 链** | `i2c_bus_type.p->klist_devices` | `bus_add_device()` | `dev->p->knode_bus` | **所有** `dev.bus = &i2c_bus_type` 的 `struct device` |
| **Drv 链** | `i2c_bus_type.p->klist_drivers` | `bus_add_driver()` | `drv->p->knode_bus` | **所有** `drv->bus = &i2c_bus_type` 的 `struct device_driver` |

**要点**：dev 链上**同时有 adapter 和 client**，靠 `dev->type` 区分，不是两条独立链表：

```text
klist_devices（i2c 总线 dev 链，示意）
  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
  │ i2c-0        │───►│ 0-001e       │───►│ 0-00xx ...   │───► ...
  │ type=adapter │    │ type=client  │    │ type=client  │
  │ 无 driver    │    │ driver=ap3216c│   │              │
  └──────────────┘    └──────────────┘    └──────────────┘

klist_drivers（i2c 总线 Drv 链，示意）
  ┌──────────────┐    ┌──────────────┐
  │ ap3216c      │───►│ 其他 i2c_drv │───► ...
  └──────────────┘    └──────────────┘
```

- **adapter** 入链：`i2c_register_adapter` → `device_register(&adap->dev)` → `bus_add_device`（`adap->dev.type = &i2c_adapter_type`）
- **client** 入链：`of_i2c_register_device` → `i2c_new_device` → `device_register(&client->dev)` → `bus_add_device`（`client->dev.type = &i2c_client_type`）
- **driver** 入链：`i2c_register_driver` → `driver_register` → `bus_add_driver`

#### ② 入链与「扫对方链」的完整路径

**A. adapter 侧（左）—— `i2c_register_adapter`**

            │

**B. driver 侧（右）—— `i2c_register_driver`**

#### ③ client 生成与匹配（本板 AP3216C）

> **先分清两件事**：`i2c_device_match` **不负责生成** client，只负责把**已存在的** `i2c_client` 与 `i2c_driver` 配对。  
> client 的生成发生在上一节 ②-A 的 `of_i2c_register_devices` 路径；生成后 `device_register` 会立刻尝试 match。

##### ③-A 生成 client：dts → `struct i2c_client` → `0-001e`

**触发点**：`i2c_register_adapter` 在 `i2c-0` 入 dev 链之后调用 `of_i2c_register_devices(adap)`（`i2c-core.c` 1460 行）。

**前提**：`i2c_imx_probe` 里已设置 `adapter.dev.of_node = pdev->dev.of_node`，指向 dts 节点 `i2c@021a0000`（即 `&i2c1`）。没有 `of_node`，`of_i2c_register_devices` 直接 return，不会建任何 client。

**遍历子节点**：

```c
// i2c-core.c
static void of_i2c_register_devices(struct i2c_adapter *adap)
{
    if (!adap->dev.of_node)
        return;

    for_each_available_child_of_node(adap->dev.of_node, node)
        of_i2c_register_device(adap, node);
}
```

本板 `&i2c1` 下：`mag3110@0e` 因 `status = "disabled"` **被跳过**；`ap3216c@1e` 为 available，进入 `of_i2c_register_device`。

**解析 dts 并填 `i2c_board_info`**（`i2c-core.c` 1257～1294 行）：

```text
of_i2c_register_device(adap, ap3216c@1e)
  │
  ├─ of_modalias_node(node, info.type, ...)
  │     dts: compatible = "LiteOn,ap3216c", "ap3216c"
  │     → 取第一项，去厂商前缀 → info.type = "ap3216c"
  │
  ├─ of_get_property(node, "reg") → info.addr = 0x1e
  ├─ info.of_node = of_node_get(node)    // 保留 OF 节点指针
  └─ i2c_new_device(adap, &info)
```

**`i2c_new_device` 构造 client 对象**（`i2c-core.c` 937～987 行）：

| 字段 / 动作 | 代码赋值 | 本板 AP3216C 结果 |
|-------------|----------|-------------------|
| `client->adapter` | `= adap` | 绑到 `i2c-0` |
| `client->addr` | `= info.addr` | `0x1e` |
| `client->name` | `strlcpy(..., info.type, ...)` | `"ap3216c"` |
| `client->dev.parent` | `= &adap->dev` | sysfs 父设备 `i2c-0` |
| `client->dev.bus` | `= &i2c_bus_type` | 挂 i2c 总线 |
| `client->dev.type` | `= &i2c_client_type` | 标记为 client（非 adapter） |
| `client->dev.of_node` | `= info.of_node` | 指向 `ap3216c@1e` |
| 设备名 | `i2c_dev_set_name(adap, client)` | **`"0-001e"`**（`nr=0`，`addr=0x1e`） |

`i2c_dev_set_name` 实现（`i2c-core.c` 905～918 行）：

```c
dev_set_name(&client->dev, "%d-%04x", i2c_adapter_id(adap), client->addr);
// → "0-001e"
```

**注册进驱动模型**：

```text
i2c_new_device
  └─ device_register(&client->dev)          drivers/base/core.c
        ├─ bus_add_device(dev)
        │     └─ klist_add_tail → 0-001e 入 klist_devices（dev 链）
        └─ bus_probe_device(dev)
              └─ device_attach(dev)
                    └─ bus_for_each_drv → i2c_device_match   ← 进入 ③-B
                         · 若 ap3216c 驱动尚未加载 → 无匹配，client 暂存
                         · 若驱动已在 Drv 链 → 当场 match + probe
```

生成完成时，`struct i2c_client` 已存在且挂在总线上，但 **`client->driver` 可能仍为空**（驱动未加载或尚未 match）。

##### ③-B 匹配：`i2c_device_match` 完整逻辑

当 `device_attach` 或 `driver_attach` 遍历对端链表时，驱动核心调用：

```c
driver_match_device(drv, dev)   // drivers/base/base.h
  → drv->bus->match(dev, drv)
  → i2c_bus_type.match = i2c_device_match
```

`i2c_device_match` 完整实现（`i2c-core.c` 457～479 行）：

```c
static int i2c_device_match(struct device *dev, struct device_driver *drv)
{
    struct i2c_client *client = i2c_verify_client(dev);
    struct i2c_driver *driver;

    if (!client)
        return 0;

    /* Attempt an OF style match */
    if (of_driver_match_device(dev, drv))
        return 1;

    /* Then ACPI style match */
    if (acpi_driver_match_device(dev, drv))
        return 1;

    driver = to_i2c_driver(drv);
    if (driver->id_table)
        return i2c_match_id(driver->id_table, client) != NULL;

    return 0;
}
```

**第一步：`i2c_verify_client` — 过滤 dev 链上的非 client**

```c
// i2c-core.c 761～765 行
struct i2c_client *i2c_verify_client(struct device *dev)
{
    return (dev->type == &i2c_client_type)
            ? to_i2c_client(dev) : NULL;
}
```

| dev 链上的设备 | `dev->type` | `i2c_verify_client` | 能否与 ap3216c 驱动匹配 |
|----------------|-------------|----------------------|-------------------------|
| `i2c-0` | `i2c_adapter_type` | `NULL` → return 0 | 否（adapter 跳过） |
| `0-001e` | `i2c_client_type` | 返回 `client` | 继续往下匹配 |

这就是为什么 `driver_attach` 扫 dev 链时会**跳过 `i2c-0`**，只对 `0-001e` 尝试绑定。

**第二步：OF 匹配（本板主路径）**

```text
of_driver_match_device(dev, drv)
  → of_match_device(drv->of_match_table, dev->of_node)
       client->dev.of_node 的 compatible:
         "LiteOn,ap3216c", "ap3216c"
       ap3216c_driver.driver.of_match_table:
         { .compatible = "LiteOn,ap3216c" }
       → 第一项 compatible 命中 → return 1
```

dts 与驱动表对应关系：

| 来源 | 内容 |
|------|------|
| dts `ap3216c@1e` | `compatible = "LiteOn,ap3216c", "ap3216c"` |
| `ap3216c.c` | `ap3216c_of_match[] = { { .compatible = "LiteOn,ap3216c" } }` |
| `ap3216c_driver` | `.driver.of_match_table = ap3216c_of_match` |

**第三步：ACPI 匹配** — 本板无 ACPI I2C 设备，跳过。

**第四步：`id_table` 匹配（兜底）**

```c
// i2c-core.c 446～454 行
static const struct i2c_device_id *i2c_match_id(...)
{
    while (id->name[0]) {
        if (strcmp(client->name, id->name) == 0)
            return id;
        id++;
    }
    return NULL;
}
```

本板：`client->name` 由 `of_modalias_node` 生成为 `"ap3216c"`，与 `ap3216c_id[] = { { "ap3216c", 0 } }` 一致。  
无 OF 的板子可走此路径；本板通常已在第二步 OF 匹配成功。

**本板一次匹配的判定链**：

```text
driver_attach(ap3216c) 扫到 dev = 0-001e
  → i2c_device_match(0-001e, ap3216c)
       ├─ i2c_verify_client → client ✓
       ├─ of_driver_match_device
       │     "LiteOn,ap3216c" == "LiteOn,ap3216c" → return 1  ✓
       └─ （不再走 id_table）
  → driver_probe_device → really_probe
```

##### ③-C 匹配成功后：`i2c_device_probe` → `ap3216c_probe`

`really_probe` 里调用 `dev->bus->probe(dev)`，即 `i2c_bus_type.probe = i2c_device_probe`（`i2c-core.c` 626～668 行）：

```text
i2c_device_probe(dev)
  ├─ client = i2c_verify_client(dev)         // 再次确认为 client
  ├─ of_irq_get(of_node) → client->irq      // 本板 ap3216c 无 interrupt 属性 → irq=0
  ├─ 检查 driver->probe && driver->id_table  // 4.1 要求 id_table 非空
  ├─ of_clk_set_defaults(of_node)
  └─ driver->probe(client, i2c_match_id(id_table, client))
         │
         └─ ap3216c_probe(client, id)       // ap3216c.c
               ├─ ap3216c_init → write_reg 0x00=0x04/0x03
               └─ misc_register → /dev/ap3216c
```

`i2c_match_id` 在 probe 时再次用 `client->name`（`"ap3216c"`）查 `id_table`，把匹配的 `id` 指针传给 `ap3216c_probe` 的第二个参数。

**生成 → 匹配 → probe 一图串起来**：

```text
dts ap3216c@1e
    │
    ▼ ③-A 生成
of_i2c_register_device → i2c_new_device → device_register
    │                                        │
    │                              0-001e 入 dev 链
    │                                        │
    ▼ ③-B 匹配 ◄─────────────────────────────┘
    │         device_attach / driver_attach
    │              → i2c_device_match
    │                   of_driver_match_device("LiteOn,ap3216c")
    ▼ ③-C probe
really_probe → i2c_device_probe → ap3216c_probe
    │
    ▼
/dev/ap3216c  +  client->driver = ap3216c
```

因此：**匹配只发生在 client ↔ i2c_driver 之间**；adapter 虽在 dev 链上，但 `i2c_verify_client` 会将其过滤掉。

#### ④ 本板 AP3216C 时序（链上先后）

```text
时刻 T1  i2c_imx_probe 完成 i2c_register_adapter
         dev 链:  [ i2c-0 ]
         Drv 链:  [ ]                    （ap3216c 模块可能尚未 insmod）

时刻 T2  of_i2c_register_devices 建 client
         dev 链:  [ i2c-0 ] → [ 0-001e ]
         device_attach：Drv 链为空 → 0-001e 暂无人 bind

时刻 T3  insmod ap3216c → i2c_register_driver
         Drv 链:  [ ap3216c ]
         driver_attach 扫 dev 链 → 跳过 i2c-0 → 匹配 0-001e → ap3216c_probe

         （若 T3 早于 T2：ap3216c 先上 Drv 链，T2 时 device_attach 即可当场 bind）
```

### 4.2 本板：总线驱动侧（左）

```text
i2c_imx_probe
  ① 分配/使用内嵌的 i2c_adapter（在 imx_i2c_struct 里）
  ② adapter.algo = &i2c_imx_algo
        .master_xfer = i2c_imx_xfer
  ③ i2c_add_numbered_adapter(&adapter)
       → i2c_register_adapter
            · 适配器登记（出现 i2c-0）
            · of_i2c_register_devices  ← 按 dts 建 client（本板主路径）
            · 通知已有 i2c_driver 做匹配
```

### 4.3 本板：设备驱动侧（右）

```text
module_i2c_driver(ap3216c_driver)
  → i2c_add_driver → i2c_register_driver
       · 把 ap3216c 挂进 Drv 链表
       · 遍历已有 adapter/client → i2c_device_match → ap3216c_probe
```

本板 client 由 **`of_i2c_register_device`** 按 dts 的 `reg`/`compatible` 创建；驱动通过 **`.probe` + `of_match_table`** 绑定。硬件是否可用在 **`ap3216c_init`** 写寄存器时经 `i2c_transfer` → `i2c_imx_xfer` 验证（失败打 `ap3216c init failed`）。

对称性仍然成立：

```text

```

## 六、读数路径与 i2c-dev

### 6.1 本板主路径（专用驱动 + misc）

```text
应用 → /dev/ap3216c 或 sysfs als
  → ap3216c 驱动持有的 i2c_client
  → i2c_transfer → i2c_imx_xfer → 硬件
```

### 6.2 图2 上的 i2c-dev（通用字符设备）

```text
应用 → /dev/i2c-0（major 89，i2c-dev.c）
  → 内核用临时/通用方式对 adapter 发 i2c_msg
  → 同一套 i2c_transfer / master_xfer
```

用途：`i2cdetect`、`i2cget` 等。  
`i2cdetect` 见 **`UU`**：该地址已有 **bound 的 `i2c_client`**（被 `ap3216c` 占用），不是「空地址有器件应答」的那种显示。
