## 二、第一部分：I2C 框架（三层）

分析 I2C 驱动 = 分析 Linux 里 **总线 — 设备 — 驱动** 各层对象及其关系。先建立整体框架，再往框架上「放零件」。

### 2.3 三层各自职责

#### I2C 总线驱动层（主机 / 控制器）

通信中起 **主机** 作用：产生 start / stop / ACK 等。随 SoC 而异，由芯片厂商提供。

**本板文件：** `drivers/i2c/busses/i2c-imx.c`。

该层主要工作：

1. 填充 `i2c_adapter`，用核心层接口注册  
2. 做片上 I2C 主机相关初始化（时钟、IO、中断、寄存器）  
3. 通过核心层把适配器登记进内核  

#### I2C 总线核心层（中间层）

连接总线驱动层与设备驱动层；**与具体芯片无关**，使用内核 `i2c-core.c`。

主要提供：

1. 适配器注册（进入 `i2c_bus_type` 的 dev 链）  
2. `of_i2c_register_devices`：按 dts 子节点实例化 `i2c_client`  
3. `i2c_transfer`：主从数据传输入口  
4. `i2c_register_driver` / `i2c_add_driver`：登记设备驱动并匹配  

#### I2C 设备驱动层（从机侧软件）

按具体从设备编写。**本板示例：** `drivers/char/ap3216c.c`。

该层主要工作：

1. 提供 `of_match_table` / `id_table` 供匹配  
2. 在 `.probe` 里完成器件初始化与用户接口  
3. 通过 `i2c_transfer` 与总线通信  
4. 通过 `i2c_register_driver` 挂进 Drv 链

## 四、关键结构体

核心层主要提供「连接方法」，不负责填充 SoC/芯片私有数据；结构体重点在 **总线驱动层** 与 **设备驱动层**。

### 4.1 总线驱动层

#### 厂商私有结构（`imx_i2c_struct`）

内含锁、等待队列、当前 `i2c_msg`、状态机、寄存器、时钟、IRQ，以及嵌入的 **`struct i2c_adapter adap`**（`i2c-imx.c`）。

#### `i2c_adapter`（标识一条物理 I2C 总线）

关键字段：`algo`（通信算法）、`dev`、`nr`（总线号）、clients 链表等。

#### `i2c_algorithm`（一套通信方法）

最重要：`.master_xfer(adap, msgs, num)` —— 真正起停总线、收发字节。  
缺少 algorithm 的 adapter **什么也做不了**。

**本板：** `i2c_imx_algo.master_xfer = i2c_imx_xfer`。

#### `i2c_msg`（一次纯 I2C 事务描述）

```text
addr   — 7bit/10bit 从地址
flags  — 0=写，I2C_M_RD=读，以及 TEN/NOSTART 等
len    — 长度
buf    — 数据指针
```

传输三要素：源、目的、长度。写：`addr` 为目的、`buf` 为源；读则对调语义（数据从机→主机缓冲）。

### 4.2 设备驱动层

#### `i2c_driver`

一套驱动方法。本板 `ap3216c_driver` 使用：

- `.probe` / `.remove`  
- `of_match_table`（`compatible = "LiteOn,ap3216c"`）  
- `id_table`（`"ap3216c"`）

#### `i2c_client`

描述总线上的一颗真实从设备：`addr`、`name`、`adapter`、`driver` 等。

### 5.1 文本图④ — 对象挂接关系

```text

                    │ addr | flags | len | buf        │
                    └──────────────▲──────────────────┘
                                   │ msg
                    ┌──────────────┴──────────────────┐

                    │  … | msg | state | regs | clk    │

                    └────────────────────┬─────────────┘
                                         │ adap
              ┌──────────────────────────┼──────────────────────────┐
              ▼                          ▼                          │
     ┌── i2c_adapter ──┐       ┌── i2c_adapter ──┐                 │
     │ algo            │       │ algo ──────────────► i2c_algorithm │
     │ clients         │       │ clients         │   master_xfer   │
     └───┬──────┬──────┘       └───┬──────┬──────┘   functionality │
         │      │                  │      │
         ▼      ▼                  ▼      ▼
     i2c_client  i2c_client    i2c_client  i2c_client
     (adapter↑)  (adapter↑)    (adapter↑)  (adapter↑)
         \        \                /        /
          \        \              /        /
           \________\____ driver /________/
                         ▼
                  ┌─ i2c_driver ─┐
                  │ probe / …    │
                  └──────────────┘
```

### 5.2 三对关系

| 关系 | 含义 |
|------|------|
| **adapter ↔ client** | 与硬件「控制器 ↔ 从设备」一致；一个 adapter 可挂多个 client（clients 链表）；client 通过 `.adapter` 指回 |
| **adapter ↔ algorithm** | adapter 是物理总线抽象；algorithm 是通信方法；adapter.algo → master_xfer |
| **driver ↔ client** | driver 是一套方法；client 是具体芯片实例；**一对多**（同类多颗芯片） |

## 六、注册路径：`i2c_add_adapter` / `i2c_add_driver`

本树 4.1.15 的注册对称性（与图③一致）：

### 6.1 `i2c_add_adapter` → `i2c_register_adapter`

1. `device_register(&adap->dev)` → `bus_add_device` → adapter 入 **dev 链**（`klist_devices`）  
2. `of_i2c_register_devices(adap)` → 按 dts 子节点建 `i2c_client`（本板主路径）  
3. `bus_for_each_drv` → 通知已有 `i2c_driver`（`__process_new_adapter`）  

### 6.2 `i2c_add_driver` → `i2c_register_driver`

1. `driver_register` → `bus_add_driver` → driver 入 **Drv 链**（`klist_drivers`）  
2. `driver_attach` → `bus_for_each_dev` → 对每个 client 尝试 `i2c_device_match`  
3. 匹配成功 → `i2c_device_probe` → `driver->probe(client)`  

**对称性：** 先注册哪边都行；后到的一侧会扫另一侧链表并尝试匹配。

### 6.3 本板调用入口

| 步骤 | 本板符号 | 文件 |
|------|----------|------|
| 注册 adapter | `i2c_add_numbered_adapter`（`i2c_imx_probe` 内） | `i2c-imx.c` |
| 建 client | `of_i2c_register_devices` → `of_i2c_register_device` | `i2c-core.c` |
| 注册 driver | `module_i2c_driver(ap3216c_driver)` | `ap3216c.c` |
| 匹配 | `i2c_device_match` → `ap3216c_probe` | `i2c-core.c` / `ap3216c.c` |

细节深挖：`13` §六（`platform_driver_register`）、`14` §4.1.1（dev/Drv 链表）。

## 七、代码走读 — 总线驱动（`i2c-imx`）

本板 I2C 控制器经 **platform 总线** 出现，probe 里构造 `i2c_adapter` 并注册。

```text
of_platform_populate → platform_device(i2c@021a0000)   【设备先到】
        ↓
platform_driver_register(i2c_imx) → i2c_imx_probe      【驱动后到】
  · 分配/使用 imx_i2c_struct（内嵌 adapter）
  · 申请时钟、IRQ，ioremap 寄存器
  · adapter.algo = &i2c_imx_algo（master_xfer=i2c_imx_xfer）
  · i2c_add_numbered_adapter → i2c-0
  · of_i2c_register_devices → 建 ap3216c@1e 的 i2c_client(0-001e)   ← §7.2 展开
        ↓
之后传输：i2c_transfer → algo->master_xfer → i2c_imx_xfer        ← §7.3 展开
```

### 7.1 `i2c_imx_probe`：adapter 如何就绪

`i2c_imx_probe`（`drivers/i2c/busses/i2c-imx.c`）在 platform 匹配成功后，把控制器变成可被核心层使用的 `i2c_adapter`：

```text
i2c_imx_probe(pdev)
  ├─ platform_get_irq / platform_get_resource → request_irq(i2c_imx_isr)
  ├─ devm_ioremap_resource → i2c_imx->base（I2C1 MMIO 0x021a0000）
  ├─ devm_clk_get + clk_prepare_enable
  ├─ i2c_imx->adapter.algo = &i2c_imx_algo        ← .master_xfer = i2c_imx_xfer
  ├─ i2c_imx->adapter.nr = pdev->id               ← 本板 i2c1 → nr=0 → 设备名 i2c-0
  ├─ i2c_imx->adapter.dev.of_node = pdev->dev.of_node  ← 指向 dts 节点 i2c@021a0000
  ├─ i2c_set_adapdata(&adapter, i2c_imx)          ← xfer 里 i2c_get_adapdata 取回私有结构
  └─ i2c_add_numbered_adapter(&i2c_imx->adapter)
         └─ i2c_register_adapter(adap)             ← 进入 §7.2
```

**关键**：`adapter.dev.of_node` 必须指向 dts 里的 `&i2c1`（`i2c@021a0000`），后续 `of_i2c_register_devices` 才能遍历其**子节点**找到 `ap3216c@1e`。

### 7.2 `of_i2c_register_devices`：从 dts 到 `0-001e`

#### 7.2.1 调用时机与入口

`i2c_add_numbered_adapter` 最终进入 `i2c_register_adapter`（`drivers/i2c/i2c-core.c`）。在 `device_register(&adap->dev)` 把 `i2c-0` 挂进 dev 链之后，核心层立刻按 OF 建子设备：

```text
i2c_register_adapter(adap)
  ├─ device_register(&adap->dev)          → i2c-0 入 klist_devices
  ├─ of_i2c_register_devices(adap)        ← 本板建 client 的入口
  └─ bus_for_each_drv(...)                → 通知已有 i2c_driver
```

`of_i2c_register_devices` 逻辑很直接：

```c
// drivers/i2c/i2c-core.c
static void of_i2c_register_devices(struct i2c_adapter *adap)
{
    struct device_node *node;

    if (!adap->dev.of_node)    // adapter 无 OF 节点则跳过
        return;

    for_each_available_child_of_node(adap->dev.of_node, node)
        of_i2c_register_device(adap, node);
}
```

本板 dts（`imx6ull-14x14-evk-gengtao0901.dts`）中，`&i2c1` 下有一个 **available** 子节点：

```dts
&i2c1 {
    clock-frequency = <100000>;
    status = "okay";
    ap3216c@1e {
        compatible = "LiteOn,ap3216c", "ap3216c";
        reg = <0x1e>;
    };
};
```

遍历时 `node` = `ap3216c@1e`，进入 `of_i2c_register_device`。

#### 7.2.2 `of_i2c_register_device`：解析 dts → 填 `i2c_board_info`

```text
of_i2c_register_device(adap, ap3216c@1e)
  │
  ├─ of_modalias_node(node, info.type, ...)
  │     · 取 compatible 第一项 "LiteOn,ap3216c"
  │     · 生成 modalias → info.type = "ap3216c"（client->name 来源）
  │
  ├─ of_get_property(node, "reg", ...) → info.addr = 0x1e
  │
  ├─ info.of_node = of_node_get(node)   ← 保留 OF 节点，供后续 match 用
  │
  └─ i2c_new_device(adap, &info)
```

对应代码（`i2c-core.c` 1257～1301 行）：

| 步骤 | 代码动作 | 本板结果 |
|------|----------|----------|
| modalias | `of_modalias_node` | `client->name = "ap3216c"` |
| 地址 | `be32_to_cpup(reg)` | `client->addr = 0x1e` |
| OF 绑定 | `info.of_node = node` | `client->dev.of_node` → `ap3216c@1e` |
| 实例化 | `i2c_new_device` | 得到 `struct i2c_client *` |

#### 7.2.3 `i2c_new_device`：构造 `i2c_client` 并注册进总线

`i2c_new_device`（`i2c-core.c` 937～995 行）完成 client 对象的填充与驱动模型注册：

```text
i2c_new_device(adap, &info)
  ├─ kzalloc(struct i2c_client)
  ├─ client->adapter = adap              ← 绑到 i2c-0
  ├─ client->addr = 0x1e
  ├─ strlcpy(client->name, "ap3216c", ...)
  ├─ i2c_check_client_addr_validity()     ← 7bit 地址合法性
  ├─ i2c_check_addr_busy(adap, 0x1e)      ← 同总线同地址不可重复
  ├─ client->dev.parent = &adap->dev    ← sysfs 父子：0-001e 挂在 i2c-0 下
  ├─ client->dev.bus = &i2c_bus_type
  ├─ client->dev.type = &i2c_client_type
  ├─ client->dev.of_node = ap3216c@1e
  ├─ i2c_dev_set_name(adap, client)
  │     └─ dev_set_name("%d-%04x", adap->nr, addr)
  │           → 设备名 **"0-001e"**（nr=0，addr=0x1e）
  └─ device_register(&client->dev)
        ├─ bus_add_device → 0-001e 入 klist_devices（dev 链）
        └─ bus_probe_device → device_attach
              └─ 若 ap3216c 驱动已在 Drv 链 → i2c_device_match → probe
                 若驱动尚未加载 → 0-001e 暂存，等 insmod 后再 bind
```

**此时链上状态**（与 `14` §4.1.1 一致）：

```text
klist_devices:  [ i2c-0 ] → [ 0-001e ]
klist_drivers:  [ ] 或 [ ap3216c ]（取决于模块加载先后）
```

### 7.3 传输路径：`i2c_transfer` → `i2c_imx_xfer`

adapter 和 client 就绪后，设备驱动通过 **`i2c_transfer`** 发起读写。下面分别用 **`ap3216c_read_reg`（读）** 和 **`ap3216c_write_reg`（写）** 对照说明。

#### 7.3.1 设备驱动层：读 — 组两条 `i2c_msg`

读一个字节寄存器需要 **两条 msg**（写寄存器地址 + 读数据，中间 repeated START）：

```c
static int ap3216c_read_reg(struct i2c_client *client, u8 reg, u8 *buf)
{
    struct i2c_msg msg[2] = {
        [0] = { .addr = client->addr, .flags = 0,       .len = 1, .buf = &reg },
        [1] = { .addr = client->addr, .flags = I2C_M_RD, .len = 1, .buf = buf },
    };
    if (2 != i2c_transfer(client->adapter, msg, 2))
        return -1;
    return 0;
}
```

| msg | addr | flags | 含义 |
|-----|------|-------|------|
| msg[0] | 0x1e | 写 | 先发寄存器号（如 0x0C = ALS 低字节） |
| msg[1] | 0x1e | `I2C_M_RD` | 再读 1 字节到 `buf` |

`client->adapter` 即 **`i2c-0`**，因此这次传输走 I2C1 硬件。

#### 7.3.2 核心层：`i2c_transfer` 加锁并下发

```text
i2c_transfer(adap, msgs, 2)                    // i2c-core.c
  ├─ i2c_lock_adapter(adap)                    // 总线互斥，防止并发传输
  ├─ __i2c_transfer(adap, msgs, 2)
  │     └─ adap->algo->master_xfer(adap, msgs, 2)
  │           = i2c_imx_xfer(...)              // 进入控制器驱动
  └─ i2c_unlock_adapter(adap)
```

`__i2c_transfer` 在仲裁丢失（`-EAGAIN`）时会按 `adap->retries` 重试，然后返回**成功执行的 msg 条数**（本例期望返回 2）。

#### 7.3.3 控制器层：`i2c_imx_xfer` 状态机

`i2c_imx_xfer`（`i2c-imx.c` 888～958 行）是 algorithm 的唯一实现，把 `i2c_msg[]` 翻译成对 IMX I2C 寄存器的操作：

```text
i2c_imx_xfer(adapter, msgs, num=2)
  │
  ├─ i2c_imx = i2c_get_adapdata(adapter)       // 取回 imx_i2c_struct
  │
  ├─ i2c_imx_start(i2c_imx)                    // 一次传输的开始
  │     ├─ i2c_imx_set_clk()                   // 按 dts clock-frequency=100k 分频
  │     ├─ clk_prepare_enable(clk)
  │     ├─ 写 I2CR：I2CR_IEN | I2CR_MSTA | I2CR_IIEN | I2CR_MTX
  │     └─ i2c_imx_bus_busy(1)                 // 等 I2SR_IBB 置位（总线被占用=START 已发）
  │
  ├─ for (i = 0; i < num; i++)                 // 逐条处理 msg
  │     ├─ if (i > 0)                          // 第 2 条 msg：repeated START
  │     │     └─ I2CR_RSTA → i2c_imx_bus_busy(1)
  │     │
  │     ├─ msg[0] 写：i2c_imx_write()
  │     │     ├─ 写 I2DR = addr<<1（0x3c，写方向）
  │     │     ├─ i2c_imx_trx_complete()        // 等字节传完
  │     │     ├─ i2c_imx_acked()               // 查 I2SR_RXAK，无 ACK 则 -EIO
  │     │     └─ 写 I2DR = reg（如 0x0C）
  │     │
  │     └─ msg[1] 读：i2c_imx_read()
  │           ├─ 切接收模式（清 I2CR_MTX 等）
  │           ├─ 写 I2DR = addr<<1 | 1（0x3d，读方向）
  │           ├─ i2c_imx_trx_complete + i2c_imx_acked
  │           └─ 读 I2DR → msgs[1].buf[0]
  │
  └─ i2c_imx_stop(i2c_imx)                     // 清 MSTA 发 STOP，disable clk
```

#### 7.3.4 中断与等待：`i2c_imx_isr` + `i2c_imx_trx_complete`

`i2c_imx` 采用 **中断 + 等待队列**，不是轮询寄存器：

```text
写/读每个字节后：
  i2c_imx_trx_complete(i2c_imx)
    └─ wait_event_timeout(queue, i2c_imx->i2csr & I2SR_IIF, HZ/10)
           ▲                              │
           │                              │ 硬件传完 1 字节置 I2SR_IIF
           │                              ▼
           │                    i2c_imx_isr(irq)
           │                      ├─ 读 I2SR，保存到 i2c_imx->i2csr
           │                      ├─ 清 I2SR_IIF
           │                      └─ wake_up(&i2c_imx->queue)  → 唤醒 trx_complete
```

probe 里 `devm_request_irq(..., i2c_imx_isr, ...)` 把 I2C1 中断与上述唤醒链接好。若 100ms 内等不到 `I2SR_IIF`，`i2c_imx_trx_complete` 返回 `-ETIMEDOUT`，上层 `ap3216c_read_reg` 失败。

#### 7.3.5 本板一次读 ALS 的完整垂直路径

以 `cat .../ap3216c/als` 为例，一次读 ALS 要访问 **0x0C、0x0D** 两个寄存器，即两次 `ap3216c_read_reg`，每次 2 条 msg：

```text
show_als
  → ap3216c_read_als_data(client)
       → ap3216c_read_reg(0x0C) + ap3216c_read_reg(0x0D)
            → i2c_transfer(i2c-0, msg[2], 2)    × 2 次
                 → i2c_imx_xfer
                      → I2C1 @ 0x021a0000 寄存器 I2CR/I2DR/I2SR
                           → SCL/SDA → AP3216C(U9) @ 0x1E
```

| 层次 | 文件 | 本板符号 |
|------|------|----------|
| 设备驱动 | `ap3216c.c` | `ap3216c_read_reg` → `i2c_transfer` |
| I2C 核心 | `i2c-core.c` | `i2c_transfer` → `__i2c_transfer` |
| 总线驱动 | `i2c-imx.c` | `i2c_imx_xfer` / `i2c_imx_write` / `i2c_imx_read` |
| 硬件 | I2C1 MMIO | `IMX_I2C_I2CR` / `I2DR` / `I2SR` |

`ap3216c_init`（probe 里写 `0x00=0x04` 复位、`0x00=0x03` 使能）走的也是同一条链；若硬件/地址/总线有误，会在这里打出 `ap3216c init failed`。

#### 7.3.6 写路径对照：`ap3216c_write_reg` → `i2c_imx_write`

写寄存器比读简单：**只需 1 条 msg**，把「寄存器号 + 数据」连续写在同一次写事务里，无需 repeated START。

##### 设备驱动层

```c
static int ap3216c_write_reg(struct i2c_client *client, u8 reg, u8 data)
{
    u8 buf[2] = {reg, data};

    struct i2c_msg msg = {
        .addr  = client->addr,
        .flags = 0,          /* 写 */
        .len   = 2,
        .buf   = buf,        /* buf[0]=reg, buf[1]=data */
    };

    if (1 != i2c_transfer(client->adapter, &msg, 1))
        return -1;
    return 0;
}
```

| 字段 | 本板取值（以 `ap3216c_init` 复位为例） | 含义 |
|------|----------------------------------------|------|
| `addr` | `0x1e` | 7bit 从地址 |
| `flags` | `0`（写） | 整条 msg 为写方向 |
| `len` | `2` | 连续写 2 字节 |
| `buf[0]` | `0x00`（`AP3216C_SYSTEMCONG`） | 寄存器地址 |
| `buf[1]` | `0x04` | 软件复位命令 |

**读 vs 写 msg 对比：**

| 操作 | msg 条数 | `i2c_transfer` 返回值期望 | 总线事务 |
|------|----------|---------------------------|----------|
| `ap3216c_read_reg` | 2 | `2` | START → 写 reg → **RSTART** → 读 1 字节 → STOP |
| `ap3216c_write_reg` | 1 | `1` | START → 写 reg → 写 data → STOP |

##### 核心层

与读路径相同，只是 `num=1`：

```text
i2c_transfer(adap, &msg, 1)
  ├─ i2c_lock_adapter(adap)
  ├─ __i2c_transfer(adap, &msg, 1)
  │     └─ i2c_imx_xfer(adap, &msg, 1)
  └─ i2c_unlock_adapter(adap)
```

##### 控制器层：`i2c_imx_write` 逐字节下发

`i2c_imx_xfer` 里 `msgs[0].flags` 无 `I2C_M_RD`，走 **`i2c_imx_write`**（`i2c-imx.c` 752～783 行）：

```text
i2c_imx_xfer(adapter, msgs, num=1)     // 写 0x00=0x04 复位
  │
  ├─ i2c_imx_start(i2c_imx)            // START，总线进入主机发送模式
  │
  └─ i2c_imx_write(i2c_imx, &msgs[0])
        │
        ├─ 写 I2DR = 0x1e << 1 = 0x3C   // 从地址 + 写位
        ├─ trx_complete → isr 唤醒
        ├─ i2c_imx_acked()              // 从机 ACK？无则 -EIO（地址错/器件未上电）
        │
        ├─ 写 I2DR = buf[0] = 0x00     // 寄存器号
        ├─ trx_complete + acked
        │
        ├─ 写 I2DR = buf[1] = 0x04     // 数据（软件复位）
        └─ trx_complete + acked
  │
  └─ i2c_imx_stop(i2c_imx)             // STOP，释放总线
```

每条「写 I2DR」之后都经历 **trx_complete → isr 置 I2SR_IIF → wake_up**（与 §7.3.4 读路径相同），写 2 字节数据加上 1 字节地址共 **3 次** 中断等待。

##### 本板 `ap3216c_init` 完整写序列

`ap3216c_probe` → `ap3216c_init` 连续两次写配置寄存器：

```text
ap3216c_init(client)
  ├─ ap3216c_write_reg(client, 0x00, 0x04)    // 软件复位
  │     └─ i2c_transfer × 1（1 msg，写 2 字节）→ i2c_imx_write × 1
  ├─ mdelay(50)                               // 等待复位完成
  └─ ap3216c_write_reg(client, 0x00, 0x03)    // 使能 IR/ALS/PS
        └─ i2c_transfer × 1 → i2c_imx_write × 1
```

任意一步 `i2c_imx_acked` 失败（无 ACK）或 `trx_complete` 超时，都会导致 `ap3216c_write_reg` 返回 `-1`，最终 `ap3216c_probe` 打印 **`ap3216c init failed`**。这是本板验证「I2C 物理链路是否通」的第一道关卡——比读 ALS 更早执行。

##### 读/写路径一图对照

```text
                    ap3216c.c
           ┌──────────┴──────────┐
           ▼                     ▼
   ap3216c_read_reg      ap3216c_write_reg
   msg[2], num=2         msg[1], num=1
   写reg + RSTART + 读    写 reg + data
           │                     │
           └──────────┬──────────┘
                      ▼
              i2c_transfer (i2c-core.c)
                      ▼
              i2c_imx_xfer (i2c-imx.c)
           ┌──────────┴──────────┐
           ▼                     ▼
    i2c_imx_write            i2c_imx_read
    （probe init / 写配置）   （show_als / 读数据）
           │                     │
           └──────────┬──────────┘
                      ▼
         I2C1 寄存器 I2CR / I2DR / I2SR + IRQ
                      ▼
              AP3216C @ 0x1E（SCL/SDA）
```

三层（总线驱动 / 核心 / 设备驱动）+ `i2c_bus_type` 上 adapter↔driver 对称注册，把 I2C 框架串起来；结构体上是 **adapter+algorithm 管总线，client+driver 管芯片，msg 管一帧传输**。

### 11.2 双总线视角（对照 §2.2）

AP3216C 打通涉及 **两条总线、两次匹配**：

```text
【第一次：platform 总线 — 造「主机」】
dtb: i2c@021a0000 (status=okay, pinctrl_i2c1)
  → of_platform_populate → platform_device
  → platform_driver_register(i2c_imx)
  → i2c_imx_probe → i2c_adapter(i2c-0)

【第二次：i2c 总线 — 绑「从机」】
dtb: ap3216c@1e (compatible, reg=0x1e)
  → of_i2c_register_devices → i2c_client(0-001e)
  → i2c_add_driver(ap3216c) → match → ap3216c_probe
  → /dev/ap3216c
```

硬件信号链（写 dts 前必对）：

```text
AP3216C(U9) ──SCL/SDA── I2C1 ── UART4_TX/RX 复用 ── i2c@021a0000
              7bit 地址 0x1E
              reg = <0x1e>   （不是节点名 @1e 本身）
```

        ↓
③ subsys_initcall: platform_driver_register(i2c_imx)

| 2 | `i2c_add_driver` | 扫已有 client | 登记 `ap3216c_driver` | bind + probe |

### 11.5 分层打通：L0～L4 与 I2C 三层对应

用 `11` 的验证层级，映射到本文 **三层框架**：

| 层级 | I2C 框架层 | 要做什么 | 成功判据 | 卡住了先查 |
|------|------------|----------|----------|------------|
| **L0** | 总线驱动 + 核心 | `&i2c1 status=okay`、pinctrl、`CONFIG_I2C_IMX` | `/dev/i2c-0`；dmesg `IMX I2C adapter registered` | dtsi/disabled、pinctrl、内核配置 |
| **L1** | OF → client 前提 | 删 `fxls8471@1e`，挂 `ap3216c@1e`，重编 dtb | `/proc/device-tree/.../ap3216c@1e` 存在 | 改错 dts、U-Boot 旧 dtb |
| **L2** | adapter + 硬件 | `i2cdetect -y 0` 见 `0x1e` | 地址有应答（未绑驱动时为 `1e`） | 供电、SCL/SDA、扫错总线号 |
| **L3** | 设备驱动注册 | overlay 引入 `ap3216c.c`，`CONFIG_LITEON_AP3216C=y`，重编 zImage | `nm vmlinux \| grep ap3216c_probe`；板上 `/dev/ap3216c` | 只更 dtb、未更内核 |
| **L4** | probe + 用户态 | 绑定后读 als/ps | `0x1e=UU`；`cat .../als` 有数且随环境变 | compatible、init 写寄存器失败 |

**打通最小闭环（按层递进）：**

```text
L0：i2c-0 存在          ← 总线驱动层 + platform 匹配
L1：dtb 有 ap3216c@1e    ← OF 节点（尚未要求驱动）
L2：i2cdetect 见 1e      ← adapter + algorithm + 硬件
L3：/dev/ap3216c 存在    ← i2c_driver probe + misc
L4：als/ps 可读且变化    ← i2c_msg + i2c_transfer 全链路
```

### 11.6 代码走读：总线侧（L0 对应 §七）

本板 dts 关键片段：

```dts
&i2c1 {
	clock-frequency = <100000>;
	pinctrl-0 = <&pinctrl_i2c1>;
	status = "okay";
	ap3216c@1e {
		compatible = "LiteOn,ap3216c", "ap3216c";
		reg = <0x1e>;
	};
};
```

走读链（与 §7.2 一致，标注 AP3216C 相关点）：

```text
imx6ul_init_machine
  of_platform_populate
    → platform_device(i2c@021a0000)     /* 父节点，带 pinctrl/clock-frequency */

i2c_adap_imx_init → platform_driver_register(i2c_imx)
  i2c_imx_probe
    adapter.dev.of_node = &i2c1          /* 后面遍历 ap3216c@1e 靠这个 */
    of_property_read_u32("clock-frequency", 100000)
    pinctrl_bind_pins                    /* pinctrl_i2c1：SCL/SDA */
    i2c_add_numbered_adapter
      i2c_register_adapter
        of_i2c_register_devices
          of_i2c_register_device(ap3216c@1e)
            reg → client->addr = 0x1e
            compatible → client->name = ap3216c
            i2c_new_device → 0-001e
```

### 11.7 代码走读：设备侧（L3/L4 对应 §八）

驱动匹配表（`ap3216c.c`）：

```text
of_match_table:  "LiteOn,ap3216c"   ← dts compatible 第一项
id_table:        "ap3216c"          ← of_modalias 生成名；probe 强制需要
probe:           ap3216c_probe
```

probe 内部（初始化 + 用户接口，一次 probe 完成）：

```text
ap3216c_probe(client, id)
  ├─ ap3216c_init(client)
  │    ap3216c_write_reg(0x00, 0x04)   /* 复位 */
  │    mdelay(50)
  │    ap3216c_write_reg(0x00, 0x03)   /* 使能 IR/ALS/PS */
  │         └─ i2c_transfer → i2c_imx_xfer   /* 失败 → ap3216c init failed */
  ├─ misc_register → /dev/ap3216c
  └─ ap3216c.client = client           /* 后续 sysfs/ioctl 用 */
```

**读 als 时的 `i2c_msg` 路径（对照 §4.1 三要素）：**

```text
cat .../ap3216c/als
  → show_als
       → ap3216c_read_als_data(client)
            → ap3216c_read_reg(0x0C) / (0x0D)
                 msg[0]: addr=0x1e, flags=写, buf=寄存器号
                 msg[1]: addr=0x1e, flags=读, buf=数据
                 i2c_transfer(client->adapter, msg, 2)
                      → i2c_imx_xfer → I2C1 硬件
```

### 11.8 按三层框架回查失败

| 现象 | 框架层 | 对应 L | 先查 |
|------|--------|--------|------|
| 无 `/dev/i2c-0` | 总线驱动 / platform | L0 | `I2C_IMX`、`&i2c1`、pinctrl |
| 无 `ap3216c@1e` in procfs | OF（client 前提） | L1 | dtb 是否重编、是否加载 |
| `i2cdetect` 无 `1e` | adapter + 硬件 | L2 | 供电、接线、总线号 0 |
| 有 `1e` 无 `UU`、无 `/dev/ap3216c` | 设备驱动 match/probe | L3 | 驱动是否编进、`compatible` |
| `ap3216c init failed` | probe 内 i2c_transfer | L4 | 地址/总线/器件 |
| dmesg 无 ap3216 字样 | — | L3/L4 | **成功时常无日志**；看 `/dev/ap3216c` |
| `fxls8471 probe 0-001e failed` | client 冲突 | L1 | 未删 EVK 节点 |

### 11.9 板上速查（打通验收）

```bash
# L0
ls /dev/i2c-0

# L1
find /proc/device-tree -name 'ap3216c@1e'

# L2/L4
i2cdetect -y 0          # 期望 0x1e → UU（L4 绑定后）

# L3/L4
ls -l /dev/ap3216c
ls -l /sys/bus/i2c/devices/0-001e/driver

# L4 读数
cat /sys/devices/virtual/misc/ap3216c/als
cat /sys/devices/virtual/misc/ap3216c/ps
```

### 11.10 本章一句话

**按本文思路打通 AP3216C = 先在 platform 总线上用 `i2c-imx` 造出 `i2c-0`，再在 i2c 总线上用 dts + `of_i2c_register_*` 造 `0-001e`，最后用 `ap3216c_driver` match/probe 出 `/dev/ap3216c`；L0→L4 逐层验收，传输统一走 `i2c_msg` → `i2c_transfer` → `i2c_imx_xfer`。**
