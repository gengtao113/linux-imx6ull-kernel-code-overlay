## 一、导读

### 1.1 一句话结论

LED0 设备树里两处看似"并列"的节点，走的是**两条完全不同的匹配机制**：

```text
leds {                                  ← compatible = "gpio-leds" → leds-gpio 驱动（platform 匹配）
    compatible = "gpio-leds";
    pinctrl-0 = <&pinctrl_gpio_leds>;   ← 不是匹配，是"引用" pin group → pinctrl 子系统
    led0 { gpios = <&gpio1 3 GPIO_ACTIVE_LOW>; }  ← phandle → gpiolib 解析 GPIO
};
pinctrl_gpio_leds: gpio-leds {          ← 是 iomuxc 控制器下的"数据"，无独立驱动
    fsl,pins = <MX6UL_PAD_GPIO1_IO03__GPIO1_IO03 0x17059>;
};
```

- **`compatible` 决定"谁来管"**：`gpio-leds` 让内核把整个 `leds` 节点交给 **leds-gpio** 驱动。
- **`pinctrl-0` 决定"脚怎么复用"**：引用 `pinctrl_gpio_leds`，让 **iomuxc pinctrl 驱动**把 GPIO1_IO03 mux 成 GPIO。
- **`gpios` 决定"用哪根脚、极性如何"**：phandle `&gpio1` + 脚号 `3` + `GPIO_ACTIVE_LOW`，交给 **gpiolib** 拿 GPIO 并自动反相。

三条链缺一不可：没有 compatible → 驱动不跑；没有 pinctrl-0 → 脚仍是普通 pad、电平出不去；没有 gpios → 驱动不知道控制哪根脚。

### 1.2 硬件 ↔ 节点 ↔ 驱动（速查）

| 硬件 | 设备树 | 驱动 / 子系统 |
|------|--------|----------------|
| LED0（底板，共阳，阴极接 GPIO1_IO03） | `led0` 子节点 | **leds-gpio** → `/sys/class/leds/sys-led/` |
| GPIO1_IO03（IOMUX pad，ALT5=GPIO） | `pinctrl_gpio_leds` + `fsl,pins` | **pinctrl-imx**（iomuxc 控制器） |
| GPIO 控制器 `0x0209c000` | `gpio1`（`compatible = "fsl,imx6ul-gpio"`） | **gpio-mxc**（gpiolib 后端） |
| LED 亮度 / 触发 | `label` / `default-state` / `linux,default-trigger` | **LED class** 子系统 |

### 1.3 匹配总览（从 dts 到 /sys/class/leds）

```text
形态 A  板级 dts（leds + pinctrl_gpio_leds）
           │ dtc
形态 B  dtb 二进制块
           │ unflatten
形态 C  device_node 树
           │
           ├─ ① leds 节点 compatible="gpio-leds" ──► of_gpio_leds_match[] → gpio_led_probe
           │        └─ gpio_leds_create 遍历子节点 led0
           │                ├─ 读 label        → "sys-led"
           │                ├─ 读 default-state → LEDS_GPIO_DEFSTATE_ON
           │                └─ 读 gpios        → devm_get_gpiod_from_child
           │                          ↓
           ├─ ② gpios = <&gpio1 3 GPIO_ACTIVE_LOW> ──► gpiolib（gpio-mxc 控制器）
           │        └─ 拿到 GPIO 描述符，active-low 自动反相
           │
           └─ ③ pinctrl-0 = <&pinctrl_gpio_leds> ──► pinctrl_bind_pins()
                    └─ iomuxc（fsl,imx6ul-iomuxc）写 MUX/PAD 寄存器
                    └─ 最终 led_classdev_register → /sys/class/leds/sys-led/
```

## 二、两段（其实是三段）匹配链总览

LED0 的 dts 虽然只有几行，却牵扯**三段各自独立**的匹配。先建立整体认识，后面再逐段展开。

| 链 | dts 关键字段 | 匹配键 | 内核入口 | 结果 |
|----|--------------|--------|----------|------|
| **A. LED 驱动链** | `leds` 的 `compatible = "gpio-leds"` | **字符串对表** | `of_gpio_leds_match[]` → `gpio_led_probe` | 出 `sys-led`，注册 LED class |
| **B. pinctrl 链** | `leds` 的 `pinctrl-0` + `pinctrl-names` | **phandle 引用**（非 compatible） | `pinctrl_bind_pins()` → iomuxc 写寄存器 | GPIO1_IO03 mux 成 GPIO |
| **C. GPIO 链** | `led0` 的 `gpios = <&gpio1 3 GPIO_ACTIVE_LOW>` | **phandle + 脚号 + 标志** | `devm_get_gpiod_from_child()` → gpiolib | 拿到带反相的 GPIO 描述符 |

**核心分界：只有链 A 走"compatible 对表匹配"。** 链 B、链 C 都是**按 phandle 引用**，不是按 compatible 匹配。这个区分是整个文档最想讲清的一点。

## 三、链 A：`leds` 节点如何匹配 leds-gpio 驱动

> 源码：`drivers/leds/leds-gpio.c`（内核树 / overlay 同源）  
> 辅助：`drivers/base/platform.c`、`drivers/of/device.c`

### 3.1 platform 匹配：compatible 对表

leds-gpio 是一个 **platform 驱动**，其匹配表只有一项：

```c
/* drivers/leds/leds-gpio.c:236 */
static const struct of_device_id of_gpio_leds_match[] = {
	{ .compatible = "gpio-leds", },
	{},
};
MODULE_DEVICE_TABLE(of, of_gpio_leds_match);

/* drivers/leds/leds-gpio.c:290 */
static struct platform_driver gpio_led_driver = {
	.probe		= gpio_led_probe,
	.driver		= {
		.name	= "leds-gpio",
		.of_match_table = of_gpio_leds_match,   /* ← 指向上面那张表 */
	},
};
module_platform_driver(gpio_led_driver);
```

匹配过程（platform 总线通用逻辑）：

```text
of_platform_populate(root)                       /* 从 device_node 树创建设备 */
  → 对 status="okay" 的每个节点建 platform_device
  → leds 节点 → platform_device（dev.of_node = leds 节点）
        ↓
platform_match(dev, drv)                         /* drivers/base/platform.c */
  → of_driver_match_device(dev, drv)
  → 拿 leds 节点的 compatible "gpio-leds"
  → 在 of_gpio_leds_match[] 里逐项比对
  → 命中 "gpio-leds"
        ↓
gpio_led_probe(pdev)                             /* 驱动被调用 */
```

| dts | 内核 |
|-----|------|
| `compatible = "gpio-leds";` | `of_gpio_leds_match[0].compatible` 命中 |
| 命中后 | 调用 `gpio_led_probe()` |

**一句话：** dts 里的 `compatible = "gpio-leds"` 字符串，必须和驱动 `of_device_id[]` 里的 `.compatible = "gpio-leds"` 完全一致，驱动才会被调用。

#### 3.1.1 展开：`of_platform_populate` 内部实现（从 dtb 到 platform_device 树）

`of_platform_populate` 是"设备树 → platform_device 树"的**总入口**。上面 §3.1 流程图第 1 行就是它，本节把它内部实现展开。

**（1）谁调用它：ARM 启动路径**

它由板级初始化回调在 `arch_initcall` 阶段触发，不是内核凭空自跑：

```c
/* arch/arm/kernel/setup.c:820 */
static int __init customize_machine(void)
{
	of_iommu_init();
	if (machine_desc->init_machine)              /* 板级自定义了 init_machine */
		machine_desc->init_machine();
#ifdef CONFIG_OF
	else
		of_platform_populate(NULL, of_default_bus_match_table,  /* 兜底路径 */
					NULL, NULL);
#endif
	return 0;
}
arch_initcall(customize_machine);
```

i.MX6ULL **走 `init_machine` 分支**（不是 else 兜底），因为 mach-imx6ul.c 定义了它：

```c
/* arch/arm/mach-imx/mach-imx6ul.c:169 */
static void __init imx6ul_init_machine(void)
{
	struct device *parent;
	parent = imx_soc_device_init();
	...
	of_platform_populate(NULL, of_default_bus_match_table, NULL, NULL);  /* ← 第 177 行 */
	imx6ul_enet_init();
	imx_anatop_init();

}

/* arch/arm/mach-imx/mach-imx6ul.c:214 */

	.map_io		= imx6ul_map_io,
	.init_irq	= imx6ul_init_irq,
	.init_machine	= imx6ul_init_machine,      /* ← 第 217 行 */
	.init_late	= imx6ul_init_late,
	.dt_compat	= imx6ul_dt_compat,         /* {"fsl,imx6ul","fsl,imx6ull"} */
MACHINE_END
```

`dt_compat` 让内核在启动早期用根节点的 `compatible` 选中这个 `machine_desc`。

**（2）函数本体逐行（drivers/of/platform.c:435）**

```c
int of_platform_populate(struct device_node *root,
			const struct of_device_id *matches,
			const struct of_dev_auxdata *lookup,
			struct device *parent)
{
	struct device_node *child;
	int rc = 0;

	root = root ? of_node_get(root) : of_find_node_by_path("/");   /* NULL → 根节点 */
	if (!root)
		return -EINVAL;

	for_each_child_of_node(root, child) {                          /* 遍历根的子节点 */
		rc = of_platform_bus_create(child, matches, lookup, parent, true);
		if (rc)
			break;
	}
	of_node_set_flag(root, OF_POPULATED_BUS);

	of_node_put(root);                                             /* 归还引用计数 */
	return rc;
}
```

| 行 | 动作 | 含义 |
|----|------|------|
| `root = of_find_node_by_path("/")` | 入参 NULL 时取根节点 | 从整棵树顶层开始 |
| `for_each_child_of_node(root, child)` | 遍历 `/` 直接子节点 | `/soc`、`/leds`、`/backlight`、`/chosen`、`/memory`… |
| `of_platform_bus_create(child, ..., true)` | 每个子节点递归建设备 | **strict=true**（见下） |
| `OF_POPULATED_BUS` | 给根打标记 | 表示"这层已被 populate 过" |

**（3）`matches` 参数：`of_default_bus_match_table`**

```c
/* drivers/of/platform.c:26 */
const struct of_device_id of_default_bus_match_table[] = {
	{ .compatible = "simple-bus", },
	{ .compatible = "simple-mfd", },
#ifdef CONFIG_ARM_AMBA
	{ .compatible = "arm,amba-bus", },
#endif
	{}
};
```

`matches` 的作用**不是**"匹配出驱动"，而是**"判断哪些节点算总线、需要继续往下递归建子设备"**。

**（4）关键：strict=true + `of_match_node` 决定递归边界**

`of_platform_bus_create`（drivers/of/platform.c:327）里两处关键判断：

```c
/* ① strict 模式：没有 compatible 的节点直接跳过 */
if (strict && (!of_get_property(bus, "compatible", NULL))) {
	pr_debug("skipping %s, no compatible prop\n", bus->full_name);
	return 0;
}
...
dev = of_platform_device_create_pdata(bus, ...);      /* ② 建本节点的设备 */
if (!dev || !of_match_node(matches, bus))              /* ③ 本节点匹配总线类型吗？ */
	return 0;                                         /* 不匹配 → 不递归子节点 */

for_each_child_of_node(bus, child)                     /* ④ 匹配 → 递归子节点 */
	of_platform_bus_create(child, matches, ...);
```

于是根节点 `/` 的每个子节点被这样分流：

| 根的子节点 | compatible | 建 device？ | 递归子节点？ | 说明 |
|-----------|------------|-------------|--------------|------|
| `/soc` | `simple-bus` | ✅ | ✅ 继续往下建 aips-bus 等 | 匹配 `simple-bus`（imx6ull.dtsi:145） |
| `/leds` | `gpio-leds` | ✅ | ❌ 停 | **led0 不被建成独立 platform_device** |
| `/backlight` | （各板不同） | ✅ | ❌ 停 | 非总线型 |
| `/chosen` | 无 | ❌ 跳过 | — | strict 跳过 |
| `/memory` | 无 | ❌ 跳过 | — | strict 跳过 |

**这正是"`led0` 为什么不是独立 platform_device"的根因**：`/leds` 的 compatible 是 `gpio-leds`，不在 `of_default_bus_match_table` 里，`of_match_node(matches, bus)` 返回 NULL → `of_platform_bus_create` 建完 `leds` 设备后**不递归** → `led0` 留在设备树里，由 leds-gpio 驱动在 probe 时用 `device_for_each_child_node` 自己遍历（见 §3.2）。

**（5）完整调用链 + 一句话**

```text
arch_initcall(customize_machine)                          arch/arm/kernel/setup.c:838
  → machine_desc->init_machine() = imx6ul_init_machine    mach-imx6ul.c:217
      → of_platform_populate(NULL, of_default_bus_match_table, NULL, NULL)
          → root = of_find_node_by_path("/")
          → for_each_child_of_node(/):
                of_platform_bus_create(child, matches, strict=true)
                   ├─ 无 compatible → 跳过（/chosen、/memory）
                   ├─ 有 compatible → of_platform_device_create_pdata 建 device
                   │                     （→ of_device_alloc → platform_device_add，见 §3.1.2）
                   └─ of_match_node(matches, child) 命中 simple-bus → 递归子节点
                        （/soc 递归；/leds 不递归 → led0 不建 device）
```

**一句话：** `of_platform_populate` 以根节点为起点，`for_each_child_of_node` 递归扫描设备树；strict 模式要求每个节点有 `compatible`，`of_default_bus_match_table`（`simple-bus` 等）决定"哪些节点继续往下递归"——LED 案例里 `/soc` 递归到各控制器，`/leds` 建成一个 platform_device 但**不再往下递归**，所以 `led0` 是 leds-gpio 驱动 probe 时自己遍历的子节点，而不是独立的 platform_device。

#### 3.1.2 展开：`platform_device` 内部实现与 `platform_match` 四步回退

上面流程里的 `platform_device` 和 `platform_match` 两处，是"设备树节点 → 驱动"之间的**关键桥梁**。这里把它们内部实现展开。

**（1）`platform_device` 是什么**

`platform_device` 是 Linux 设备模型里"平台总线设备"的一个壳，它**内嵌 `struct device`**（按值，不是指针），通过 `container_of` 互相转换：

```c
/* include/linux/platform_device.h:18 */
struct platform_device {
	const char	*name;         /* 设备名，如 "leds" */
	int		id;             /* 实例号：-1=无、-2=自动 */
	bool		id_auto;
	struct device	dev;           /* ★ 内嵌通用 device，非指针 */
	u32		num_resources;  /* 资源个数 */
	struct resource	*resource;     /* 资源表：reg/中断 等 */
	const struct platform_device_id	*id_entry;
	char *driver_override;         /* 强制指定驱动名 */
	struct mfd_cell *mfd_cell;
	struct pdev_archdata	archdata;
};

#define to_platform_device(x) container_of((x), struct platform_device, dev)
```

| 字段 | 作用 |
|------|------|
| `name` / `id` | 决定设备在总线上的名字（`"%s"` 或 `"%s.%d"`） |
| `dev` | 内嵌的设备模型对象，`device_add()` 就操作它 |
| `resource[]` | 记录 `reg`（内存）/ `irq`（中断）等硬件资源，驱动用 `platform_get_resource()` 取 |
| `driver_override` | 若非空，`platform_match` 只按这个名字找驱动 |

**（2）名字的内存小技巧**

`platform_device_alloc()` 不是单独 malloc 名字，而是分配一个更大的结构，把名字写在 `platform_device` 后面：

```c
/* drivers/base/platform.c:188 */
struct platform_object {
	struct platform_device pdev;
	char name[];                 /* 柔性数组，紧跟 pdev 之后 */
};

/* drivers/base/platform.c:228 */
struct platform_device *platform_device_alloc(const char *name, int id)
{
	struct platform_object *pa;
	pa = kzalloc(sizeof(*pa) + strlen(name) + 1, GFP_KERNEL);
	if (pa) {
		strcpy(pa->name, name);       /* 名字写在 pdev 后面的内存 */
		pa->pdev.name = pa->name;     /* name 指针指回同一块 */
		pa->pdev.id = id;
		device_initialize(&pa->pdev.dev);   /* ★ 初始化内嵌 device */
		pa->pdev.dev.release = platform_device_release;
		arch_setup_pdev_archdata(&pa->pdev);
	}
	return pa ? &pa->pdev : NULL;
}
```

一次 `kzalloc` 同时拿到 `platform_device` 和它的名字；释放时 `container_of` 找回 `platform_object` 一起 free。

**（3）从 device_node 到 platform_device：四层调用（LED 为例）**

源码 `drivers/of/platform.c`：

```text
of_platform_populate(root)                        /* 入口，root 通常是 / 或 /soc */
  └─ of_platform_bus_create(bus, ...)             /* 对一个节点 + 其子节点递归建设备 */
       └─ of_platform_device_create_pdata(np, ...)   /* 建单个设备 */
            └─ of_device_alloc(np, bus_id, parent)   /* 分配 + 填资源 + 绑 of_node */
```

- `of_platform_bus_create`（of/platform.c:327）：strict 模式要求节点有 `compatible`，否则跳过；建完本节点后 `for_each_child_of_node` 递归处理子节点。
- `of_platform_device_create_pdata`（of/platform.c:168）：

```c
if (!of_device_is_available(np) ||            /* status != "okay" 就不建 */
    of_node_test_and_set_flag(np, OF_POPULATED))  /* 防重复建 */
	return NULL;

dev = of_device_alloc(np, bus_id, parent);
dev->dev.bus = &platform_bus_type;            /* ★ 挂到 platform 总线 */
of_dma_configure(&dev->dev, dev->dev.of_node);
if (of_device_add(dev) != 0) ...              /* ★ 注册进设备模型 */
```

`of_device_is_available()` 就是"只有 `status = "okay"` 的节点才建设备"的代码依据。

- `of_device_alloc`（of/platform.c:105，最核心）：

```c
dev = platform_device_alloc("", -1);          /* 先分配空壳 */

while (of_address_to_resource(np, num_reg, &temp_res) == 0)
	num_reg++;                                /* 数 reg（地址） */
num_irq = of_irq_count(np);                   /* 数 interrupts */

if (num_irq || num_reg) {                     /* 建资源表 */
	res = kzalloc(sizeof(*res) * (num_irq + num_reg), GFP_KERNEL);
	dev->num_resources = num_reg + num_irq;
	dev->resource = res;
	for (i = 0; i < num_reg; i++, res++)
		of_address_to_resource(np, i, res);
	if (of_irq_to_resource_table(np, res, num_irq) != num_irq)
		pr_debug("not all legacy IRQ resources mapped for %s\n", np->name);
}

dev->dev.of_node = of_node_get(np);           /* ★ 让 device 记住对应设备树节点 */
dev->dev.parent = parent ?: &platform_bus;

if (bus_id)
	dev_set_name(&dev->dev, "%s", bus_id);
else
	of_device_make_bus_id(&dev->dev);        /* 没指定名字就用节点名 */
```

三个产物：

| 产物 | 来源 | 作用 |
|------|------|------|
| `dev->dev.of_node` | `of_node_get(np)` | 让 `device` 记住设备树节点（引用计数 +1），后续驱动靠它读属性 |
| `dev->resource[]` | 从 `reg`/`interrupts` 翻译 | 硬件资源表 |
| `dev_name` | `bus_id` 或节点名 | 设备在 sysfs 里的名字 |

**LED 特例：为什么 `num_resources = 0`。** `leds` 节点没有 `reg` 也没有 `interrupts` → `num_reg = 0`、`num_irq = 0` → 不建资源表。因为 LED 不是内存映射外设，没有自己的寄存器基址；真正有 `reg` 的是 `gpio1`（`0x0209c000`）和 `iomuxc`（`0x020e0000`）那些控制器。

**（4）`platform_device_add`：推入设备模型，`device_add` 是分水岭**

`of_device_add` 最终调到 `platform_device_add`（drivers/base/platform.c:308）：

```c
if (!pdev->dev.parent)
	pdev->dev.parent = &platform_bus;
pdev->dev.bus = &platform_bus_type;            /* ★ 总线 = platform_bus_type */

switch (pdev->id) {                            /* 按 id 决定名字 */
default:
	dev_set_name(&pdev->dev, "%s.%d", pdev->name, pdev->id); break;
case PLATFORM_DEVID_NONE:                      /* -1，如 LED */
	dev_set_name(&pdev->dev, "%s", pdev->name); break;
case PLATFORM_DEVID_AUTO:                      /* -2 */
	... ida_simple_get(...); dev_set_name(&pdev->dev, "%s.%d.auto", ...);
}

for (i = 0; i < pdev->num_resources; i++) {    /* 资源挂到全局资源树防冲突 */
	... if (resource_type(r) == IORESOURCE_MEM) p = &iomem_resource; ...
	if (p && insert_resource(p, r)) { ... }
}

ret = device_add(&pdev->dev);                  /* ★ 进入设备模型，触发驱动匹配 */
```

**`device_add()` 是分水岭**：它把内嵌 `struct device` 挂到 platform 总线上，随后设备模型核心遍历总线上已注册的驱动，调用 `platform_bus_type.match` 尝试绑定。

**（5）`platform_match` 四步回退（drivers/base/platform.c:820）**

```c
static int platform_match(struct device *dev, struct device_driver *drv)
{
	struct platform_device *pdev = to_platform_device(dev);
	struct platform_driver *pdrv = to_platform_driver(drv);

	/* ① 强制驱动名（driver_override） */
	if (pdev->driver_override)
		return !strcmp(pdev->driver_override, drv->name);

	/* ② OF 风格：compatible 对 of_device_id 表（★ LED 走这里） */
	if (of_driver_match_device(dev, drv))
		return 1;

	/* ③ ACPI 风格 */
	if (acpi_driver_match_device(dev, drv))
		return 1;

	/* ④ 老式 id_table */
	if (pdrv->id_table)
		return platform_match_id(pdrv->id_table, pdev) != NULL;

	/* ⑤ 兜底：设备名 == 驱动名 */
	return (strcmp(pdev->name, drv->name) == 0);
}
```

| 步骤 | 匹配键 | LED 是否走 |
|------|--------|-----------|
| ① `driver_override` | 强制驱动名 | 否（本板没设） |
| ② `of_driver_match_device` | **`compatible` 对表** | **✅ 命中 `"gpio-leds"`** |
| ③ `acpi_driver_match_device` | ACPI | 否（ARM 无 ACPI） |
| ④ `id_table` | 平台 ID 表 | 否（leds-gpio 没这张表） |
| ⑤ 名字兜底 | `pdev->name` == `drv->name` | 否（"leds" ≠ "leds-gpio"） |

**LED 命中第 ② 步**：`of_driver_match_device()` 拿 `leds` 节点的 `compatible = "gpio-leds"`，比对 `of_gpio_leds_match[] = { {.compatible="gpio-leds"} }`，命中后设备模型回调 `gpio_led_probe()`。

**（6）完整时间线**

```text
① of_platform_bus_create 遇到 leds 节点（有 compatible，status 默认 okay）
② of_device_alloc：
     platform_device_alloc("", -1) → kzalloc(platform_object) + device_initialize
     数 reg/irq = 0/0 → 不建 resource 表
     dev.of_node = of_node_get(leds)；命名 → "leds"
③ of_platform_device_create_pdata：dev.bus = platform_bus_type
④ of_device_add → platform_device_add：
     parent = platform_bus；dev_set_name("leds")；（无 resource 跳过 insert_resource）
     device_add(&dev)  ← 进入设备模型
⑤ device_add 触发 bus.match = platform_match：② of_driver_match_device 命中 "gpio-leds"
⑥ 设备模型回调 gpio_led_probe()（见 §3.2）
```

**一句话：** `platform_device` 是设备树节点在 Linux 设备模型里的壳——`of_device_alloc` 把 `device_node` 翻译成 `resource` 表和 `dev.of_node` 指针，`platform_device_add` 再按 `name` 命名、挂到 `platform_bus_type`；总线核心调用 `platform_match`，其中第 ② 步 `of_driver_match_device` 用 `compatible` 对表，正是 LED 案例里 `"gpio-leds"` 命中 leds-gpio 驱动的落点。

### 3.3 `led0` 子节点三个属性的读法

对照本板 dts：


|------|----------|--------|------|
| `label` | `fwnode_property_read_string(child, "label", ...)` | `"sys-led"` | LED 的名字 → `/sys/class/leds/sys-led/` |
| `gpios` | `devm_get_gpiod_from_child(dev, NULL, child)` | `&gpio1 3 ACTIVE_LOW` | 拿到 GPIO1_IO03 的描述符（见 §5） |
| `default-state` | `fwnode_property_read_string(child, "default-state", ...)` | `"on"` | 上电默认点亮（见 §3.4） |
| `linux,default-trigger`（可选，本板没写） | `fwnode_property_read_string(child, ...)` | 无 | 默认触发源（heartbeat/timer 等，运行时可改） |

### 3.4 `create_gpio_led`：注册到 LED class 子系统

| 点 | 说明 |
|----|------|
| `brightness = LED_FULL` | **`default-state = "on"` 得到的是 255（满亮度），不是 1**（LED class 用 0~255）。板上实测 `brightness` 初值 = 255 |
| `gpiod_direction_output(gpiod, state)` | 把脚设成输出；因为 active-low，内核写 1 → 物理脚输出 0 → 共阳 LED 点亮（见 §5.4） |
| `led_classdev_register` | 生成 `/sys/class/leds/sys-led/` 下的 `brightness` / `trigger` 等文件 |

## 四、链 B：`pinctrl_gpio_leds` 为什么这样写（独立链）

> 源码：`drivers/pinctrl/freescale/pinctrl-imx.c`、`pinctrl-imx6ul.c`、`drivers/base/pinctrl.c`、`drivers/pinctrl/devicetree.c`  
> 通用机制与屏 `09`、网卡 `10` §3.4.1 是**同一套 pinctrl 子系统**。

### 4.1 核心结论：pinctrl 组不走 compatible 匹配

很多人误以为 `pinctrl_gpio_leds: gpio-leds { ... }` 也会像 `leds` 一样被某个驱动"匹配"。**不是。**

```dts
pinctrl_gpio_leds: gpio-leds {
    fsl,pins = <
        MX6UL_PAD_GPIO1_IO03__GPIO1_IO03	0x17059
    >;
};
```

它**没有 `compatible`**，它只是 iomuxc 控制器节点下的一份**"引脚配置数据"**。它自己不是设备，不被任何驱动单独 probe。它被消费的唯一方式，是 `leds` 节点通过 `pinctrl-0 = <&pinctrl_gpio_leds>` **按 phandle 引用它**。

### 4.2 控制器链：iomuxc 才是被"匹配"的设备

真正被 `compatible` 匹配的，是它**上面的 iomuxc 控制器**：

```dts
/* arch/arm/boot/dts/imx6ull.dtsi */
iomuxc: iomuxc@020e0000 {
    compatible = "fsl,imx6ul-iomuxc";
    ...
};
```

```c
/* drivers/pinctrl/freescale/pinctrl-imx6ul.c:326 */
static struct of_device_id imx6ul_pinctrl_of_match[] = {
	{ .compatible = "fsl,imx6ul-iomuxc", .data = &imx6ul_pinctrl_info, },
	{ .compatible = "fsl,imx6ull-iomuxc-snvs", .data = &imx6ull_snvs_pinctrl_info, },
	{ /* sentinel */ }
};

static int imx6ul_pinctrl_probe(struct platform_device *pdev) { ... }
```

| 层级 | 匹配键 | 内核入口 | 作用 |
|------|--------|----------|------|
| **iomuxc 控制器** | `fsl,imx6ul-iomuxc` | `imx6ul_pinctrl_probe` | 建立整个 pinctrl 设备，登记所有 group |
| **`pinctrl_gpio_leds` 组** | 无（只是 group 数据） | 被消费，不单独 probe | 描述 GPIO1_IO03 的 mux + pad 配置 |

`iomuxc` 在 `arch_initcall` 阶段就注册，它的 probe 会**扫描自己节点下所有带 `fsl,pins` 的子节点**（即一个个 group，包括 `pinctrl_gpio_leds`），解析成内部 pin map。这个阶段只是"登记"，**还没真正写寄存器**。

### 4.3 消费链：`pinctrl-0` + `pinctrl-names` → `pinctrl_bind_pins()`

真正"写寄存器、把脚 mux 成 GPIO"发生在 **leds 驱动 probe 之前**，由设备核心自动完成：

```text
leds 的 platform_device 创建后、gpio_led_probe 调用前
        ↓
device core → pinctrl_bind_pins(&pdev->dev)          /* drivers/base/pinctrl.c:22 */
        ↓
读 pinctrl-names（="default"）+ pinctrl-0（phandle → pinctrl_gpio_leds）
        ↓
pinctrl_dt_to_map → imx_dt_node_to_map                /* 解析 fsl,pins 成 pin map */
        ↓
pinctrl_select_state("default")
        ↓
imx_pmx_set / imx_pinconf_set                         /* 写 IOMUXC 的 MUX 和 PAD 寄存器 */
        ↓
GPIO1_IO03 被 mux 成 GPIO 功能，pad 电气按 0x17059 配好
```

所以本板 dts 里 `leds` 节点写的这两行，作用是**在 leds-gpio 驱动 probe 前**把脚备好：

```dts
pinctrl-names = "default";
pinctrl-0 = <&pinctrl_gpio_leds>;
```

| 字段 | 含义 |
|------|------|
| `pinctrl-names = "default"` | 定义一组状态名，这里只有一个"默认状态" |
| `pinctrl-0 = <&pinctrl_gpio_leds>` | default 状态用到的 group 列表（phandle 引用） |

### 4.4 `fsl,pins` 单行：`MX6UL_PAD_GPIO1_IO03__GPIO1_IO03  0x17059`

```text
MX6UL_PAD_GPIO1_IO03__GPIO1_IO03	0x17059
│                    │              │
│                    │              └─ PAD 电气配置（上下拉/驱动/速度等）
│                    └─ 复用功能：把 GPIO1_IO03 pad 选为 GPIO1_IO03（ALT5 = GPIO）
└─ 物理 pad 名
```

宏展开（`imx6ul-pinfunc.h` 里 `MX6UL_PAD_GPIO1_IO03__GPIO1_IO03` 5 个值）：

```text
0x0068   mux_reg    → 物理 0x020E0068（IOMUXC_SW_MUX_CTL_PAD_GPIO1_IO03）
0x02F4   conf_reg   → 物理 0x020E02F4（IOMUXC_SW_PAD_CTL_PAD_GPIO1_IO03）
0x0000   input_reg  → 无输入寄存器（本脚不需）
0x5      mux_mode   → ALT5 = GPIO1_IO03
0x0      input_val
```

`0x17059` 按位（PAD_CTL 寄存器）：

| 位段 | 值 | 含义 |
|------|----|------|
| SION（bit30） | 1 | 软件输入使能 |
| PUS（上下拉选择） | 11 | 22K 上拉 |
| PUE（pull/keeper 使能） | 1 | 使能上下拉 |
| PKE | 0 | 关闭 keeper |
| ODE | 0 | 关闭开漏 |
| SPEED | 01 | 100 MHz |
| DSE（驱动强度） | 011 | R0/3 |
| SRE（压摆率） | 1 | 慢压摆 |

这些细节已在 `24` 附录 D 展开，本文不再重复；这里只需记住：**`fsl,pins` 一行 = "选哪个功能（mux）+ 用什么电气（pad）"**，由 pinctrl 子系统在 probe 前写进 IOMUXC。

## 五、链 C：`gpios = <&gpio1 3 GPIO_ACTIVE_LOW>` 如何解析

### 5.1 三元组结构

```dts
gpios = <&gpio1 3 GPIO_ACTIVE_LOW>;
         │    │  │
         │    │  └─ 极性标志：0x1 = 低电平有效（active-low）
         │    └─ 该控制器内的引脚号：3 → GPIO1_IO03
         └─ phandle：指向哪个 GPIO 控制器（gpio1）
```

编译成 dtb 后（板上 `dtc` 反编译实测）：

```text
gpios = <0x08 0x03 0x01>;
         │    │    └─ 0x01 = GPIO_ACTIVE_LOW
         │    └─ 0x03 = 脚号 3
         └─ 0x08 = gpio1 的 phandle
```

label 消失、变 phandle，与网卡文档 `10` 里 `phy-handle` 的机制完全一样。

### 5.2 `&gpio1` phandle → gpio-mxc 控制器

`&gpio1` 指向 `imx6ull.dtsi` 里定义的控制器节点：

```dts
gpio1: gpio@0209c000 {
    compatible = "fsl,imx6ul-gpio", "fsl,imx35-gpio";
    ...
};
```

```c
/* drivers/gpio/gpio-mxc.c:152 */
static const struct of_device_id mxc_gpio_dt_ids[] = {
	{ .compatible = "fsl,imx1-gpio", ... },
	...
	{ .compatible = "fsl,imx35-gpio", ... },   /* ← 第二项命中 */
	...
};
```

| 元素 | 含义 |
|------|------|
| `gpio1` | SoC 第 1 组 GPIO（Bank1），物理基址 `0x0209c000` |
| `3` | Bank1 里的第 3 根（offset 3）→ **GPIO1_IO03** |
| GPIO 全局号 | (bank-1)×32 + offset = **3**（Linux gpio 子系统内部编号，本板正好是 3） |

内核 gpiolib 拿到 phandle 后，找到对应的 **gpio-mxc** 控制器，再由脚号 3 定位到该控制器内的 GPIO 资源，返回一个 `struct gpio_desc`。

### 5.3 驱动读取路径

```text
gpio_leds_create(led0 子节点)
  → devm_get_gpiod_from_child(dev, NULL, child)
  → fwnode_get_named_gpiod(child, "gpios", 0, ...)
  → of_get_named_gpiod_flags(...)          /* 解析 phandle + 脚号 + 标志 */
  → gpiod_get_index(...) / gpio_request
  → 返回 gpiod（含 active-low 信息）
```

### 5.4 `GPIO_ACTIVE_LOW`：gpiolib 自动反相

`GPIO_ACTIVE_LOW = 0x1`。它的作用**不是**"直接输出低电平"，而是告诉 gpiolib：**这颗 LED 是低电平点亮**，让上层语义保持"1 = 亮、0 = 灭"。

```text
物理事实：共阳 LED，阴极接 GPIO1_IO03 → 脚输出 0 才亮
逻辑需求：/sys/class/leds/sys-led/brightness 写 1 应该"亮"
解决办法：GPIO_ACTIVE_LOW 让 gpiolib 在逻辑值和物理电平之间自动取反

brightness = 1（逻辑"亮"）
   → gpio_led_set → gpiod_set_value(gpiod, 1)
   → gpiolib 因 active-low 反相 → 物理脚输出 0
   → 阴极 0，共阳 LED 点亮 ✅

brightness = 0（逻辑"灭"）
   → 反相 → 物理脚输出 1 → LED 灭 ✅
```

| 项 | 值 |
|----|----|
| `gpiod_direction_output(gpiod, state)` | state=1（on），因 active-low，物理输出 0 |
| 逻辑层 `brightness` 范围 | 0~255，1 与 255 都"亮"（leds-gpio 只看 0/非 0） |
| 板上实测 | `echo 1 > brightness` 亮，`echo 0 > brightness` 灭 |

**一句话：** `gpios` 三元组 = "哪个控制器（phandle）+ 哪根脚（3）+ 什么极性（active-low）"，gpiolib 负责拿到 GPIO 并按极性自动反相，让上层统一用"1=亮"的逻辑。

## 六、三条链的时序（一次启动的完整顺序）

```text
① arch_initcall 阶段
   iomuxc（fsl,imx6ul-iomuxc）probe → 登记所有 group（含 pinctrl_gpio_leds）
   gpio1（fsl,imx6ul-gpio）probe → gpio-mxc 控制器就绪，注册到 gpiolib

② of_platform_populate 到 leds 节点
   → 建 platform_device（status 默认 okay）
   → device core：pinctrl_bind_pins()         ← 链 B 生效：写 IOMUXC，脚 mux 成 GPIO
   → platform_match：compatible "gpio-leds"   ← 链 A 匹配
   → gpio_led_probe → gpio_leds_create
        → 遍历 led0：
            读 label="sys-led"
            读 default-state="on" → LED_FULL=255
            读 gpios=<&gpio1 3 ACTIVE_LOW>    ← 链 C 生效：拿 gpiod
        → create_gpio_led：
            gpiod_direction_output(gpiod, 1)  → 物理输出 0 → 灯亮
            led_classdev_register → /sys/class/leds/sys-led/

③ 用户空间
   echo 1/0 > /sys/class/leds/sys-led/brightness  → 亮/灭
   echo heartbeat > .../trigger                   → 心跳闪烁
```

注意顺序：**pinctrl（链 B）在 gpio_led_probe（链 A）之前**就由设备核心完成，所以驱动 probe 时脚已经是 GPIO、电平能正常输出。

## 七、为什么这样写（设计动机与最佳实践）

### 7.1 为什么要 `compatible = "gpio-leds"`，而不是别的

- `gpio-leds` 是 Linux **内核自带的 LED 驱动绑定名**，写在 `leds-gpio.c` 的 `of_gpio_leds_match[]` 里。
- 只要你写 `gpio-leds`，内核就自动有驱动接管，**不用自己写任何 C 代码**——这正是"改设备树就能点灯"的原因。
- 换成别的字符串（比如 `my-leds`）→ 没驱动匹配 → 节点被无视，灯不亮。

### 7.2 为什么 `label` / `default-state` / `gpios` 要分开写

- 每个子节点（`led0`）表示**一颗** LED，节点下用属性描述它的"名字 / 初始状态 / 脚"。
- 一个 `leds` 节点可以有多个子节点（`led0`/`led1`/…），驱动 `device_for_each_child_node` 一次全建出来。这比写死一个 LED 更通用。
- `label` 决定 sysfs 路径名，和节点名解耦：节点可以叫 `led0`，用户看到的是 `sys-led`。

### 7.3 为什么 pinctrl 要单独一个 group，而不是把 mux 写死在 leds 里

- 内核把"脚复用"（pinctrl）和"设备功能"（leds）**彻底分开**：pinctrl 归 iomuxc 控制器管，leds 归 leds-gpio 管。
- `leds` 只是"用脚"，它通过 `pinctrl-0 = <&...>` **声明**需要哪些 group，具体怎么 mux 是 pinctrl 的事。
- 好处：同一颗 pad 被多个外设共用时，谁 `status=okay` 谁引用，冲突一目了然；本板 GPIO1_IO03 还同时被 `&tsc`（电阻触摸）引用，因为 tsc 被 disabled，才不冲突（见 `24` L0）。

### 7.4 为什么要 `GPIO_ACTIVE_LOW`（而不是在代码里反相）

- 共阳 LED 是"低电平亮"，是**硬件事实**。
- 用 `GPIO_ACTIVE_LOW` 在 dts 里声明极性，让 gpiolib 统一反相，上层永远用"1=亮"的直觉操作。
- 不写它 → gpiolib 默认 active-high → `echo 1 > brightness` 实际输出高电平 → 灯反而**灭**，语义混乱。

### 7.5 一句话设计原则

**dts 描述的是"硬件真相"（哪根脚、什么极性、默认状态），内核各子系统据此匹配并驱动；`compatible` 选驱动、phandle 引资源、`fsl,pins` 配复用，三者各司其职。**

## 九、一句话

LED0 设备树的匹配本质是三条链的接力：**`compatible = "gpio-leds"` 让 leds-gpio 驱动接管、遍历出 `sys-led`；`pinctrl-0` 让 iomuxc 在 probe 前把 GPIO1_IO03 mux 成 GPIO；`gpios = <&gpio1 3 GPIO_ACTIVE_LOW>` 让 gpiolib 拿到这根脚并按共阳极性自动反相**——三条链齐了，`/sys/class/leds/sys-led/brightness` 才能指哪亮哪。
